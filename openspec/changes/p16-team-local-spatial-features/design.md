## 2. 口径（本 change 的第一交付，先于任何数字）

### 2.1 位置一律以 `ControlFact` 为权威

2026-09-29 侦察实测：同一批 7372 个 episode，两种口径给出的「后场起点占比」差 **3 倍**：

| 口径 | 后场起点 | 机制 |
|---|---|---|
| 首个决策动作的 `Event.x` | **7.5%** | ❌ episode 开场是**带球**，首个 `pass`/`shot` 晚**中位 8 秒**（p90 16s），球已离后场 |
| `control_established.location` | **23.5%** | ✅ 观测层对「episode 在哪开始」的定义 |

**规则**：
- episode 的**起点位置**取该 episode 的 `control_established` 事实的 `location`；
- **终点位置**同理取收束侧事实（具体取哪个字段在实现时定，且**必须与起点同源**）；
- **不得**以决策动作的 `Event.x` 代替——它是**动作主体的位置**（对 tackle 甚至是防守者位置，
  见 `lib.rs:4085`），只有在主体恰为持球者时才等于球位。

### 2.2 已知放大器：门球落点硬编码过中线

`goal_kick_land`（`lib.rs:3159`）逐字：

```rust
let (lo, hi) = if dir > 0.0 { (0.50, 0.82) } else { (0.18, 0.50) };
```

门将开大脚落点恒过半场，占重开的 **31.7%**（1666/5258 实测）。
**这不是缺陷**（门球本就该开到中场），但它是「用首个决策动作当位置」时把后场开局记成中场开局的主要来源。
**记录在案，供 reader 理解偏差量级。**

### 2.3 时间基准

sidecar 有四种 `TimeBasis`（`StateCommit` / `EventEmit` / `DeterministicFlightEnd` / `Unknown`）。

**规则**：**同一特征只混用同 basis 的字段**；跨 basis 的特征必须显式标注并单独列出。
（P17A 报告 §6 已把 basis 混用列为已知局限，本 change 不得重复该错误。）

## 3. 特征清单

### 3.1 静态特征（**复用既有实现，不重写**）

`viewer/match-metrics.js` 的 `teamShape(frame, team)` 已实现：
`depth`（q10–q90 纵深）/ `width` / `cx`,`cy`（重心）/ `spread`（到重心距离）/ `n`（有效人数）。
引擎侧实测可用：`sampleEngineFrames(game, {stepSec})` 60s 得 301 帧、每帧 22 人、**0 个 null**。

⚠️ **层差（必须决策，见 §5）**：`teamShape` 是 **JS**，而 15B 的 `PhaseAnnotator` 是 **Rust**
（design §11 的入参/产物都在 Rust 侧）。`engine/src/` 里**没有任何团队宽度/重心/spread 实现**。

⚠️ **两处不是引擎侧的约束**：`includeExtrapolated:false` 与 `MIN_OUTFIELD_PLAYERS = 7`
在引擎侧是**空操作**（引擎帧不带外推标记、每队恒 10 名外场）——它们只对真实侧（SkillCorner）生效。
**不得**把它们写成「引擎侧会掉帧」的理由。

### 3.2 时间关系特征（本 change 新增，**这是实际工作量**）

原 #16 的静态快照判不了三档（`build_up ≠ 后场`、`progression ≠ 球向前移动`、
`final_third ≠ 前 1/3`）。新增四条，每条须给定义 + 覆盖率 + 缺失处理：

| 特征 | 定义要点 | 备注 |
|---|---|---|
| **球门向净推进** | 按球队进攻方向归一化（主队攻 x=1、客队攻 x=0），窗口内末位置 − 首位置 | 已有口径（侦察 §1） |
| **推进 / 回撤 / 横向转移** | 连续动作窗口内三者的分量；纵向与横向分开 | 需定义窗口长度 |
| **线间距变化** | 队形 `depth`/`spread` 随推进的变化 | 依赖 §3.1 的层差决策 |
| **接应是否形成** | 推进后球前方是否出现可接应队友（距离/角度阈值待定） | 最接近「战术意图」的一条 |

**每条特征必须报告**：可计算帧占比 / `unknown` 占比 / 缺失原因（外推点、人数不足、basis 不可得）。

### 3.3 轨迹数据从哪来

`episode.event_indexes` **只挂 1.6% 的 beat**（8361/536426）——**「用它重建轨迹」不通**。
必须走 `sampleEngineFrames` 的全量采样（侦察实测两种读法差别很大：
`event_indexes` 口径得 18.1% 后场起点，全量 23.5%）。

## 4. phaseability gate（本 change 的验收）

**不是「特征算得出来」，而是裁决三档能否判定。** 二选一，都要证据：

- **够** → 给出三档各自的可执行谓词：用哪些特征、什么时间窗、如何**不退化**成「区域 = 阶段」；
- **不够** → 明确指出缺什么（哪类观测不存在），以及 15B 应保留 `unknown` 还是需补数据/模型。

**硬约束**：**不得**用区域/坐标冒充战术阶段。若最终只能用几何代理，
必须命名为**证据**（如 `GoalwardProgressEvidence`），**不得复用 `Phase`**。

**判别检验的做法**（实现时定细节）：对每一档给出「应属该档」与「不应属」的参考集，
用特征做可分性检验；**参考集不能只用区域构造**（那会让检验退化成循环论证）。

## 5. 待决策（实现前须闭合）

   （前者改动引擎侧、后者只需导出；两条都要估工。）

3. **判别检验的参考集怎么构造**（不得用区域构造，否则循环）。
4. **三档若判不了的降级路径**：写进 15B design 的 `unknown` 策略。
