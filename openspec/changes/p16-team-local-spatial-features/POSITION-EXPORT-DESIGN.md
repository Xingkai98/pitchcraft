## 1. 事实核对：用户三条论证

**结论：三条论证均成立。① 机制成立、损失量级需收窄表述；② 成立（这是支持 C 的主要理由）；
③ 成立但适用范围要收窄——它只约束「进事件流」的选项。**

### ① 「引擎本来就有真值，`movers` 只是它的差分」——**成立**

逐条核过：

- `MatchState.pos: [(f64,f64); 22]` 的读写点实测 **175 处**（用户记 140，同量级）；
  决策逻辑直接读它（`nearest_defender` / 传球目标 / 空间打分）。
- **每拍 22 人里平均 19.46 人不出现在 beat 里**（30 场 / 160894 拍实测）。
  `movers` 是**稀疏增量**：`compute_mover_candidates` 对「dead-zone 内不动」的球员
  `continue`，门将/罚下/被排除者另有分支。

**损失量级（本轮实测，与引擎真值 `st.pos` 直接对照）**：

| 对照 | 最大偏差（归一） | 均值 | 有偏差的帧 |
|---|---|---|---|
| **beat-only 重放 vs 引擎真值 `st.pos`** | **0.0168** | 0.000009 | **58 / 5365（1.1%）** |
| viewer 渲染路径（`sampleEngineFrames` 整秒） vs 引擎真值 | **0.0386** | 0.00219 | 529 / 750（70.5%）帧含 >1cm 点；点级 7.47% |
| **beat-only 重放 vs 渲染路径**（**可复现**，见下） | **0.0796** | 0.00278 | 616 / 894 帧含 >1cm 点；点级 9.27% |

⚠️ **三行都是归一化坐标（0–1）下的欧氏距离，没有换成米**。**归一化距离不能乘单一标量**
换算成米——球场 105×68 是各向异性的，正确换算是 `hypot(dx×105, dy×68)`。
本文件初稿曾在括号里写「≈8.4 m / ≈1.1 m / ≈2.5 m」（那是**直接 ×105 或 ×68**，两行还用了
不同标量）——**已删**：那是错的换算，且两行口径不一致。
真要读米数，最差点 `t=800, id=10`（`dx=0.0422, dy=−0.0675`）的正确值是
`hypot(0.0422×105, 0.0675×68) ≈ 6.38 m`（直接 ×105 会**高估 ~31%**）。
**判断量级请以归一化值为准**：最大偏差 0.0796 ≈ 球场对角线的 8%。

**对照的两端**：前两行都以「引擎真值 `st.pos`」为对照，需要临时插桩才能复现
（本 change 的插桩已删，不进库）；**第三行是「重放 vs 渲染路径」**，两端都来自公开面，
**可复现**——探针
`openspec/changes/p16-team-local-spatial-features/notes/probes/position-fidelity.mjs`
（`node …/position-fidelity.mjs 1 900`；只用公开 API，零引擎插桩）。

**机制（已定位两个，非推测）**：

1. **highlight 提交点直写 `st.pos`**：`commit_beat_positions_ex` 的 `extras` 通道
   （传球落点对账 / 拦截者就位 / 门将扑救位 / tackle 结算）**不产 mover**；
   实测最大偏差点 `t=4588, id=16` 紧邻 `tackle@4587`。
2. **carry-forward 会把陈旧位置一直带下去**：某球员一旦经上述路径被改写、
   而此后若干拍又不进 `movers`（dead-zone 内不动），重放就**永久停留在旧值**，
   直到该球员下一次进 `movers` 才自愈。

> ⚠️ **两处更正（必须记录，本 agent 自己犯的）**
>
> 1. `OPEN-QUESTIONS.md` 初稿写过「A 与 JS `sampleEngineFrames` 逐点同值，
>    `max |Δ| = 0.000000`」。**那是探针 bug**：比较脚本对数组误用 `.x`/`.y`（得 `NaN`），
>    而 `NaN > max` 恒 `false` ⇒ max 永远是初值 0，计数器却照常 `++`
>    （所以「比了 13134 个点」看着很可信）。**假证据**。
> 2. 我在把设计草稿改成 v2 时，一度把「beat-only 重放 **vs 渲染路径**」的 **0.0795**
>    当成「beat-only 重放 **vs 真值**」的损失量级引用。**这是拿两个不同对照的数当同一个**——
>    0.0795 里**大部分是渲染路径自己的偏差**（0.0386），不是重放的损失。
>    重放的真实损失是 **0.0168**，比它小 4.7 倍。
>
> **教训（写进本 change 的产物纪律）**：探针须①对「比较失败（NaN）」显式判红；
> ②**每张表都写明对照的两端是什么**——「A vs B」与「A vs C」不可混。

**这条论证的结论因此要**收窄**表述**：
`movers` 确实是**残缺**的派生物（上面两条机制成立，损失确凿），所以「引擎有真值、
应当导出真值」这个**原则**成立；但**损失的绝对量级不大**（整秒点上最大偏差
**0.0168（归一化）**、只影响 1.1% 的帧）。**因此支持 C 的主要是论证 ②（原则），
不是损失的大小。**

### ② 「A 违反 P15A 自己的原则」——成立

`engine/src/observation.rs` 模块头逐字：

> **本文件不引用 `MatchState`**——提交点在 `lib.rs` 调用，本模块**不读取事件文本、
> 不做任何推断**。

beat-only 重放正是「从事件文本事后推断」，与 P15A 建观察层时刻意拒绝的做法同构。
用户指出我把 C 写成「撞本 change 边界」是**判错了边界**：C 加一个**只读位置事实**与
`ControlFact` 同类——不动决策、不动 RNG、不动正式事件流。**接受这条更正。**

### ③ 「体积才是当初没记录的真实原因」——成立，**但只对「进事件流」的选项成立**

体积实测（20 场 / 90 分钟，引擎现有事件流 **1663 KB/场**）：

| 每拍全量 22 人的编码 | 字节/拍 | 增量/场 | 300 seed |
|---|---|---|---|
| 引擎现有 verbose mover 格式 | 2134 | **+672%** | ≈ 3.3 GB |
| 紧凑 `id:x,y;` | 352 | **+111%** | ≈ 540 MB |
| 量化 0.1 m `id,420,310;` | 220 | +69% | ≈ 338 MB |

⚠️ **但这条数字不适用于 sidecar**：实测 `DiagnosticMatch` **从不被序列化**——
`events_json()` 只序列化 `events`（`observation.rs`），sidecar 是**进程内的 Rust 值**，
经 opt-in API 返回。**位置若进 sidecar，事件流的字节增量 = 0。**

⇒ 用户论证 ③ 排除了「把位置塞进事件流」，但**没有**排除「把位置放进 sidecar」。
真正的粒度选择因此比我原先设想的宽。

## 2. 粒度方案

### 2.1 选项对比

| # | 方案 | 保真 | 事件流增量 | sidecar 内存 | 判定 |
|---|---|---|---|---|---|
| **G0** | 不记，从 beat 重放（我原推荐的 A） | ⚠️ 最大偏 **0.0168**（归一化），1.1% 帧 | 0 | 0 | **否**（论证 ①② 否决；原则错，量级小） |
| **G1** | **每 tick 全量 22 人 → sidecar** | ✅ **恒等** `st.pos`（零损失） | **0** | ≈ 1.9 MB/场 | **推荐** |
| G2 | 只在 `ControlFact` 提交点记快照 | ⚠️ 太稀疏（多数拍没有事实） | 0 | 极小 | 否（15B 需逐帧队形，P36 口径是逐帧算再均值） |
| G3 | 每 N tick + 插值 | ⚠️ 插值误差 | 0 | 小 | 否（稀疏采样改变估计量的 n 依赖——P37 D2 否决 trim1 的同类理由） |
| G4 | 每 tick 全量 → **事件流**（改协议） | ✅ | **+69% ~ +672%** | — | **架构级，另立 change** |

### 2.2 推荐：G1（每 tick 全量位置 → sidecar）

> **措辞对齐（用户 2026-09-29 指出，务必先读）**：**sidecar 就是 `DiagnosticMatch`**，
> 它（及其 `events_json()` 只序列化 `events` 的性质）**早已存在**。
> G1 是**给它加一个字段**（`state_snapshots`），**不是**新加一个 sidecar、
> 也**不是**新的序列化取舍。「不入 JSON」是 `DiagnosticMatch` **本来就有**的性质。

**为什么每 tick（1 Hz）而不是 0.2s**：1 Hz 是引擎的原生 tick 分辨率，快照**不做插值**、
无估计量偏差；下游要更稀可自行抽稀（子采样是纯函数，不改上游）。采样更细反而制造
「看起来更精确」的伪分辨率。

**为什么全量 22 人而不是只记外场**：门将位置是 `possessionProxy`（控球代理，含门将参与
最近者判定）的输入，也是「球门向推进」的参照；剔除门将的口径属**下游**（P36 口径已在
`teamShape` 里做），不应在上游把数据扔掉。

### 2.2b G1 的核心承诺必须有守卫（审阅 P1-4）

G1 相对 G0 的**唯一**正当理由是「快照 = `st.pos` 的逐位恒等（零损失）」。
**这条承诺不能只活在文字里**——按本仓「假覆盖」的教训，必须有一条**定向变异可红**的测试：

- **正向**：按 seed 跑，逐拍断言 `snapshot[i].pos == st.pos@tick_i`（对拍内 `st.pos` 求哈希相等）。
- **反证条**：把采样点改成「`emit_beat_with_main` 之后」→ 断言必须红（因为丢拍）。
  这条同时是 §2.4 采样点修复的**验收**。
- **覆盖面**：断言「快照数 == tick 数」（不是 beat 数）——seed 1 上 `5399 != 5365`，
  这条断言对该变异有区分度。

⚠️ **判别力边界**（审阅 P2-NEW-2）：`caliber_coverage_on_a_real_seed` 只对
「使**起点可得率 < 100%**」的变异敏感；若把起点换成带 fallback 的动作位置口径
（不产生 `None`），**它仍绿**——那种变异由
`caliber_start_comes_from_control_fact_not_action_position` +
`caliber_guard_has_discriminating_power` 抓。**别把覆盖测试当成「起点来源」的通用守卫。**

### 2.3 记在哪一层

**推荐：`DiagnosticMatch` 新增字段**，**不新增 `ControlFactKind`，不改闭集枚举**。

```rust
/// 逐 tick 的引擎位置快照（P16）。**只读观测量**，不是控制事实。
pub struct StateSnapshot {
    pub t: ObservedTime,          // basis 恒 StateCommit（tick 末提交）
    /// 22 人位置（下标 = id，与事件协议同：0=主队门将、21=客队门将）。
    pub pos: [(f64, f64); 22],
    /// **本拍结束时仍活跃的**高亮参与者 id（取自 `st.highlight` 的 `participants` 的 id 列）。
    /// 含两种情形：飞行中间拍（同一高亮延续），与**链式 finalize 拍**
    /// （本拍 finalize 后又建了新高亮，如 `start_goal_kick`）——定义统一为「拍末活跃者」。
    /// 它们的位置由高亮**钉住**（`commit_beat_positions_ex` 跳过其 `st.pos` 写回），
    /// 是**进行中的量**、不是稳定观测——记下来是为让下游能过滤或单独报告这批拍。
    /// （**不是**为了「防陈旧」：实测飞行期该位置**不变**，见 §2.4。）
    pub frozen: Vec<i32>,
}
// DiagnosticMatch 增：pub state_snapshots: Vec<StateSnapshot>,
```

**三条理由**：

1. **不撞不变量**。`ControlFact` 闭集不变 ⇒ 不变量 10（detail↔kind 配对）不受影响；
   事实数不变 ⇒ **`gap_count() == 0` 与 300 seed 校准门不受影响**。
   若改成新增 fact kind，则每次 tick 都产 fact，`facts` 量级 ×5000，
   `invariant_violations` 的比较语义、P17A 的全部 fact 统计都会漂——**那是破坏，不是扩展**。
2. **指纹有字段盲区——是限制，不是纯收益**。`sidecar_schema_fingerprint()`
   （`tests/p17a/model.rs`）只 `add!` 17 个闭集枚举的 `ALL`，**不含结构体字段**。
   故新增 `state_snapshots` **不会**让它陈旧（字面事实），但代价是：
   带位置的 P16 运行与不带位置的 P17A 运行，在该指纹上**不可区分**——
   这与该函数的既定用途（「闭集变化必然改变指纹，使两次结果不可比在产物层可察觉」）
   **方向相反**。⇒ **必须靠别的手段补**：递增 `CALIBER_VERSION`，并在 P16 产物里
   显式记录「是否含 `state_snapshots`」（及采样点数），使两次运行可比性可判。
3. **事件流不变，但源码文本会变**。`simulate()` 传 `disabled()` recorder，
   `observe_state` 若仿既有命令写 `if !self.enabled { return; }`，则所有命令是空操作 ⇒
   **事件流逐字节一致门结构上不受影响**（与 P15A 既有的
   `p15_recorder_stays_out_of_the_decision_path` 同一机制，不是新承诺）。

   ⚠️ **但「不碰生成逻辑」≠「不碰引擎源码文本」**，两点后果须预先声明：
   - `tests/p17a/report.rs` 的 `engine_source_fingerprint` 覆盖
     `lib.rs` + `observation.rs` + `rng.rs`——本 change 会改前两个 ⇒ **P17A 已落盘产物
     须重生成**才与源码「同源」（否则 `on_disk_artifacts_share_one_provenance_block` 类
     一致性检查会提示不可比）；
   - `tools/benchmark-baseline.test.mjs` 的 `engineFingerprint.sourceSha256` 哈希
     `engine/src/lib.rs` ⇒ 源哈希变，哨兵走**慢路径**（重算引擎指标；行为不变则**放行**并
     提示重生成，**不是硬失败**）。

### 2.4 采样点与调用形态

#### ⚠️ 采样点**不是** `emit_beat_with_main`（审阅 P0-1 更正）

初稿把采样点定在 `emit_beat_with_main` 之后。**那是错的**，实测：

- **出拍有两个族**：`emit_beat_with_main`（12 处出现，含定义）与**裸 `beat_event(...)`**
  （27 处出现，含定义）——后者遍布 `finalize_highlight` 飞行拍、`advance_restart_prep`、
  `advance_dead_ball`、`start_goal_kick`、角球/界外/任意球/头球/解围的 emit。
  实测 5 seed：**≥16.7% 的拍不经 `emit_beat_with_main`**（26822 拍里 22334 带 `main`，
  其中还有一批走裸 `beat_event`）。
- **更致命：有些 tick 根本不产 beat**。seed 1 实测 `while t < dur` 共 **5399** 个 tick，
  但 beat 只有 **5365** 个——**34 个 tick 无任何 beat**（其事件是 `foul` 或 `kickoff`）。
  这些 tick 上 `emit_beat_with_main` 一次都不调。

⇒ **正确的采样点：`match_events` 的 `while t < dur { tick(...); ... }` 循环体里、
`tick` 返回之后**，取 `st.pos` 与 `st.highlight`。这样：

- 覆盖**每一个** tick（含犯规/开球的无 beat 拍）；
- 拍数 = **tick 数**（5399/场），**不是** beat 数（5365/场）——§2.6 的内存估算据此更正。

#### 为什么是「`tick` 返回之后」而不是「`tick()` 内、finalize 之前」

初稿这两句**互相矛盾**（审阅 P1-NEW-1 抓到）：`finalize_highlight` 是在 **`tick()` 内部**
调用的，`tick` 一返回 finalize 早就跑完了——「返回之后」与「finalize 之前」是两个互斥的位置。

**取「返回之后」，因为那正是「本拍终态」的定义**：`tick()` 返回时该 tick 的全部状态变更
已结束（`finalize_highlight` 在 `tick` 内、其后无再改 `st.pos`/`st.highlight` 的路径）。
另一侧（finalize 之前）取到的是**未对账的中间态**，且要把采样写进 `tick()` 内部——
与「在主循环采样」冲突，并让「快照数 == tick 数」这条守卫依赖 `tick` 的早返回分支。

⚠️ **`frozen` 在 finalize 拍上不保证为空**（审阅 P1-B 更正）：`finalize_highlight` 用
`st.highlight.take()` 消费**本拍被 finalize 的那条**高亮，但它的若干分支**会链式建新高亮**——
例如 `ShotOffTarget` / 出界 → `start_goal_kick` / `start_corner` / `start_throw_in`，
而这些函数内部**逐字** `st.highlight = Some(Highlight { .. })`。

⇒ 于是 finalize 拍采样时 `st.highlight` **可能仍是 `Some`**，`frozen` 记为**新高亮的参与者**。
**这不是问题**：`frozen` 的统一定义就是「**本拍结束时仍活跃的高亮参与者**」，
flight 中间拍与链式 finalize 拍自动一致（初稿那句「finalize 拍 `frozen` 自然为空」
**是错的**，且与本文件排空拍段的自述打架——那里正以「finalize 能链式产新高亮」为前提）。

#### 终场排空拍**不**记快照（边界，须显式写）

`while t < dur` 退出后还有一段 `while st.highlight.is_some() { finalize_highlight(...) }`
的**排空循环**，它在**同一 `t = dur`** 上反复产 beat，随后被尾哨压缩
（`events.drain(drain_start..)` 按时间戳**去重**，只保留每个时间戳第一拍）。
那段**不属于比赛时间**：比赛已结束、哨声在即，且它的 beat 本来就被丢弃。

⇒ **快照只覆盖主 tick 循环 `t ∈ [1, dur)`（5399 拍）**，排空拍不记。
「快照数 == tick 数」这条守卫的 `tick 数` 特指主循环的 5399，**不含**排空拍。
（否则会在 `t = dur` 上叠出一堆同时间戳的快照，与 beat 去重口径打架。）

#### ⚠️ `frozen` 的来源（审阅 P0-2 更正）

初稿说「`frozen` 必须一起记」，但**没说它从哪来**——而且在初稿选的采样点上它**恒为空**：
`emit_beat_with_main` → `beat_movers_main` → `commit_beat_positions_ex(st, movers, &[], ...)`
（第三个实参就是 `frozen`，**字面是 `&[]`**）。真正非空的 `frozen` 只出现在裸 `beat_event`
的高亮飞行拍（`beat_movers(st, rng, t, &participants, &participants)`）。

**唯一可靠来源 = `st.highlight` 的 `participants`**（`Highlight` 结构体字段）。
⚠️ 注意类型：`participants: Vec<(i32, (f64,f64))>`，而快照的 `frozen: Vec<i32>`——
须**取 id 列**（`participants.iter().map(|(id, _)| *id).collect()`），
**不是**「直接把它作为」。（`tick` 里传给 `beat_movers` 的 `excluded` 正是这个映射，可复用其形态。）
采样点取 `tick` 返回之后时，`frozen` = **该拍结束时仍活跃的高亮参与者**——
finalize 拍若链式建了新高亮（`start_goal_kick` 等），记的就是新高亮的参与者（见上）。

#### 飞行期冻结者的位置是**钉住的**（主证据：结构保证），所以 `frozen` 不承担「防陈旧」

**主证据（源码逐字）**：`commit_beat_positions_ex` 里
`if st.sent_off[id] || frozen_mask[id] { continue; }` 跳过冻结者的 `st.pos` 写回；
且飞行拍的路径只调 `beat_movers(st, rng, t, &excluded, &excluded)` 后**直接 `return`**——
**飞行期没有任何路径写参与者的 `st.pos`**。故该位置**就是引擎的权威钉住值**，
不是「落后于更近真值的陈旧量」（初稿用「陈旧」一词不准确）。

**复现佐证（插桩，seed 1，5399 tick）**——仅作次要旁证，样本量按本文件别处的标准偏小：

| 量 | 值 |
|---|---|
| 有高亮的 tick | 713 / 5399 |
| 有高亮时平均参与者数 | ≈1.76（总参与者 1258） |
| 飞行中参与者位置**变了**的次数 | **0** |
| 飞行中参与者位置**没变**的次数 | 269（= 相邻同参与者 tick 对数） |

⇒ `frozen` 的用途是**标记「进行中的量」**（让下游能过滤/单列），**不是**防陈旧。

**那还要不要记？要，但理由是另一个**：下游要能**区分**「这个位置是引擎本拍提交的终态」
与「这个位置是飞行中的中途值（马上会被 finalize 改写）」。后者用于「瞬时队形」时
是个**进行中的量**，不是稳定观测。`frozen` 让下游能过滤或单独报告这批拍。
**成本 ≈ 0**（全 5399 拍摊薄后平均 0.233 人/拍 = 1258/5399；只在那 713 个有高亮的拍上
则为 ≈1.76 人/拍）。若审阅认为这不值得，删掉它也不影响 G1 的核心保证。

### 2.5 与「phase_segments」的关系

不变。`PhaseSegment` 仍**恒为空数组**（#113 定论：15B 的标注器由**纯函数**在
`DiagnosticMatch` 之后填，判据 = `annotate_phases(&手搭 fixture)`）。本 change **不实现 15B**。

### 2.6 内存与落盘

- 内存：**5399 tick/场**（§2.4 更正：拍 = tick，**不是** beat 数 5365）× 22 人 × 2 f64
  × 8 字节 ≈ **1.90 MB/场**；加每拍 `t: ObservedTime`（16 B）与 `frozen: Vec<i32>`（24 B）
  ≈ **2.11 MB/场**。P17A 已是「逐场跑、跨场聚合」的形态，峰值 = 单场，可接受。
- ⚠️ **编码必须保持 `[(f64,f64); 22]`，不得改 `f32` 或量化**（审阅 P1-5）：
  G1 的正当性全部押在「逐位恒等 `st.pos`」上；`f32`/量化都是**有损**，会把快照降级成
  `st.pos` 的又一个近似——与 G0（beat 重放）在**性质**上无法区分，只是误差更小。
  省内存只能靠「少采样 / 不采样」，不能靠有损编码。
- **落盘策略：位置快照不落盘。** P16 产物只落**摘要**（覆盖率 + 特征统计 + provenance）。
  理由：300 场全落 ≈ 2.11 MB × 300 ≈ **633 MB**，且 P17A 的产物纪律是
  「可复现的聚合」而非原始数据。
  回放定位靠 `(seed, episode_id, t)` 重跑即可——确定性由既有门保证。

## 3. 「渲染也直接用位置」的判断

**判断：技术方向成立，但它是架构级决定，超出本 change 边界，不宜作为 P16 的产物。**

### 3.1 为什么方向成立

本方案导出的是 `st.pos`——而 `st.pos` **就是**引擎自己的渲染位置：highlight 提交点
（传球落点、拦截者就位、门将扑救位）**直接写 `st.pos`**，viewer 现在也正是靠那些
事件字段去还原。所以「引擎导出位置」与「画面显示的位置」**本来就是同一个量**，
不存在两套真值。这一条支持用户的直觉。

### 3.2 为什么不能由 P16 定

1. **撞 spec 的规范条款，不只是实现**。`openspec/specs/event-stream-protocol/spec.md`
   逐字规定 `movers` 是「**增量——只含移动球员**」，且场景明写
   「**静止球员不在其中**」；还有「`beat` **SHALL NOT** 同时携带 `main` 与 `ball`」。
   「渲染直接用位置」= 把增量换成全量快照 = **改协议**（MODIFIED requirement + 场景重写）。
2. **撞两层架构**。`CLAUDE.md`： 「引擎产事件流，画面消费事件流，**事件流是唯一接缝**」。
   让画面吃位置，等于让位置**经事件流**流过去——那就是 G4，实测 **+69% ~ +672%** 体量。
3. **会损失动画**。viewer 现在走 `game.js` 的**锚点时间线 + 插值**：拍间补帧是为了
   在 1 Hz 数据上得到连续运动。「直接用位置」若不插值 ⇒ 1 Hz 步进（观感退化）；
   若插值 ⇒ 仍需计算。**「不用计算」这个收益不成立**——省掉的是**反推**，不是插值。
4. **收益与代价不对称**。「渲染直接用位置」的收益 = 渲染路径相对引擎真值的偏差，
   实测 **最大 0.0386（归一化）、点级 7.47% 超 1 cm、70.5% 的整秒帧含超 1 cm 的点**
   （对照见 §1 ①）。**这是真实存在的偏差**，且集中在高亮参与者（冻结球员的位置由
   highlight 提交点事后对账，插值层看不到）。代价是全节点 **×1.7–7.7** 的体量与
   一次协议变更（§3.2 ①②③）。**不建议**在本 change 里做，但这条收益是真的，不是零。

### 3.3 建议

- **本 change**：走 G1（sidecar，事件流零增量），把位置**先给分析层**。
- **已另立探索 issue（用户 2026-09-29 拍板「先不做」）**：**GH #122**
  （`【探索】渲染直接消费引擎位置（替代 movers 增量 + 插值）`，`wayfinder:research`）。
  §2.1 的 G4 行与 §3.2 的四条已作为该 issue 的起点材料。
  **#122 是「待定 / 未排期」，不是 P16 的前置**——P16 不得为它预留结构或改 `viewer/`。
- ⚠️ **不要**在本 change 里顺手改 `viewer/` 或协议——那是**方向决策**，按本 change 的
  红线须用户拍板。
