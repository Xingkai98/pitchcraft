## Q1. JS→Rust 的层差怎么处理？（design §5.1）

### 背景（本次实测，2026-09-29）

`viewer/match-metrics.js` 的 `teamShape` 是 **JS**，15B 的 `PhaseAnnotator` 在 **Rust**。
两条路都实测过了：

| 路径 | 做法 | 实测工 / 保真度 |
|---|---|---|
| **A. 引擎导出快照** | 引擎在 beat 事件里已含**每一名移动球员的 `from/to`**（`Event.movers`）+ 持球者的 `beat.main`。Rust 侧从 `lineup` + 逐拍 `movers/main` 重放，可得**每个 tick 的 22 人位置** | ✅ 实测：5 seed，**0 帧缺人**（26822 拍全 22 人齐）；tick 间隔恒 1.0s（偶有 2.0s） |
| **B. 移植 `teamShape` 进 Rust** | 把 q10–q90 / 重心 / spread 的 JS 实现照搬 | ✅ 纯函数、口径已在 `match-metrics.js` 头部冻结，移植风险低 |

### ⚠️ 关键实测：**A 与 JS 的 `sampleEngineFrames` 逐点同值**

在整秒（tick 边界）上比对 597 帧 × 22 人 = **13134 个点，`max |Δ| = 0.000000`**。
聚合到标尺口径（逐场切 300s 窗 → 均值 → 跨场均值，5 seed）后差**全部 < 0.1%**：

```text
depth : js=40.222  beat重建=40.189  Δ=-0.1%
width : js=40.752  beat重建=40.754  Δ= 0.0%
cx    : js=52.789  beat重建=52.794  Δ= 0.0%
cy    : js=34.008  beat重建=34.008  Δ=-0.0%
spread: js=18.564  beat重建=18.559  Δ=-0.0%
```

⚠️ **但两者不是同一个东西**：JS 侧经 viewer 的**演绎层**（`interpretation.js` + `game.js` 插值），
在**拍内非整秒**处会偏离引擎提交态（实测单点最大偏 0.87 m，因高亮参与者被排除出 movers）。
**整秒处完全相等**是因为拍边界上演绎层的锚点就是引擎提交的位置。

### 选项

- **A（推荐）：Rust 侧从事件流的 `lineup` + `movers/main` 重放**。零引擎改动、零 JS 依赖，
  15B 的 `PhaseAnnotator` 直接吃；口径与标尺在**整秒采样点**上逐点相同（已实测）。
  代价：须把「重放」写成纯函数并单测（**本 change 已可交付，见下文风险**）。
- **B：把 `teamShape` 移植进 Rust**（复制 q10–q90 口径），再走 A 的重放帧。
  两条**不互斥**——A 解决「帧从哪来」，B 解决「指标在哪算」。**推荐 A+B 同时做**：
  重放帧 + Rust 侧指标，与 JS 标尺在整秒点上互为哨兵。
- **C：引擎导出新快照接口**（如 `state_at(t) -> 22 pos`）。需要**改 `engine/src/`**，
  撞本 change「不改生成逻辑」边界（虽然只加只读接口），工最大。

### 需要用户确认的是

**15B 的 `PhaseAnnotator` 入参用哪条**——尤其：若选 A/B，则 `PhaseAnnotator` 的
`spatial_features` 入参由本 change 的 Rust 模块填充（**本 change 的实际交付**）；
若选 C，则本 change 只给定义、不落地成 Rust 类型。

**实现 agent 的倾向（供参考，不代拍）**：A+B。理由：零引擎改动、与既有标尺在整秒点同源、
可写成纯函数单测（符合本仓「动画逻辑写成纯函数」的分层）。

## Q2. 终点位置的权威字段（design §5.2）—— **实现 agent 已按证据选定，请复核**

design 说「终点取同源的收束侧字段，具体取哪个**在实现时定**」。已用 100 seed / 10102 episodes 定死：

**规则**（唯一实现 `closing_fact`，见 `engine/tests/p16/caliber.rs`）：

1. **收束侧事实**：`t == end_t` 且带 `location` 的**最早**一条；
2. **回退**：`end_t` 上没有带位置事实（死球 / 哨声：`dead_ball_started`、`match_ended`
   **不带 `location`**）时，取窗内（`start_t ≤ t < end_t`、下标 > 起点事实）最后一条带位置事实。

**为什么是「最早」不是「最后」**（这是本条唯一的真决策，实测支撑）：

| 取法 | 选中「他队 `control_established`」（= 下一个 episode 的开启事实） |
|---|---|
| `t == end_t` 的**最后**一条（朴素写法） | **2578 / 10102 = 25.5%** ❌ |
| `t == end_t` 的**最早**一条（本实现） | **172 / 10102 = 1.7%** ✅ |

那 1.7% 是**跨队易主的同刻交接**——`control_established` 在同一 `t` 里既收束本条 episode
又开启下一条（`observation.rs` 的 `control_established`：先 `close_episode` 再 `open_new_episode`），
**本就是收束侧**，取它是对的。

⚠️ **两种取法的位置值实测完全一致**（10102 条里 **0** 条分歧）——差异只在**审计栏**
`end_fact_kind`。故这条不是「为了数字好看」，是「让报告里『终点取哪类事实』说得准」。

**覆盖率**（100 seed，10102 episodes）：

| 量 | 值 |
|---|---|
| 终点位置可得（**同源收束侧**） | **8768 / 10102 = 86.8%** |
| ├ `contest_started` | 2222 |
| └ `control_established` | 6570 |
| 不可得（`None`，不猜） | 1334（13.2%），按 `end_reason`：`foul` 622 / `out` 619 / `goal` 40 / `full_time` 29 / 开放 24 |

**需要用户确认**：这条口径是否认可（**若不认可，改的是本模块唯一的终点定义**）。

## Q3. 判别参考集怎么构造（design §5.3）—— **本 change 的核心难点，需要方向性输入**

契约：**不得只用区域构造**（否则退化成循环论证）。
`build_up ≠ 后场`、`progression ≠ 球向前移动`、`final_third ≠ 前 1/3`。

### 已排除的做法（写下来是为了不再考虑）

- ❌ 用「起点/终点落在哪个三分带」当标签——那正是契约禁的「区域 = 阶段」。
- ❌ 用几何量（净推进 > θ）自造标签再自证——循环。

### 候选构造（都需用户选择/补充）

1. **P17A 的动作链 motif 当标签**（**推荐**，不依赖区域）：
   - `build_up` ≈ 后场起的 `pickup → pass+ → pass+` 链条（多次成功传递、**有回传/横传**）；
   - `progression` ≈ 跨过中场线的连续推进链条；
   - `final_third` ≈ 射门前链条（`→ shot` 结尾）。
   证据源：P17A 已有 `EpisodeRecord.actions` / `tokens()` / `first_shot_index`。
   ⚠️ 风险：motif 定义本身也可能悄悄用位置（如「传球落点 x 增大」）——须逐条审。
2. **引擎显式信号当标签**：`shot_setup` / 起脚窗口 / `transition` 窗口——但**这些大多不在观测层**
   （sidecar 不带），且 `attacking_transition` 已按 #113 判为 team-state。**可能不可用**。
3. **人工标注一小批 episode**（10–30 场×若干 episode）当**金标**，再看特征能否复现。
   最贵但最不循环；若用户接受，本 change 的裁决会**可信得多**。
4. **半监督**：用 1 的 motif 生成候选，用户抽检若干条确认/否认。

### 需要用户确认的是

**用哪种构造**（1 / 2 / 3 / 4）。若选 3，需用户给**标注预算**（多少条、谁标）。
**实现 agent 的倾向**：1 为主 + 3 抽检（若预算允许）。但**这是方向性决策，不代拍**。
