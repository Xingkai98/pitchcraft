# Design: 比赛标尺

## 上下文

P35 之后，真实比赛与引擎比赛都能在 viewer 里播放。但要把它变成**调参判据**，
需要三件事：两边用**同一份**指标实现、口径**固定**且记录在案、对比基准来自**实测分布**
而非拍脑袋的常数。本 change 做这三件事。

设计前做过一次指标体检，并经**两轮独立审阅**修正口径。最终口径与采样：
- **口径**：队形纵深用「掐头去尾各 1 人、取剩余 8 人的跨度」（`trim1`）；
- **采样**：真实 2 场 × 7/6 窗 = **13 个满窗**（game1 7 + game2 6；game2 尾部 246s 残窗丢弃）（步长 900s、窗宽 300s；game2 末窗仅 246s 需记录）；
  引擎 5 种子 × **5400s 默认时长**、按同规则切 = **30 窗口**（相位同构）。

**口径的演化过程本身是教训**（详见 D3）：`max-min` → `p10–p90` → `trim1`，每一步都是
被实测/审阅推翻的。四个候选估计量在同一注入实验下的表现：

| 估计量 | 最前球员→x=+1.4 | 最后球员→x=−1.4 |
|---|---|---|
| `max-min` | +83.1m | +185.4m |
| `p10–p90`（线性插值） | +8.3m | +18.5m |
| `p10–p90`（floor 索引） | +0.0m | **+185.4m** |
| **`trim1`（采用）** | **+0.0m** | **+0.0m** |

`p10–p90 floor` 看似抗噪，实则在**防守侧**与 `max-min` 完全一样——只测单侧会得到错误的
"抗噪 60 倍"结论（这正是第一轮修订犯的错，第二轮审阅纠正）

## Goals / Non-Goals

**Goals**
- 真实侧与引擎侧**共用**一份指标实现（口径分叉 = 数字不可比）。
- 指标口径显式写进 spec（剔除门将、瞬时队形、米制、控球代理、采样间隔）。
- 对比以**真实多场分布区间**为准，而不是"等于某个值"。
- 指标函数与对比逻辑进 CI；不需要看画面。
- 把实测基线（真实分布）落盘，作为后续引擎校准的目标。

**Non-Goals**
- **不改引擎**。本 change 是测量工具；引擎的队形偏差是后续 change 的修复对象。
- 不做可视化（曲线图/热图）。数字与文本报告足够，且不依赖视觉。
- 不做事件层指标（传球成功率、射门转化等）——那需要**从 tracking 反推事件**，
  是另一个研究领域（P35 design 已论证不做）。本 change 只做**位置层**指标。
- 不追求"引擎复刻真实比赛"。目标是**落在真实分布区间内**，不是相等。

## 决策

### D1: 统一帧表示是两侧的唯一接口

**选择**：指标函数只接受一种输入形状：

```jsonc
{ t: 0.2, players: [{ id, x, y } | null × 22], ball: [x, y] | null }
```

- tracking 侧：帧序列已是 `players: [[x,y]|null]`，转成对象数组（`fromTrackingFrame`）。
- 引擎侧：用 `Game.seekTo(t)` + `game.players` / `game.ball` 按固定间隔采样。

**理由**：口径分叉是这类对比最隐蔽的失败模式——两边各写一份"看起来一样"的实现，
数字却因细节（是否含门将、采样相位）而不可比。一份实现、一种输入，从结构上排除。

**代价**：引擎侧需要采样（不能直接读内部状态），确认了"标尺只消费两侧都能提供的观测"。

### D2: 五个口径，缺一不可

这些不是风格选择——每一项都会显著改变数字，必须写进 spec：

| 口径 | 取值 | 不这么做会怎样 |
|---|---|---|
| **剔除门将** | 排除 id 0 / 21 | 纵深变成"门将到前锋"，虚高十几米（实测 33→64m） |
| **瞬时队形** | 单帧瞬时跨度（非整场分位） | 与"整场 x 分位"差一倍，是两个不同的量 |
| **纵深的估计量** | `trim1`：掐头去尾各 1 人、取剩余 8 人跨度 | `max-min` 只由最前/最后两人决定，单个离群球员即可撑大 180m |
| **米制换算** | `x×105`, `y×68` | 归一化数字无法与足球常识对照 |
| **控球代理** | 离球最近者所属队 | 不定义就无法按相位分桶；两侧算法必须一致 |
| **采样间隔** | 0.2s（5Hz） | 与 tracking 的 `keyframeHz` 对齐；相位不同会引入抽样偏差 |
| **球相关指标的取帧** | 主口径用**原始球帧**（`ballFill` 缺省）；报告全帧对照 | 真实侧 40% 帧的球位是补全推断（见下） |

**球相关指标的取帧策略（审阅 P2-6）**：真实侧约 40% 帧的球位是 `nearest` 启发式补全的，
实测补全帧的"球到最近球员距离"恒为 0.000m（补全是把球放到该球员脚下），且补全链最长连续 132s。
这意味着任何**以球为条件**的量（控球代理、弹性分桶、重心到球距离）在补全帧上测的是**补全启发式
而非数据**。主口径因此只用原始观测球帧；全帧结果作为报告项并列，两者的差异本身就是口径敏感性披露。

**控球代理的已知局限**：这只是"谁离球最近"，不等于真实持球权（不处理传球在途、
二点球）。作为**相位分桶**用途足够，但必须显式标注为代理，不得当作引擎事实。
（对齐项目既有做法：`derive-audit-features.js` 对不可观测的事实标 `unknown` 而不猜。）

### D3: 指标取舍由实测体检决定

体检结果（**最终口径 `trim1` × 最终采样**：真实 13 窗 / 引擎 30 窗；值 = 均值，括号 = 范围）：

| 候选指标 | 真实 | 引擎 | 分离？ | 结论 |
|---|---|---|---|---|
| **主队纵深（trim1）** | 25.2m (16.2–29.6) | 39.6m (32.1–47.6) | ✅ 不重叠（余量 2.6m） | **采用** |
| **紧凑度（到重心）** | 15.2m (10.7–17.2) | 20.0m (17.9–23.2) | ✅ 不重叠 | **采用** |
| **两队重心间距** | 8.3m (6.8–10.5) | 15.1m (11.7–18.0) | ✅ 不重叠 | **采用** |
| 客队纵深（trim1） | 26.2m (20.2–29.6) | 38.9m (29.2–46.1) | ⚠️ **边缘接触** | 报告项 + 人工复核 |
| 宽度（非门将） | 39.6m (28.2–46.8) | 32.5m (30.3–34.4) | ❌ 重叠 | 仅报告 |
| 重心到球距离（原始球帧） | 18.4m | 20.3m | ❌ 重叠 | 仅报告 |

**实现期数字重生成（2026-09-18）**：本表已整体更新为**实现期基线**
（`viewer/data/benchmark-baseline.json`，13 满窗）的数字——它是标尺此后引用的唯一数字源
（R2-P2-1：文档数字必须从同一份基线 JSON 引用）。重生成暴露了设计期探针的一个 bug：
「紧凑度」把**排序后的 x 与未排序的 y 按下标配对**（应为同一球员的 (x,y) 配对），
修正后真实 15.30→15.24、引擎 19.83→19.98（差 ≤0.2m，分离结论不变）；「宽度」「重心到球
距离」行此前是 14 窗探针值，一并更新到 13 窗（重心到球按主口径 = 只用原始球帧）。

**客队纵深是边缘案例，如实记录**：真实最高 29.6 vs 引擎最低 29.2，**重叠仅 0.4m**。
即引擎在极少数窗口（30 个里的 1 个，seed 99）能短暂进入真实范围。这不改变"引擎偏散"的整体
结论（均值差 49%），但意味着**它不能承受一个紧阈值**。故列为报告项 + 人工复核，不进自动门。

**为什么用 `trim1` 而不是 `p10–p90`（两轮审阅的结论）**：`p10–p90` 有**约定歧义**——
"p10–p90"四个字不定义一个数，线性插值与 floor 索引在同一数据上差 2.4m；
且 floor 索引在 n=10 时不对称（最大值 0% 权重、最小值 100%），**防守侧注入的响应
与 `max-min` 完全相同**（+185.4m）。`trim1` 两侧对称（各 0%）、无需分位约定、一句话可写清。

**未采用的候选维度**：另测过"球员间距离分布""按三区划分"等，实测不与真实分离或
与已有三项高度共线，不纳入（避免标尺臃肿）。

**关键判断**：**宽度不能当门**——真实的宽度波动极大（28–47m，取决于攻防相位与场面），
与引擎（30–34m）区间重叠。硬套会让门变得随机。它仍作为报告项输出（人看趋势），
但不进断言。

**这体现一个原则**：**指标能不能当门，由实测分布是否分离决定，不由"它听起来重要"决定。**

### D4: 弹性指标降级为「口径敏感性报告」，不作校准目标

**原假设**：真实比赛的队形纵深几乎不随球移动（Δ=4.4m），引擎会明显拉长（Δ=11.3m），
"引擎弹性是真实的 2.6 倍"——看起来是个很有价值的发现。

**审阅推翻了它（P1-2），我复核确认**：这个 2.6× 是**分桶口径的产物**。换一个同样合理的
分桶方式（"球相对本队重心前后"而非"球在哪个半场"）：

| 分桶口径 | 真实 Δ | 引擎 Δ | 倍数 |
|---|---|---|---|
| 球在哪个半场 | +4.5m | +11.3m | 2.5× |
| 球相对本队重心前后 | **−0.1m** | +2.0m | 信号消失 |

真实侧的 Δ 从 +4.5m 变成 −0.1m——**"真实队形不随球拉长"这个前提本身不成立**，
它只是"按半场分桶"这一特定口径下的现象。第二重污染：真实侧 40% 帧的球位是补全推断
（见 D2），只用原始球帧算，弹性还会再变 36%。

**选择**：弹性**不进断言、不作校准目标**，仅作为**口径敏感性报告**输出（同时给出两种
分桶的结果，让读者看到它对口径的依赖）。这本身是有价值的——它诚实地说明"这个量不稳"。

**这条修正的教训**（值得记进项目笔记）：一个指标"看起来有信号"不等于"这个信号物理上成立"。
换一个同样合理的口径就消失的信号，不能作为校准目标——否则会让后续 change 去优化一个幻觉。

### D5: 对比方式——「观测范围报警」而非「p5–p95 验收门」

**原设计**：断言「引擎值 ∈ 真实分布的 p5–p95」。**审阅证伪（P1-3），我复核确认**：

用 game1 导出的区间去检查 **game2**（同一数据集、同一采集管线的另一场真实比赛）：

| 指标（trim1 口径） | game1 的观测范围 | game2 窗口落在范围内 |
|---|---|---|
| 纵深 | [24.2, 27.2] | **3/6** |
| 紧凑度 | [14.0, 17.2] | 5/6 |
| 重心间距 | [6.8, 10.5] | 6/6 |

（审阅在 5 种口径下都复现了同类结果，纵深 2–3/7 落入——**结论与估计量约定无关**。）

**用它验收，会把一半的真实比赛判为"不像真实足球"。** 2 场数据导出的 p5–p95 区间，
其自身的不确定性（bootstrap p5 的 90% CI 宽 9.4m）比区间本身（9.5m）还大——
**这样的区间不能作为验收判据**。

**修正后的定位**：
- 真实侧分布作为**观测范围**（`[min, max]` + 分位数），用于**报警**而非验收：
  引擎值落在观测范围外 → 提示"偏离真实比赛观测到的范围"。
- 区间**必须标注样本量与不确定性**（当前 2 场 / 13 个满窗），不得表述为"真实足球的分布"。
- 「引擎落在区间内」**不是**本 change 的验收目标；本 change 的目标是**量出差距**。
  真正的验收门要等样本扩大（SkillCorner）后再立，或用不对称判据（中位数 + 极值约束）。

**为什么当前仍可用**：最终口径下引擎 30 窗口的主队纵深 32.1–47.6，
真实 13 窗口 16.2–29.6——**余量 2.6m，完全不重叠**；均值差 57%。
差距远大于样本不确定性——**"引擎队形偏散"这个结论是稳的**，只是"用区间当验收门"不成立。

### D5b: 门的形态必须显式定义（审阅 P1-4）

原设计只说"落在区间内则通过"，没说清落地形态。按字面实施会导致 **CI 首日即红**
（引擎当前必然越界），且在校准 change 落地前无法变绿——这会破坏项目「verify 全绿才收尾」
的既有流程。**必须在实施前拍板**：

**用户拍板（2026-09-18）：默认 = 报告期**（只输出数字与对比，不产生 pass/fail）。
理由：校准目标尚未确定——用户明确表示"需要多跑一些比赛看看大范围的数据"，
在样本扩大、目标定下来之前，标尺的职责是**量出差距**，不是判定合格。

| 形态 | 含义 | 状态 |
|---|---|---|
| **报告期（当前默认）** | 输出指标、对比、偏离方向与幅度；不产生 pass/fail | **采用** |
| ratchet | 断言"不超冻结基线+ε"（防恶化） | 待样本扩大后评估 |
| xfail | 显式标记预期失败 | 不用 |

**报告期的取舍（诚实记录）**：proposal 原写「让回归被自动挡住」——报告期**做不到**这一点，
回归不会被自动拦截，只能靠人看报告发现漂移。这是用户在有意识权衡后的选择：
在目标和样本都不确定时，先建立**可复现的观测能力**，而不是先立一个会误导的门。
一旦样本扩大 + 校准目标确定，再升级为 ratchet 或区间门。

**"多跑比赛看大范围数据"的直接含义**：当前 13 个真实窗口导出的范围**连另一场真实比赛
都容不下**（game1 范围只容纳 game2 的 3/6）——这正是样本不足的表现，
也正是用户想要的"大范围数据"要解决的问题。**扩大样本因此成为校准的前置条件**，
而不是可选项（见"后续"节）。

另需写死：**聚合规则**（断言种子均值还是每个种子——引擎种子间纵深 ±10%，会影响结果）
与**种子集**（冻结，禁止按结果重挑，对齐项目 L1 主场优势门的教训）。

**引擎取样方案改用 90 分钟**（审阅 P1-4c）：原设计写"引擎默认 5 分钟/场"是**事实错误**
（引擎默认 `match_duration_seconds=5400`，5 分钟是 viewer 的 config 传参）。且真实取的是
中段 5 分钟切片、引擎跑的是完整 300s 比赛（含开场瞬态），相位不同构。改为：**引擎跑 5400s，
按与真实相同的规则切 5 分钟窗口**——相位同构，样本量从 5 升到 30（5 种子 × 6 窗口），
彻底消掉这组可比性问题（实测 90 分钟跑一场仅 ~4s）。

### D6: 分层——对齐既有 `realism.rs` 的组织

引擎侧已有 L1（规格门）/ L2（不变量）/ L3（报告带）的分层经验。本 change 沿用同样的思路：

| 层 | 内容 | 运行时机 |
|---|---|---|
| **单测** | 指标函数的纯函数测试（已知输入 → 已知输出、边界、口径正确性） | 默认（有断言） |
| **报告** | 三项采用指标 + 报告项 + 口径敏感性对照 + 偏离真实范围的方向与幅度 | 默认跑（**不判定**，见 D5b） |
| **ratchet 门** | 引擎指标不超冻结基线 + ε（防恶化） | **待样本扩大后评估** |

**唯一有断言的是指标单测**——它保证"量出来的数是对的"，不保证"引擎像真实"。
这是报告期的实质：**测量可靠 + 不判定符合性**。

**口径正确性的测试是本 change 的重点**：例如「剔除门将」这条，必须有一个测试构造
"门将在极端位置"的输入，断言它**不影响**纵深结果。否则口径会在某次重构里悄悄失效，
而数字只是缓慢漂移，没人会发现。

## 风险与权衡

- **真实样本量（最关键的已知限制）**：Metrica 仅 **2 场 / 13 个满窗**，且是匿名样本
  （联赛、球队风格、比分状态均未知）。**这些数据不能代表"足球的分布"**，只能代表
  "这两场比赛观测到的范围"。基线文件 SHALL 显式声明未覆盖的维度（联赛/球队风格/
  比分状态/换人前后/天气场地），防止后续 change 把它当基准引用。
  区间的不确定性（bootstrap CI 宽度 ≈ 区间本身）已在 D5 说明——**这是"只能报警不能验收"的根因**。
- **控球代理的粗糙**：见 D2。它只用于分桶与报告，不参与断言；补全帧上的循环论证
  （球被放到某球员脚下 → "离球最近者"必然是他）已通过"只用原始球帧"规避。
- **不追求引擎"像"真实**：本 change 明确不把"缩小差距"当作目标——目标是**量出差距**。
  缩小差距是后续 change 的事，且应有自己的立项与验收。
- **基线陈旧性**（审阅 P2-7）：两侧共用同一函数是优点，但函数修正后基线不会自动作废，
  门会拿旧分布判新值、静默失真。基线文件 SHALL 记录指标模块的版本/哈希，加载时校验，
  不匹配即提示重生成（对齐项目 P28「行为等价重构绑定执行层」的教训）。
- **基线重生成链路**（审阅 P2-9）：基线依赖真实数据（不入库），文档 SHALL 写清完整链路
  （`fetch-tracking-data.mjs` → `convert-tracking-to-frames.mjs` → 基线生成命令），
  否则"可复现"只是口号。基线入库位置：`viewer/data/benchmark-baseline.json`。

## 扩大样本的可行性（已实测，2026-09-18）

用户要"多跑一些比赛看看大范围的数据"——这是校准的前置条件，故本设计**实测验证了可行性**：

| 项 | 结果 |
|---|---|
| 数据源 | SkillCorner/opendata（GitHub 公开） |
| **许可** | **MIT**（比 Metrica 的"未声明许可"干净得多，可公开发布对比） |
| 场次 | **20 场**（README 写 10 场，实际 `data/matches/` 有 20 个目录）——是 Metrica 的 10 倍 |
| 内容 | 2024/25 澳超，每场含 tracking（广播追踪）+ dynamic events + match.json + phases |
| **tracking 取用** | **Git LFS 指针**（仓库内仅 133 字节）；实体需从 `media.githubusercontent.com` 取。
  实测：**分支名是 `master` 不是 `main`**（用 main 会 404）——`.../master/data/matches/<id>/<id>_tracking_extrapolated.jsonl` 可取得 90.7MB 实体 |
| 单场帧数 | 60301 帧（帧 0 起，前若干帧为开赛前空帧） |

**接入需额外处理四件事**（调研原型 `research/.../notes/prototype-skillcorner-adapter.mjs` 已验证思路）：
坐标系是"米 + 球场中心原点"需归一；朝向在 `match.json` 的 `home_team_side`；
身份映射走 `match.json.players[]` 的 `team_id` + `player_role`（**注意：tracking 的 `player_id`
对应 `players[].id` 而非 `trackable_object`，用错字段匹配率为 0%**）；
以及 **`is_detected=false` 是外推值不是缺失**（实测球员点仅 ~58% 是真检测）——
外推点坐标看起来正常但不可信，需标注或弱化，**Métrica 没有这个标记**。

**结论**：扩大样本**技术上可行、许可更干净、样本量 ×10**，
但接入是独立工作量（新格式 + LFS + 外推点语义），应作为**独立 change**，不是本 change 的顺带事。

## 审阅记录

本设计经过**两轮**独立审阅（subagent），报告在 `reviews/design-review.md` 与
`reviews/design-review-round2.md`。

**第一轮**（结论：需修）——四条 P1 全部采纳：

| 发现 | 修改 |
|---|---|
| P1-1 纵深 `max-min` 抗噪差 | 换修剪统计（**但第一轮的选择本身在第二轮被纠正**，见下） |
| P1-2 弹性的 2.6× 是分桶口径产物 | 弹性降级为口径敏感性报告，不作校准目标 |
| P1-3 2 场数据的 p5–p95 不能当验收门 | 降级为"观测范围报警"，标注样本量不确定性 |
| P1-4 门的形态未定义（CI 首日即红等） | 新增 D5b：形态定义 + 聚合规则 + 种子集 + 引擎改跑 5400s |

**第二轮**（结论：小修后可用）——抓到第一轮修订自身的两个缺陷：

| 发现 | 修改 |
|---|---|
| R2-P1-1 `p10–p90` 有约定歧义，且 floor 索引**不对称**（防守侧响应与 `max-min` 相同，+185.4m）——第一轮的"抗噪 60 倍"只测了免疫的一侧 | 改用 **`trim1`**（两侧对称 0%/0%、无约定歧义） |
| R2-P1-2 默认"报告期"与 proposal 的「自动挡住」、D6 表的「分布门默认跑」**三处矛盾** | 默认改为 **ratchet**（首日即绿 + 真能挡回归） |

**第二轮同时验证为安全**的关键项：5400s 采样方案（无中场死时间、**不换边**、6 窗/种子、
`[0,300]` 窗与独立 300s 跑一致、~4s/种子）；留一交叉验证的结论在 5 种口径下都成立。
