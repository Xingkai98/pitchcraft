# Design: 连续比赛播放（continuous-playback）

## Context

Phase B（原 p2 的 B 阶段）已归档：引擎 tackle 语义补全（就近防守、可失败、loose/carrier_from 字段、两端状态一致）。事件流坐标语义自洽，"带球中被抢"在 clip 模式可看。但 viewer 仍是**解耦点播**：Game 状态机是单事件片段、`app.js` 跑 `demo_mode: true`。

用户澄清（grill Q2）：**"连续"的本质 = 引擎不断产生事件，画面逐个模拟，引擎产生得比画面快**。当前引擎 12-20s 一个事件（~150 事件/场），密度太低 → 画面空等。本 change 让引擎产**高密度事件流**（含无球跑位事件，每 1-2s 一个）+ viewer **整场连续播放**（kickoff → whistle 自动衔接，不 snap）。

## Goals / Non-Goals

**Goals:**
- 引擎产高密度事件流：新增 `off_ball_run`（无球跑位）事件，事件间隔压到 1-2s；有球事件节奏不变，中间穿插无球跑位。
- Game 连续播放模式：跨事件推进、播完自动切下一个；事件间空档由无球跑位填满（不再静止 hold）。
- app 接引擎连续流（`demo_mode: false`），控件适配整场播放/重播 + **进度条/时间轴**。
- 端到端可验证（无视觉依赖）：连续边界断言（无 snap）。

**Non-Goals:**
- 不做无球跑位/位置维持事件（`off_ball_run`）——后续单独 change。
- 不做带标签 RNG 流完整化/定点数——票据 06。
- 不做完整 90 分钟比赛规则——之后。
- 不做 Tauri 桌面壳——票据 07 已定，接入桌面独立工作。

## Decisions

### D1: 引擎事件驱动时间推进（含 off_ball_run，Q2/Q11b 确认）
- 引擎时间循环改造：**不再 `t += 12-20s 随机`**，而是 `t += 当前动作的实际时长`（距离 ÷ 速度），动作间可加小的"决策停顿"（如 0.3-1s，球员思考/调整的节奏）。
- 事件流 = 动作一个接一个：传球飞完 → 下一个动作；带球推进完 → 下一个；无球跑位完 → 下一个。**无固定间隔概念**。
- 新增 `off_ball_run`（无球跑位）事件：短距离碎步移动（每事件 1-2m），球员从当前 pos 向战术位置/球附近移动一小段。事件带 `subject`（跑位者）+ `x/y`（起点）+ `x2/y2`（终点）+ `speed`（跑速）。有球事件与无球事件按各自动作时长自然衔接。
- 一次性 `simulate()` 产出整场事件流（画面连续播放追赶，"引擎比画面快"天然满足）。
- **两端时长一致**：引擎算的事件间隔 = 画面演绎时长（都用距离÷速度），播完一个动作恰好接下一个，无空档、无 snap。
- **为什么**：用户澄清"连续 = 引擎不断产生事件，画面逐个模拟"（Q2）+ "事件时间应由动作时长自动推算"（Q11b，票据 03 落地）。

### D2: 连续播放 = Game 新增模式，默认连续；解耦模式保留
- Game 增加 `mode: 'continuous' | 'clip'`（默认 continuous）。continuous：跨事件推进、播完自动切下一个、事件间由无球跑位填满；clip：现有点播行为（调试保留，Q4 确认）。
- `playTime` 整场推进；事件间空档由 `off_ball_run` 事件锚点填充（球员持续小步移动），不再静止 hold。
- **为什么**：连续播放是主路径，解耦点播是调试工具，都保留。

### D3: 确定性用现有种子 RNG（带标签流归票据 06）
- 引擎随机仍走单一 `SeededRng`，同 seed → 同事件流（现有约束不变）。
- **为什么**：票据 06 的带标签流/定点数是引擎 AI 复杂化时的完整目标。

### D4: 连续模式的重复段处理（对齐 Phase B design D3，Q6 确认）
- Phase B 的 `carrier_from` = 被铲者带球起点；clip 模式（当前）每个事件自包含，tackle 自带"带球中被抢"完整演绎（符合用户核心诉求）。
- 连续模式里若 tackle 前正好是同一被铲者的 dribble，viewer **丢弃 carry-beat 起点**、hold 到接触时刻，避免重复前段——在 viewer 侧处理，不改变 `carrier_from` 的"带球起点"语义。

### D5: 控件与进度条（Q3 确认）
- 连续模式复用现有控件（播放/暂停、倍速 1x/2x/4x、整场重播）+ **新增整场进度条**：可拖动到任意时刻，显示当前比赛时间/总时长。
- **为什么**：用户选加进度条/时间轴，整场连续播放需要时间定位。

## Risks / Trade-offs

- **[高密度事件流事件量大增（~150 → ~1500+）]** → 引擎一次性产出整场，事件流 JSON 变大；画面连续播不卡（一次性解析）。性能可接受，必要时后续可流式（Q9-C 选项）。
- **[off_ball_run 让有球事件被淹没]** → 保持有球事件 12-20s 一个（关键时刻清晰）+ 无球跑位短距离（1-2m）碎步，视觉上"位置调整"与"关键动作"区分。
- **[连续边界断言阈值校准]** → 阈值需大于正常事件内位移、小于 snap 跳变；端到端测试里校准并注释依据。

## Migration Plan

- `engine`：新增 `off_ball_run` 事件类型 + 无球跑位生成逻辑（事件间隔 1-2s、有球事件穿插）+ 进球时间偏移 + carrier_from 对称刷新。
- `game.js`：Game 增加 mode，`step()` 跨事件推进（不 clamp 到当前事件）。
- `app.js`：`demo_mode: false` 接引擎连续流；控件适配（整场时间、整场重播、进度条）。
- `interpretation.js`：`off_ball_run` 演绎（短距离碎步）+ 连续模式 carry-beat 丢弃。
- 测试：引擎事件密度、viewer 连续模式、端到端连续边界断言。

## 前置事项（本 change 处理，grill Q5/Q8 确认）

- **进球事件同刻**（Q5）：引擎进球后 whistle +2s、kickoff +5s（对齐 demo），球先飞进球门、哨响、再开球。
- **静默迭代后 carrier_from 过期**（Q8）：shot 分支 guard 不满足时也 `carrier_from = pos_p`（与产事件分支对称）。

## Open Questions

- 进度条 UI 形态（可拖动范围、时间显示格式）——先用基础版（整场进度 + 拖动到任意时刻），观感验收后再调。
- 有球事件与无球事件的确切密度配比（Q11 未显式确认，按 Q9/Q10 推论"有球 12-20s + 无球 1-2s"）——实施时观察观感再微调。
