# Grill Design: P3 Phase C —— viewer 连续播放（continuous-playback）

> 使用 batch-grill-me skill，按轮次采访用户，敲定 Phase C 的设计细节。
> 用户在 Open Questions 全部确认前，不写实现代码。
> 背景：Phase B（引擎 tackle 语义补全）已归档，事件流坐标语义自洽。本 change 让 viewer 整场连续播放。

## 背景（facts，已从代码确认）

- `Game` 现在是 **clip 模式**（`viewer/game.js`）：每个事件独立片段、`step()` clamp 到当前事件结束、播完停。`_interpolateAnchors` 用 `prevCur/prevAny` 处理跨事件。
- `app.js` 跑 `demo_mode: true`（精简演示事件），`MATCH_CONFIG = { match_duration_seconds: 200, demo_mode: true }`。
- 引擎连续流（非 demo）约 12-20s 一个事件，2700s 约 150 事件。
- **进球事件同刻**：非 demo 路径进球后 shot/whistle/kickoff 共用同一 `t`（demo 用 +2s/+3s 拉开）。连续播放落地时球会在射门飞行中被瞬移回中圈。
- **静默迭代后 carrier_from 过期**：shot 分支"持球者不在进攻半场"时静默迭代不刷新 `carrier_from`。
- Phase B 的 `carrier_from` = 被铲者带球起点；clip 模式每个事件自包含重现带球段（用户核心诉求"带球中被抢"）。

## Round 1: Phase C 设计树 frontier

### Q1: 连续播放的入口/形态

打开页面后，怎么进入连续播放？

- **A（推荐）默认连续播放，点开即播**：页面加载 → 引擎连续流（demo_mode: false）→ Game 连续模式 → 自动从 kickoff 播到 whistle。控件保留（暂停/倍速/整场重播）。
- **B 默认暂停，点播放开始**：加载后停在 kickoff 初始态，用户点"播放"才连续播。
- **C 保留解耦点播为默认，加一个"整场播放"按钮切换**：默认仍逐事件点播，用户切到整场模式。

理由：用户要"打开就能看到一场比赛连续流转"（P2 规划原话）。A 最直接；B 稍保守；C 保留了当前调试习惯但多一个模式切换。

### Q2: 事件间空档（12-20s 无事件）球员怎么表现

连续播放里，事件之间的 12-20s，场上球员/球怎么动？

- **A（推荐）完全 hold**：球员/球停在上个事件终态（球在持球者脚下），画面静止几秒，下一个事件接着演。
- **B hold + 轻微呼吸**：球员在站位附近轻微晃动/调整（视觉上"活着"），不做实际位移。
- **C 引擎补 off_ball_run 事件**：引擎定期发跑位事件，让球员持续移动（这是后续独立 change 的工作）。

理由：A 最简且符合"事件间空档"语义（真实比赛也不是每帧都有动作，但画面静止 12-20s 确实呆）。B 是低成本视觉改善。C 是引擎工作，Phase C 先不做（p3 design D2 已定先 hold）。

### Q3: 连续模式的播放控制

连续模式下播放控件怎么安排？

- **A（推荐）复用现有控件**：播放/暂停、倍速（1x/2x/4x）、整场重播（↻）。事件导航（◀ ▶ 跳转）在连续模式改为"跳到该事件时间点继续连续播"。
- **B 加进度条/时间轴**：新增整场进度条（可拖动到任意时刻），显示当前比赛时间/总时长。
- **C 只保留播放/暂停**：最简。

理由：A 复用现有控件 + 事件导航语义微调，改动小；B 是更好的 UX 但加进度条组件；C 太简陋。Phase C 先用 A，进度条作为后续增强（p3 design Open Question）。

### Q4: clip 模式是否保留

解耦点播（clip）模式还保留吗？

- **A（推荐）保留，作为调试工具**：连续播放是主路径，clip 模式用于逐事件检查演绎（开发/调参）。
- **B 移除，只留连续播放**：界面简单，但调试单事件不方便。

理由：clip 模式是开发调试利器（Phase B 就靠它逐事件确认五段式），保留成本低。

### Q5: 进球后的事件同刻怎么处理

进球后 shot/whistle/kickoff 同刻（球会瞬移回中圈），怎么修？

- **A（推荐）引擎加时间偏移**：进球后 whistle 加 +2s、kickoff 加 +5s（对齐 demo），让球先飞进球门、哨响、再开球。这是引擎改动。
- **B viewer 侧处理**：viewer 检测进球序列，给 whistle/kickoff 的锚点人为加偏移（不改引擎）。
- **C 暂不修**：连续播放里进球时球瞬移回中圈（可接受？）。

理由：A 是引擎语义修正（demo 已用这个方案），最干净；B 是 viewer hack；C 会让连续播放有明显的瞬移 bug。

### Q6: 连续模式的重复段处理

连续模式里，若 tackle 前正好是同一被铲者的 dribble，怎么避免重复"带球段"？

- **A（推荐）viewer 丢弃 carry-beat 起点**：tackle 的 `carrier_from` 若与上一事件终态一致（同一被铲者刚带球到接触点），viewer 把被铲者起点直接设为接触点（不再重现带球段），只在 tackle 事件内演"逼近→碰撞→弹开→捡球"。
- **B 引擎改 carrier_from 为当前 pos**：Phase B 定的是"带球起点"（重现完整带球段），改成当前 pos 会让 clip 模式失去"带球中被抢"观感。
- **C 连续模式完全接受重复**：连续播时 tackle 前重放一段带球（用户能看到"他刚才带过来又被抢"，可能反而自然？）。

理由：A 保持 Phase B 语义（clip 重现带球）+ 连续模式不重复（D4 已定）；B 破坏 clip 观感；C 是另一种选择——连续模式下前一段 dribble 刚播完，tackle 又从头重放带球段，视觉上像"倒带"。

### Q7: 连续模式的事件间 hold，球的位置

连续播放中事件间空档，球停在哪？

- **A（推荐）持球者脚下**：球跟着持球者（引擎的 pos 语义），视觉上"球在脚下"。
- **B 停在事件终态位置**：球停在上一事件结束的位置（可能不在持球者脚下，但事件间无球权概念）。

理由：A 更真实（持球者控球）；B 简单但球可能飘在场上不在任何人脚下。

### Q8: 静默迭代后 carrier_from 过期怎么处理

shot 分支"持球者不在进攻半场"静默迭代后 `carrier_from` 过期，连续模式会重放旧带球段，怎么修？

- **A（推荐）引擎静默分支对称刷新**：shot 分支的 guard 不满足时也 `carrier_from = pos_p`（与产事件分支对称），引擎改动小。
- **B 靠 Q6 的丢弃逻辑**：viewer 检测到 carrier_from 与当前 pos 差异大就丢弃 carry-beat（不够精确）。
- **C 暂不修**：连续模式里偶发重放旧带球段（罕见）。

理由：A 是引擎语义修正，与 Q5 同一批引擎改动；B 是 viewer 兜底但不精确；C 有可见 bug。

## Round 2（用户澄清 2026-08-06）："连续"的本质 = 引擎产高密度事件

> 用户澄清（2026-08-06）：**引擎层不断的产生事件，画面去逐个模拟，引擎产生的比画面快就行。**
> 即：事件流是"管道"，画面是消费者。要"连续有动作"，关键是**事件密度**（不是画面 hold）。
> 当前引擎 12-20s 一个事件（~150 事件/场），密度太低 → 画面空等。需要引擎产高密度事件（含无球跑位/位置调整类事件，如 `off_ball_run`），每 1-2s 一个；画面连续播放追赶。一次性 `simulate()` 产出整场 + 画面连续播，天然满足"引擎比画面快"。

### Q9: 高密度事件流的实现

引擎怎么产高密度事件？

- **A（推荐）引擎加 `off_ball_run` 事件 + 压缩事件间隔**：新增无球跑位/位置调整事件（球员在小范围内移动/跟随/回位），事件间隔从 12-20s 压到 1-2s；保持"有球事件"（pass/dribble/shot/tackle）节奏不变，中间穿插无球跑位事件。一次性 `simulate()` 产出整场高密度事件流。
- **B 仅压缩现有事件间隔**：不做无球跑位事件，只是让现有事件更密（球员位置靠有球事件更新）。画面连续但有球事件频率过高，观感怪。
- **C 引擎改逐步产出 + 画面实时消费**：WASM 改为逐步产出事件流（流式），画面边收边播（真正"引擎比画面快"）。改动最大。

理由：A 保留现有事件语义 + 新增无球跑位让画面持续有动作，一次性产出保持现有架构简单；B 不动事件类型但密度失衡；C 是真流式（P0 的 Q6-B 选项），架构改动大，Phase C 不必引入。

### Q10: 无球跑位事件的形态

`off_ball_run` 事件怎么设计（画面怎么演）？

- **A（推荐）短距离碎步移动**：球员从当前 pos 向"战术位置/球附近"移动一小段（每事件 1-2m），画面演"碎步调整"。事件带 `subject`（跑位者）+ `x/y`（起点）+ `x2/y2`（终点）+ `speed`（跑速）。
- **B 位置维持（原地微调）**：球员在 pos 附近小幅抖动，不真正移动。
- **C 不做无球跑位，靠画面补插**：回到画面层补插。

理由：A 让画面持续有真实移动（用户要"连续"）；B 太弱；C 违背"引擎产事件"方向。

### Q11b（用户纠正 2026-08-06）：事件时间应由动作时长自动推算，而非固定间隔

> 用户纠正："有球时间为什么要确定呢，应该是根据动作和移动速度自动推算时间吧"

- **A（推荐）事件驱动时间推进**：每个事件的 t 增量 = 该动作的实际时长（距离 ÷ 速度），动作之间可加小的"决策停顿"（如 0.3-1s，球员思考/调整的节奏）。事件流 = 动作一个接一个，无固定间隔概念。下一个事件在"当前动作结束后"发生。
- **B 固定间隔 + 补事件**：维持固定 12-20s 间隔，靠 off_ball_run 填满（已被用户质疑：时间不由动作决定）。
- **C 混合**：有球事件按动作时长，无球事件固定频率。

理由：A 是事件驱动（event-driven）时间推进，票据 03 的核心——动作时长由距离÷速度决定，两端（引擎算间隔 = 画面演绎时长）一致，播完一个动作恰好接下一个，天然连续无空档。这推翻 Q11 的"有球固定节奏"假设。
