# P38 线 A：`DECOUPLE_LAG` 通道扫描（票据 #89 核心参数的第一次实测）

> 背景：候选 03（两队解耦）是**唯一**做到「队形压到真实量级 + 射门没崩」的方案
> （纵深 27.1、射门 1.8→3.8），但 `DECOUPLE_LAG = 0.10` 是**随手写的初值，从没扫描过**。
> 本文补上这次扫描，回答"0.10 是不是好值 / 有没有更优点 / 这条路通不通"。

## 0. 结论速览

| # | 结论 | 证据 |

### 2.1 曲线形状：单调，无峰

`out/lag-sweep.svg`（`plot-lag-sweep.mjs` 生成）：

- 射门（蓝，左轴）随 lag **单调上升后在高位抖动**。0.02→0.32 是 0.4→5.9，
  但逐种子噪声极大（lag 0.32 的 10 个种子：`5,8,10,7,5,5,10,2,0,7`——从 0 到 10）。
- 重心间距（橙，右轴）**严格单调**上升：9.98 → 21.96。
- 两条曲线几乎同步抬升（`corr = 0.87`）。**这不是巧合**：把防守方往后推（lag↑）
  同时给了进攻方空间（射门↑）和两队的间距（gap↑）——**同一个自由度**。

**"最优值"是什么**：如果只盯射门，lag 0.32 最高（5.9）。但它同时是 gap 最差的点之一
（21.64，真实 8.3，判据带上限 10.14），**且 41030 帧（≈11% 的比赛时间）有球队少人**。
见 §2.2——那个"最优"不成立。

### 2.1b ⚠️ 横向一行没动（修正口径后更清楚）

修正口径（§4.1）后重跑：所有 lag 的 `latSd` 在 **0.44–0.91**，干净基线 **0.55**，
真实 **10.5**。**lag 从 0.02 扫到 0.40，横向毫无变化**——与 §5 的判读一致
（候选03 的补丁里 `let ty = st.lineup[id].1;`，横向是静态模板）。
修正前那一列显示的"1.1–1.9"**全是拼接虚高**，与 lag 无因果关系。

### 2.2 ⚠️ lag 0.32 的高射门是**红牌假象**

`lag 0.32` 的 41030 少人帧 = 10 场里有球队吃了红牌。红牌改变整场动力学
（少一人的队形、射门分布全变），而射门正是最敏感的量。

三个理由判定它不是真工作点：

1. **不可复现的偶然**：少人帧数在所有 lag 上**完全不单调**——
   `20490, 14140, 0, 11160, 0, 6560, 0, 12255, 0, 0, 0, 0, 0, 41030, 31805`。
   它不是 lag 的系统效应，是**混沌分岔**。把最优值建在这种偶然上是过拟合。
2. **L1 门实测 4/9 红**（见 §3）——其中 `l1_fouls_and_cards` 直接红，说明牌本身就不对。
3. **同族的 lag 0.28（少人帧 0）只有 3.7/场**——去掉红牌，曲线在 0.28 附近就停在 ~3.7。

> 方法学备注：这正是 `CLAUDE.md` §2 与 P38 反复踩的坑——**单看一个量会选到假点**。
> 少人帧是"这次比较是否公平"的**前置检查**，不是可选诊断。

## 4. 变体：换"作用范围"和"形状"，不是换"幅度"

动机：幅度扫描显示 lag 这一个自由度是**单调兑换**。要同时要「射门↑ + 重心间距↓」，
必须改滞后**作用在谁身上**或**怎么随球位变化**。三个旋钮，全部实测：

| 变体 | 表达式 | 依据 |
|---|---|---|
| `base` | `DECOUPLE_LAG` | 全队统一（= 候选03 原形态） |
| `scope` | `DECOUPLE_LAG`（**仅 `is_defender`**） | 真实射门瞬间是"一人贴 2.5m + 一人待命 5.4m"两层——贴身层来自防线，待命层来自中场；全队一起滞后把中场也推远了 |
| `curve` | `DECOUPLE_LAG · ball_own^k` | 真实防守方**在本方禁区前沿才整体回收**，中场区域仍对位（球越靠前滞后越大） |
| `both` | 两者叠加 | — |

### 结果

| 变体 | lag | 纵深 | 重心间距 | 普通射门 | 判据组 | 结论 |
|---|---|---|---|---|---|---|
| scope | 0.08 | 30.93 | 10.94 | 1.9 | 3/7 | 纵深被顶出靶子 |
| scope | 0.14 | 32.99 | 12.16 | 3.1 | 2/7 | 更差 |
| scope | 0.20 | 34.24 | 12.75 | 4.3 | 2/7 | 更差 |
| scope | 0.28 | **37.00** | 14.06 | 3.3 | **1/7** | 纵深退回基线量级 |
| curve | 0.20 k=2 | 27.36 | 11.62 | 1.7 | 4/7 | 射门比同 lag 的 base 低 |
| curve | 0.28 k=2 | 27.44 | 12.58 | 1.4 | 4/7 | 更差 |
| curve | 0.40 k=2 | 27.39 | 14.42 | 2.0 | 4/7 | 更差 |
| curve | 0.60 k=2.5 | 27.42 | 14.85 | 2.7 | 4/7 | 更差 |
| both | 0.20 | 29.66 | 9.45 | 1.1 | 4/7 | 纵深出靶 + 射门塌 |
| both | 0.40 | 32.94 | 11.12 | 0.9 | 2/7 | 更差 |

**两个变体都不成立，且原因是结构性的**：

- **`scope`（仅防线）破坏了纵深**：把滞后只加在防线上，防线**单独后退**而中场不动 →
  队伍被**拉长**（纵深 27 → 31–37）。真实球队防线后退时**整队一起退**（保持 25m 的紧凑）。
  这个变体恰好证明：**解耦必须整队做**，否则队形被撕开。
- **`curve`（非线性）比同 lag 的 base 射门更低**：球靠前时才滞后 = 大多数时候**不滞后**，
  有效滞后小于名义值。它只是"在更小的有效幅度上重走了一遍 base 曲线"——没有新机制。

> `both` 把 scope 的纵深问题和 curve 的力度问题叠在一起，最差，符合预期。

## 7. 副产品：两个真实缺陷（与本扫描独立，但被它暴露）

### 7.1 引擎崩溃：tackle 路径产**重复 id 的 mover**

`lag = 0.03` 在 seed 123 上 `createGame` 直接抛
`beat mover id duplicate: 17`（`viewer/protocol.js::validateBeat` 的唯一性契约）。

**根因**（探针 `probes-main/probe-crash-beat.mjs`，在原始 JSON 事件流上定位到 t=2105）：

```
beat #2365 @ t=2105  重复 id=10
  第一条 {id:10, from:(0.7917,0.6672), to:(0.8006,0.6517), action:"run"}   ← beat_movers 产出
  第二条 {id:10, from:(0.8006,0.6517), to:(0.7844,0.6681), action:"run"}   ← tackle 的"推开队友"
```

`emit_tackle_highlight_impl` 先调 `beat_movers` 为全员产候选 mover，
之后又遍历"被抢者 2m 内的队友"**再 push 一条**同 id 的 mover。两条的 `from` 不同
（第二条读的是**分离后**的 `st.pos`），但 id 相同 → 协议拒绝。

**触发条件**：队友间距 < `SAME_TEAM_MIN_DIST_M`（2m）。**队形压紧后这是常态**——
所以这个崩溃是**队形压缩方案的通用风险**，不是 lag 0.03 特有：exp4b 单独跑
也崩（10 种子崩 1 个，`beat mover id duplicate: 10`）。

**修复**：push 前跳过已有 mover 的球员。补丁存
`patches/fix-tackle-duplicate-mover.patch`（5 行）。**这不是本 change 的交付物**——
它是**独立于队形机制的引擎缺陷**，建议单独立项修（本阶段不提交引擎改动）。

### 7.0 ⚠️ 评测器 `latSd` 的口径缺陷：引擎侧被**拼接灌水 6.5×**（线 B 期间发现，影响本文件）

发现经过：线 B 的 `render-trajectories.mjs`（单场）对某配置报横向 sd **0.37m**，
而 `p38-eval.mjs`（同 wasm）报 **11.26m**。差 30 倍 → 追到评测器。

**根因**：评测器把所有种子的帧 **concat 成一个序列**再算 sd。
不同场次的球员 y **均值不同**（各自战术相位），拼接后**场间偏移全计入 sd**。
`probe-latsd-caliber.mjs` 实测 **逐场 1.73m vs 拼接 11.26m（6.5×）**。
`swarm` 同样受影响（基线 0.328 → 0.488）。

**方向是反的**：动得越多的配置场间偏移越大 → **虚高越多**，
该缺陷**奖励横向大改的 hack**，与判据组"抓 hack"的初衷相反。

**真实侧本来就是逐场算再平均**（`eval-criteria.mjs --real`：10.81 / 10.22）——
引擎侧拼接 = 口径分叉，与 P36「口径分叉 = 数字不可比」同一个错误，只是发生在**时间轴**上。

**已修**：`p38-eval.mjs` 改为 `evaluateByMatch`。真实侧数字**不变**（10.81/10.22，已验证）。
本文件的 `latSd`/`swarm` 两列已按新口径重跑（§2.1b）；**结论未变且更清楚**。
→ 建议 #91 同步修 `eval-criteria.mjs`。详见 `mechanism-exploration.md` §4。

### 7.2 评测器 `fault` 的 `NaN`（`notes/criteria/README.md` 待办里那条"未修"）

判据组 README 记着「`fault` 在 exp4b 上为 `—`，需修评测器」。**根因找到且是通用的**：

`eval-criteria.mjs` 的 `teamXs()` 守卫写的是 `if (out.length < 7) return null`，
但 `fault` 是按**深度排名**算的——`acc[i]` 收"全队第 i 深"。**球队少一人时
`xs[9]` 是 `undefined`** → `acc[9]` 混进 undefined → 均值 NaN → `fault = null`。

**不是 exp4b 特有**：任何产红牌的变体都中招（本轮 lag 0.05 seed 7 复现）。
`< 7` 那种宽松守卫只防"全队丢失"，挡不住"少一人"。

**修复**：守卫改 `!== 10`（人数不足的帧整帧剔除——9 人队的"第 9 深"与 10 人队的
"第 9 深"不是同一估计量，混池会同时污染均值和断层）。本仓库的 `p38-eval.mjs` 已修；
**`notes/criteria/eval-criteria.mjs` 未改**（那是 #91 的产物，交给它自己的 owner）。
真实侧数据无红牌，**修复不改真实参考值**（仍 5.2 / 4.7，已验证）。

## 8. 对 #89 的意义

候选 03 的假设是「两队共用块锚 → 重叠 → 射门空间归零」。
**本轮扫描把这个假设钉死了，同时证明它不足以解决问题**：

1. ✅ **假设成立**：解耦确实恢复射门（0.5 → 3.7/场，去掉红牌污染后）。
2. ❌ **但它是零和的**：射门与重心间距由同一个自由度兑换（`corr = 0.87`）。
   真实足球不是零和的——它靠**防守层次**（贴身的 + 待命的）同时做到"有压迫"和"有空间"，
   而**层次是横向 + 纵深的结构，不是把整块往后搬**。
3. ❌ **上限被判据组封死**：所有 lag ≤ 5/7，被同一对**横向**判据挡住。
   decouple 全程只动 x。

**给 #89 的结论**：`DECOUPLE_LAG` **可以关闭**——它不是"待调优的参数"，
而是**一条死路**（幅度、范围、形状三个自由度全部实测穷尽）。
队形机制必须**同时处理横向**；只要横向不动，无论怎么调纵深↔射门的兑换率，
方案都过不了判据组，画面也还是"铁轨"。

这正是线 B（`mechanism-exploration.md`）的出发点。
