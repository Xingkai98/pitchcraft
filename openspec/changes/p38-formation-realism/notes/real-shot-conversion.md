# 真实射门转化率曲线（StatsBomb 大样本）

> **⚠ 数据来源与许可**：本报告全部真实侧数字来自 **StatsBomb Open Data**
> （`hudl/open-data`），依 *StatsBomb Public Data User Agreement* 使用：
> **非商用、禁止再分发原始数据、公开引用须署名 StatsBomb**。
> 原始事件 JSON **不入库**（落 `.scratch/tracking-data/statsbomb/`，gitignored）；
> 入库的 `out/real-shot-conversion.json` 是**聚合派生量**（分箱计数 + CI），不是逐条数据。

> **样本**：**356 场**（`sampleHash 09129427b2cc`）/ **9,653 次射门** / 24 个赛事，
> 跨男足五大联赛 + 世界杯 + 欧洲杯 + 欧冠 + 女足（英超/WSL、NWSL、女足世界杯、女足欧洲杯）+ 美职联。
> 分层抽样（每个「赛事-赛季」轮转取），不是随机抽——代表性靠设计。

## 0. 一句话结论

**#102 卡住的样本量缺口补上了，而且它担心的那件事不成立。**

- **#102 §2.3B：结论取决于 on-target 口径，两个都报**（n=6,067 禁区内射门）：

  | 口径 | 值 | 95% CI | vs 门的上界 0.56 |
  |---|---|---|---|
  | **引擎口径**（`realism.rs:947`，`(g+saved)/n`） | **0.420** | [0.407, 0.432] | ✅ **不冲突** |
  | **#102 自己的口径**（§2.2 †，`(g+saved+wood)/(n−blocked)`） | **0.563** | [0.549, 0.577] | ⚠️ **仍不可判定** |

  ⚠ **按被判定对象（#102）的原定义，答案是"仍未定论"，不是"解决"**。
  CI 从宽 0.315 压到 0.028（窄了 8 倍），但中心值也从 0.741 移到 0.563，
  **恰好压在 0.56 上**。两个口径差 14pp，**主因是"封堵出分母"（+11.4pp）**。
  （本报告第一版只报了引擎口径就宣称"悬案解决"——**换了被测量的定义**，已改。）
- **附带复核了引擎 L3 的三条参考带**（`realism.rs:944-954`，其注释引自研究报告而非实测）：
  射正率 / 转化率 / 禁区内进球占比，**三条全部与真实相容**（见 §5）。
- **新发现（与体积无关）**：引擎**远射桶的结果分布带外**——真实远射 saved 23.7%
  而引擎声明 11%、off 74.2% 而引擎声明 85%（§2.2）。禁区内/弧两桶九条带全绿。
- **转化率随距离陡峭衰减**（§3），且**逐赛事离散度小**（sd 0.062，§7）——
  支持"用一个常数"的简化，但那常数应当**随距离变化**而不是全局一个。

## 1. 口径（决定这些数字能否与引擎对接）

⚠ **这是最容易出错的地方**。#102 §2.3B 的教训就是**用欧氏口径去撞纵深口径的门**
= 口径错配，把一个"不可判定"说成了"直接冲突"。故本报告**两个口径都报、且显式标注**：

| 口径 | 定义 | 用途 |
|---|---|---|
| **纵深**（x-only） | `纵深米 = (120 − x) / 120 × 105` | **与引擎同口径**（`dist_to_goal_m` 只看 x）。对接引擎桶带**必须**用它 |
| **欧氏** | 到球门中心的直线距离 | 物理上更接近"射门难度"，**不是**引擎口径，仅作对照 |

- **坐标系换算**：StatsBomb 用 120×80（球门中心 `(120,40)`），引擎用 105×68 米。
- **on-target 口径（有两个，必须区分）**：
  - **引擎口径**：`(goal + saved) / n`，其中 `saved = {Saved, Saved to Post}`，
    **blocked 在分母里**——照抄 `engine/tests/realism.rs:947` 的 `sot_r`。
  - **#102 口径**（`conversion-adaptive.md` §2.2 †）：`(goal + saved + woodwork) / (n − blocked)`，
    **中柱进分子、封堵不进分母**。
  ⚠ `Saved Off Target` **不是 on-target**（StatsBomb Spec v1.1：saved *but not on target*）。
  本报告第一版用 `startsWith('Saved')` 把它算进 saved，**错**（33 脚，已修）。
- **引擎桶边界**：`BOX_DIST_M=16.5` / `ARC_DIST_M=25.0`（`engine/src/lib.rs:513,515`）。
- **全点口径、不剔除任何射门类型**（含点球/任意球/头球）——与引擎的 `regular` 统计口径一致。

## 2. ★ #102 §2.3B 的悬案：判定结果

**问题**：真实禁区内 on-target 率是否撞 L1 门带的上限？

**门带**（`realism.rs:659-661`）：禁区内 `goal ∈ [0.10,0.20]` + `saved ∈ [0.24,0.36]`
→ on-target 上界 = **0.56**。

| on-target 口径 | 公式 | 值 | 95% CI | 判定 vs 0.56 |
|---|---|---|---|---|
| **引擎口径**（`realism.rs:947`） | (goal+saved)/n | **0.420** | [0.407, 0.432] | ✅ **不冲突** |
| **#102 口径**（`conversion-adaptive.md` §2.2 †） | (goal+saved+wood)/(n−blocked) | **0.563** | [0.549, 0.577] | ⚠️ **仍不可判定** |

**两个口径差 14pp，来源可分解**：中柱进分子 **+2.5pp**、**封堵出分母 +11.4pp**
（分母 6067 → 4797）。**后者是主因**。

> ⚠ **这是本报告第一版最严重的错误**：它只报引擎口径就宣称"#102 的悬案解决了"，
> 而 #102 的悬案是**用 † 口径提出的**——换了被测量的定义去宣布对方的问题被解决。

### 2.1 ⚠ 引擎口径：只有三个 outcome，`off_target` **吸收** blocked

**这是本报告第一版算错的地方，记下来**：引擎只有 `goal / saved / off_target`
（`engine/src/lib.rs:3170-3176`；全库 **0 处** blocked）。
而 StatsBomb 把 `Blocked` **单列**。故：

> **引擎口径的 `off` = StatsBomb 的 `off` + `blocked`**。

第一版把 blocked 与 off 分开比、还写"引擎没有为这两项声明带"——**两处都错**：
引擎**有** off 带（`realism.rs:661` 禁区内 `off ∈ [0.48,0.60]`），且必须合并后再比。

### 2.2 三条带全判（引擎口径）

| 桶 | 量 | 真实 [CI] | 门带 | 判定 |
|---|---|---|---|---|
| **禁区内 ≤16.5m** | goal | 17.2% [16.3%, 18.2%] | [10%, 20%] | ✅ 带内 |
| | saved | 24.8% [23.7%, 25.9%] | [24%, 36%] | ⚠️ 跨带边（**压在下沿**） |
| | off（含 blocked） | 58.0% [56.8%, 59.3%] | [48%, 60%] | ✅ 带内 |
| **禁区弧 16.5–25m** | goal | 3.9% [3.3%, 4.7%] | [3%, 12%] | ✅ 带内（**贴下沿**） |
| | saved | 25.0% [23.4%, 26.7%] | [14%, 30%] | ✅ 带内 |
| | off（含 blocked） | 71.1% [69.3%, 72.8%] | [61%, 75%] | ✅ 带内 |
| **远射 >25m** | goal | 2.1% [1.4%, 3.2%] | [0%, 8%] | ✅ 带内 |
| | **saved** | **22.7% [20.1%, 25.4%]** | **[4%, 18%]** | ❌ **带外** |
| | **off（含 blocked）** | **75.2% [72.4%, 77.9%]** | **[78%, 92%]** | ❌ **带外** |

> **禁区弧三条全绿、禁区内三条相容（saved 压在下沿）** —— 引擎对这两桶的标定基本准。
>
> ⚠ **远射两分量带外，且是同一个偏差的两面**：
> 真实远射 saved **22.7%**（引擎声明 11%）而 off **75.2%**（引擎声明 85%）。
> 即**引擎的远射太"野"**——真实球员的远射有**五分之一强**是射正被扑，引擎只有十分之一。
> 这**与 #102 的三条必重标门是不同性质的问题**（那三条是体积标定，这条是**远射结果分布本身**）。
>
> ⚠ **"带外"是按本探针检查的 9 条带说的**（3 桶 × goal/saved/off）。
> 引擎在 `realism.rs:658-670` 共声明 **9 条**，本表全查了。

## 4. ⚠ 三个口径维度：谁是"#102 翻车"的主因

#102 §2.3B 的结论涉及**三个独立的分类选择**。把它们分开算（同一份 6,067 脚）：

| 维度 | 选项 | 对应值 |
|---|---|---|
| **A. on-target 公式** | 引擎口径 `(g+saved)/n` | **0.420** ✅ 不冲突 |
| | #102 口径 `(g+saved+wood)/(n−blocked)` | **0.563** ⚠️ 跨 0.56 |
| **B. 距离口径** | 纵深 ≤16.5m（引擎桶） | 0.420 / 0.563（A 的两行） |
| | 欧氏 ≤16.5m | 0.436 / **0.574** ⚠️ 跨 0.56 |

**结论：#102 翻车的**主因是 A（on-target 公式，14pp），不是 B（euclid/depth）。**
第一版把原因全归给 euclid/depth 错配——**不完整**：
**B 单独最多动 1.6pp（引擎口径下）或 1.1pp（#102 口径下），
而 A 单独动 14pp**；且在 #102 自己的口径下，**B 的两个选项都跨 0.56**。

> 换句话说：#102 §2.3B 当时诊断出"口径错配"是**对的**，但它认错了是哪个口径。

### 4b. B（距离口径）本身也值得记：纵深把 17% 的低质量射门算进"禁区"

「**纵深**在禁区内、但**欧氏** >16.5m」的射门 = **1,017 次**（占禁区内射门的 **16.8%**）
—— 这批是**贴近底线的极小角度射门**：

| 子集 | n | on-target | conv |
|---|---|---|---|
| 禁区内全部（纵深） | 6,067 | 42.0% | 0.406 |
| 其中「欧氏 >16.5m」（小角度） | 1,017 | **34.2%** | **0.144** |

**对引擎的启示**：
- 若引擎要用"距离"当射门质量的**输入**，**欧氏比纵深更合适**
  （纵深把 17% 的极低质量射门算进了"禁区"，稀释了质量信号）；
- 但**对接引擎现有的桶带**（它是按纵深分的）**必须用纵深口径**；
- **两者不可混用**——这是 #102 已经交过学费的教训（只是它当时记错了账）。

## 5. ★ 复核引擎 L3 的三条参考带

`realism.rs:944-954` 的 `l3_shot_ratios` 用三条带卡引擎，注释写"真实参考带
（`report.md` §五）：射正率 ~33%、转化 ~10%、禁区内进球 ~85%"。
**那三个数的来源是研究报告，不是大样本实测**——本节复核它们：

| 量 | 引擎带 | 引擎注释的"真实值" | **本样本实测** | 95% CI | 判定 |
|---|---|---|---|---|---|
| 射正率 `sot` | [0.28, 0.39] | ~0.33 | **0.371** | [0.361, 0.380] | ✅ 带内 |
| 转化率 `conv` | [0.08, 0.14] | ~0.10 | **0.121** | [0.115, 0.128] | ✅ 带内 |
| 禁区内进球占比 | [0.72, 0.92] | ~0.85 | **0.894** | [0.875, 0.910] | ✅ 带内 |

**三条全部相容**——引擎引的那三个数**站得住**（样本 9,653 射门 / 1,167 球，CI 已窄到能判定）。

> ⚠ **新的杠杆**：`sot` 与 `inside` 的真实值都**贴近带的上沿**
> （0.371 vs 上界 0.39；0.894 vs 上界 0.92），`conv` 在中段偏上。
> 若 #102 的"抬体积"方案把射门结构推向**更多近距离射门**，这三条会**先撞上沿**——
> 这是比"射门条数带 `[6,11]`"更早触发的约束，**重标时应当一并考虑**。

## 6. freeze_frame：能不能支撑"防守者距离"维度

有 `freeze_frame` 的射门：**9,491 / 9,653（98.3%）**。

→ **可以**算"射门瞬间最近防守者距离"这类**质量维度**（#102 只用了距离，没用防守者）。

⚠ 两条限制：
1. 它是**快照不是 tracking**（只在射门瞬间有），不能算"防守者的移动/逼近速度"；
2. 不同赛事的覆盖率不同（老赛季略低）。

**这是本样本相对 Metrica/SkillCorner 的独有增量**：SkillCorner 没有射门事件，
Metrica 有但只有 3 场。若 #102 的后续要把"防守者距离"纳入质量函数，**只有这份数据能做**。

## 10. 未做的与诚实声明

1. **样本是 356 场不是全量 4235 场**。停在 356 是因为它**远超 CI≤0.05 所需**（206 场）；
   继续下不会改变任何结论方向，只会把 CI 再压窄。全量需 ~10GB。
2. **没有碰"角度"维度**：`tradeoff-breaking.md` 的 AUC 0.505 说角度是噪声，本报告未独立复核。
3. **没有算"防守者距离"**：freeze_frame 支持（§6），但留给 #102 的后续。
4. **没有分赛季/分年代**：1958 世界杯与 2023 女足世界杯混在同一池里。
   若老年代的射门统计口径不同，会引入噪声——**未检验**。
5. **`blocked` 的归属**：本报告按引擎口径把 blocked 排除在 on-target 之外。
   ⚠ 但 StatsBomb 的 `Blocked` 包含"被封堵后仍可能进球"的情况（实际极少），
   且**不同数据商对 blocked 的定义不同**（Wyscout 的 `block` 标签口径待对齐）。
6. **点球/任意球未单列**：全部混在池里（实测 `Open Play` 8,928 / `Free Kick` 543 /
   `Penalty` 180 / `Corner` 2）。引擎的 `regular` 统计**含**这些，故口径一致；
   但若要建模"运动战转化率"，需剔除 `shot.type != 'Open Play'` 的射门——**未做**。
   点球转化率接近 100%，180 个点球会把总的 conv 抬高约 1.3 个百分点，**影响小但非零**。
8. **⚠ 样本不可按 `--limit` 复现**（审阅发现）：当前 `events/` 的 356 场是**多次运行累积**的，
   与 `stratifiedSample(356)` 的确定性输出**只重合 201/356**（下载时跑的是更早的取样器）。
   `manifest.json` 记了这份样本的 sha256，但**原始 JSON 不入库**，故第三方无法独立重建它。
   要得到与 `--limit` 严格一致的样本：清空 `events/` 重跑。
   脚本已加"应下载集合 vs 盘上集合"的自检（不一致时警告）。
9. **§7 的"均值"与 §2/§3 的池化值不是同一个量**：前者是**等权**跨赛事均值（0.392），
   后者是**按射门数池化**（0.406）。La Liga 占样本 32%，池化值因此偏向它。
10. **`Blocked` 的语义**：本报告按引擎口径把它并入 `off`。但 StatsBomb 的 `Blocked`
   指"被防守者挡出"，**不区分挡出后是否成为角球/二次进攻**；引擎的 `off_target`
   是纯"打偏"。两者**不等价**，只是引擎没有更好的桶。这一点在"引擎远射太野"的
   结论里可能贡献了一部分（真实远射被封堵的比例可能被 StatsBomb 记在 Blocked 里）。
