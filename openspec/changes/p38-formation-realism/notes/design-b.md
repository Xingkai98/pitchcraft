## 1. 起点：被忽略的角度到底成不成立？

### 1.1 引擎里**没有**任何球员间相互作用项（grep 证据）

用户提示的角度「球员是互相约束的，还是各自算目标？」——我查了，答案是**后者**：

| 真实足球里的相互作用 | 引擎里有吗 |
|---|---|
| 越位（进攻线 ← 对方最后一名防守者） | **没有**。`grep -i "offside\|越位" engine/src/lib.rs` → **0 命中** |
| 盯人（防守者 ← 特定进攻球员） | **没有**。没有 mark/assign 概念 |
| 协防/补位（防守者 ← 队友的失位） | **没有**。`cover`/`screen`/`press` 只存在于**未合入**的 demo 分支 |
| 压迫触发（← 队友的逼抢姿态） | **没有** |
| 队友间距 | **有**，但只有 P34 的 `SAME_TEAM_MIN_DIST_M = 2.2m` 排斥，且**只防重叠** |

`formation_target(st, id)` 的**全部输入**是：`st.lineup[id]`（自己的角色基准）、
`st.ball_pos`、`st.possession`、`st.transition`。**没有一项引用 `st.pos` 里其他 21 人的位置**。

唯一"看见别人"的地方是 `compute_mover_candidates` 第二遍的 repulsion（`:2834`）——
它是**目标层的、2.2m 的、纯防重叠的**，只在两人目标已经撞上时才介入。它**从不组织**队形形状。

**结论：用户的怀疑成立。"队形"在这个引擎里不是涌现的，是 10 个独立的"球位函数"并排画出来的。
只要不动这一点，任何在 `formation_target` 上的改动都只是换一种方式把 10 个点摆开。**

### 1.2 真正的病灶：不是"太深"，是**线的结构**

这是我这一轮最有价值的发现，而且**它解释了为什么"调常数能四项全绿却结构全错"**。

把每帧 10 名非门将按纵深排序、取相邻次序的平均间距：

```
真实 Metrica  2.7 / 3.1 / 3.1 / 3.9 / 3.1 / 3.4 / 3.4 / 5.3 / 4.5   ← 近似均匀
引擎          4.1 / 0.1 / 2.3 / 14.2 / 0.2 / 1.9 / 2.0 / 19.1 / 2.7  ← 两个大洞
```

真实球队的 9 个间距**全部落在 2.7–5.3m**，均值 ~3.7m。也就是说：

> **真实的 10 名非门将，在纵向上近似"等间距排布"——不是"3 条线 + 2 个大空隙"。**

反事实验证（`probeK`）：把 10 个目标位置按**等间距**摆开、跨度取 0.32 归一化（≈33.6m），
得到 **纵深 26.9m**，与真实 25.9m 几乎相等；而真实自己的间距序列也确实是均匀的。
**纵深这个指标，本质上是"人数 × 平均间距"的度量（q10–q90 掐掉两端各约 1 人 → ≈ 8 个间距）。**
41m 的纵深 = 8 × 5.1m 的平均缝；26m = 8 × 3.2m。**要修的不是"深度"，是"缝宽"，而缝宽由线结构决定。**

而引擎的 `default_lineup` 是一个**分线模板**：
后卫 4 人在 x∈[0.14, 0.20]（线内跨度 6.3m）、中场 4 人在 x∈[0.40, 0.42]（2.1m）、前锋在 0.62。
**线内挤在一起（0.1–2.3m），线间空出 0.20 ≈ 21m。** 这正是那两个洞的来源。

### 1.3 决定性实验：**任何"目标公式"方案都修不掉断层，只会让它搬家**

我把三套候选目标公式挂在**引擎自己的球与对方防线轨迹**上，过**结构判据**（`probeJ`）：

| 方案 | 纵深 | 平移增益 g | 相邻次序间距 | 最大断层 |
|---|---|---|---|---|
| **真实 Metrica** | **25.9** | **0.596** | 2.7/3.1/3.1/3.9/3.1/3.4/3.4/5.3/4.5 | **5.3m** |
| 引擎现状 | 40.5 | 0.176 | 4.1/0.1/2.3/14.2/0.2/1.9/2.0/19.1/2.7 | 19.1m @8→9 |
| M1 块平移 g=0.59 + 固定块深 | 25.6 ✅ | 0.590 ✅ | 2.3/**0.0**/1.2/**11.5**/0.0/1.2/0.0/**11.5**/0.0 | 11.5m @4→5 |
| M2 块平移 + 锋线锚定对手越位线 | 25.6 ✅ | 0.590 ✅ | 2.3/0.0/0.0/**12.7**/0.0/0.0/0.0/**12.7**/0.0 | 12.7m @8→9 |

**M1/M2 都把纵深与平移增益调到了真实值**（这是"四项指标全绿"级别的成功），
**但断层没有消失，只是从 8→9 搬到了 4→5，且仍然是 11.5m**（真实的 2.2 倍）。

原因很干净：**模板的线结构在任何仿射变换下都保留。** 平移、缩放、按球位插值——
都只是把那 3 条线连同它们的 21m 空隙一起搬走/压扁。**要消掉空洞，必须改变"线"本身。**

**这就是给审阅用的判据**：任何方案，先看 `probeJ` 那张表的**断层列**，再看纵深列。
断层从 19.1 降到 11.5 不算修好——它得降到 5–6m（真实量级）才算。

## 2. 三个机制上不同的方案

三个方案的**机制层**各不相同：A 是**队内**相互作用（球员↔队友），B 是**队际**相互作用
（球员↔对手），C 是**块级**动力学（球员↔全队整体）。它们不是同一个想法的三种参数。

---

### 方案 A：深度链约束（队内相互作用）—— 让"线"退化成"链"

#### A.1 机制

**改什么**：把"每人算一个绝对目标点"改成"**沿纵深次序的链式目标**"——
每名球员的目标由**它的相邻次序队友**推出，而不是由角色基准推出。

新增一个函数（签名级）：

```rust
/// 一支球队按纵深升序的 10 名非门将 id（每 tick 重算，剔除罚下者）。
/// 与 `home_defenders`（静态身份）不同：这是**动态次序**，随球移动而变。
fn depth_order(st: &MatchState, team: u32) -> Vec<i32>;

/// 链式队形目标：第 k 名的目标 = 第 k−1 名的目标 + 该档的目标间距。
/// 锚点是**块尾**（最深者），间距由角色档位给出。
fn chain_formation_target(st: &MatchState, id: i32, order: &[i32]) -> (f64, f64);
```

链的形状（足球语言）：**块尾锚定 → 逐档向前累加间距**。间距不再是常数，而是按
足球的"线密度"分配：后防 4 人之间靠紧（≈4m，防线是一条线），防线→中场放宽（≈6m，
中场要接应也要回防），中场 4 人之间（≈4m），中场→锋线（≈6m），锋线 2 人（≈5m）。
**10 人的 9 个间距落在 4–6m**，而不是现在的 0.1m 与 21m。

**关键**：这不是"把模板换成更密的模板"。模板换了仍然是模板，仍然会搬洞。
链式目标的要害在于**间距是"相邻次序"的函数，不是"角色"的函数**——
当球移动、当某个球员前插、当有人被罚下（10 人变 9 人）时，**链会自动重新分配间距**，
不会凭空留下一个固定位置的空洞。这是"相互作用"的实质：每个球员的位置**依赖于队友的位置**。

#### A.2 为什么符合足球规律

- 足球里"阵型"从来不是 3 条线，而是**连续的支持层次**：真实 tracking 数据显示
  10 人的纵深间距是 2.7–5.3m 的近似均匀分布（`probeJ` 实测），不是"线 + 空隙"。
- 真实球队**换阵/少一人/被压回时，是整体重新分配间距**，不会在中间留一个 21m 的真空。
  真空在足球里意味着"这里没人接应"——是战术错误，不是常态。
- 每档间距的**不对称**（线内紧、线间松）对应真实的"层次"：防守时后防四人是**一条线**
  （越位线要求），而中场与后防之间是**可压缩的空间**（球队被压扁时这段最先消失）。
  这正是真实球队在退防时"两条线压缩、锋线回撤"的机制。

#### A.3 预期指标效果

| 指标 | 预期 | 为什么 |
|---|---|---|
| **纵深** | 41 → **26–29m** ✅ | 直接后果：9 个间距 × ~3.5m ≈ 32m 块跨度，q10–q90 掐两端 ≈ 27m（`probeK` 实测 26.9） |
| **相邻次序间距** | **断层从 19.1 → ~5m** ✅ | 这是本方案**唯一**能真正达成的目标，也是判据的核心（§1.3） |
| 紧凑度 | 18.7 → **15–16m** | 块内跨度缩小，绕重心半径同步缩小 |
| 重心间距 | 23.5 → **变小但未必到 8m** ⚠️ | 纵深缩了重心间距会缩，但**这个指标的病在别处**（见 §2.2、§4.2） |
| 宽度 | 基本不变 | 本方案只动 x 方向，y 完全不动 |
| 弹性 | **变化不大** ⚠️ | 链锚定在块尾，块尾仍随球走；弹性由锚点规律决定，不由链决定 |

#### A.4 预期副作用

- **少一人（红牌）时链会自动变短**——这是好事，但需要测试 9 人链的间距分配不会把
  某两人挤到 `SAME_TEAM_MIN_DIST_M` 以下（现有 repulsion 会兜底，但兜底会破坏链的形状）。
- **角球/任意球准备期**走 `corner_setup_target`，不受影响（好）。
- **门将**不参与链（`id==0/21` 已单独处理）。
- **最风险的一条**：链锚在"块尾"，而块尾（防线）现在被 clamp 钉在 `base` 与 `ball` 之间。
  如果只做 A 不做 C，链会**把一个紧的块整条拖到错误的高度**——纵深对了，但位置错。
  **A 必须与 C 一起做。**

#### A.5 hack 自评

**低**。这是我最不像 hack 的方案，因为它直接替换了**产生数字的结构**，而不是替换数字。
它不依赖任何"调到某个数"的标定——间距常数（4m/6m）来自足球语义（线内紧、线间松），
即使 P36 的指标全被删掉，一个"线内紧、线间松、随球平移"的链仍然是正确的足球结构。
**唯一的标定泄漏**：我把 span 定在 0.32（≈33.6m）是看着真实的块跨度选的。
更诚实的做法是让间距常数的**和**自然给出跨度，而不是先定跨度。

#### A.6 实现代价

- 新增 `depth_order`（~15 行）、`chain_formation_target`（~30 行）、~6 个间距常数。
- 改 `compute_mover_candidates` 的第一遍：`targets[id] = Some(formation_target(st, id))`
  → 先算 `order`，再对每档用链式公式。**注意**：链要求**按次序**算，
  所以第一遍的循环要按 order 顺序而不是 `for id in 0..22`。
- 新增状态：**无**（order 每 tick 从 `st.pos` 重算，零新字段）。这是本方案的一个强项。
- 与其他部门的接口不变（仍产出 `(f64,f64)` 目标）。

### 方案 B：越位线锚定（队际相互作用）—— 让对方的防线进入我方决策

#### B.1 机制

**改什么**：给进攻方的最前线（以及防守方的防线）加一个**以对方最后一名防守者为参考**的约束。
这是引擎里**第一个跨队的位置耦合**。

```rust
/// 某队所攻球门的越位线：对方第 2 深的非门将球员的 x（归一化）。
/// 不足 2 人时退化为对方最深者；再不足时退化为球门线。
fn offside_line(st: &MatchState, team: u32) -> f64;

/// 队形目标 + 越位约束（在 chain_formation_target 之后施加）：
/// 攻方所有球员的 target_x 不得超过 offside_line − OFFSIDE_MARGIN。
fn apply_offside_cap(st: &MatchState, id: i32, tx: f64) -> f64;
```

带宽的常数只有一个：`OFFSIDE_MARGIN`（留出的安全余量，足球语义 ≈ 0.5–1.0m）。

**为什么这是"相互作用"而不是"另一个球位函数"**：`offside_line` 读的是 `st.pos` 里
**对方球员**的位置。**对方的防线动了，你的锋线就动**——这是真实的双向耦合，
也是引擎现在完全没有的东西。

#### B.2 为什么符合足球规律——而且这是**数据说的**，不是我说的

我做了两个独立的检验（`probeE`、`probeH`）：

**(a) 偏解释力（控制了球位之后，对方防线还有多少解释力）**

| | 真实 Metrica | 引擎 |
|---|---|---|
| 我方锋线 ~ 球 | R²=0.697 | R²=0.580 |
| 我方锋线 ~ 对方防线 | R²=0.894 | R²=0.650 |
| **对方防线的偏解释力** | **0.201** | 0.093 |
| **球位的偏解释力** | **0.003** | 0.023 |

真实数据里，**在已知球位的前提下，对方防线额外解释了 20% 的锋线位置方差；
而球位在已知对方防线后只额外解释 0.3%**。也就是说：

> **真实球队的锋线，跟对方防线走的成分远大于跟球走的成分。**
> 引擎正好相反——球位仍有 2.3% 的偏解释力，与对方防线（9.3%）同量级，没有分化。

**(b) 滞后交叉相关（分离因果方向，避免"双方一起随球移动"的共线性）**

`corr(Δ我方锋线(t), Δ对方防线(t−lag))` vs `corr(Δ我方锋线(t), Δ球位(t−lag))`：

| lag | 真实：防线领先 | 真实：球领先 | 引擎：防线领先 | 引擎：球领先 |
|---|---|---|---|---|
| 1 拍 (0.2s) | **0.430** | 0.157 | 0.160 | 0.156 |
| 3 拍 | **0.420** | 0.166 | 0.199 | 0.183 |
| 10 拍 | 0.346 | 0.157 | 0.160 | **0.251** |

真实侧：**防线在 1 拍前的位置变化，预测我方锋线的变化（r=0.43）是球（r=0.16）的 2.7 倍**，
且这个优势在 lag 1/3/5/10 上**持续存在**（不是噪声）。
引擎侧：**两者没有区分度**（0.160 vs 0.156），且**滞后越长，球反而越占优**（lag10: 0.251 vs 0.160）——
引擎的锋线是在**跟球**，不是在**跟人**。

**还有一个独立的佐证**（`probeC`/`probeD`）：真实比赛里"锋线离对方门线"与"对方越位线离该门线"
回归斜率 = **−1.09**、r = **−0.95**；引擎是 −1.23、r = −0.84。真实的两条线是**强反向绑定**的。
而且真实的越位余量中位数只有 **+1.5m**、p10–p90 是 [−4.4, +8.3]——
**真实锋线是贴着越位线站位的**（这正是越位规则在战术上的后果）。
引擎的中位数是 **+14.6m**、p10–p90 [9.0, 19.0]——锋线**系统性地离越位线 15m**，
既不贴线也不越线。**引擎的锋线活在一个没有越位的世界里。**

#### B.3 预期指标效果

**这一节我补了实测**（`probeL2`，修正了一版方向错误——见 §4.2 #4 的订正说明）。
把"块模型"当基线，只加越位锚定：

| 指标 | 块模型（无锚定） | 块模型 + 越位锚定 | 真实 Metrica |
|---|---|---|---|
| **重心间距** | 21.4m | **6.6m** ✅✅ | **7.4m** |
| **纵深** | 25.6m | **12.8m** ❌ | **25.9m** |
| 块跨度 | 27.7m | 13.9m | 32.5m |
| 弹性 | 0.0m | 0.0m | 10.3m |

**重心间距确实被这一条机制修好了**（21.4 → 6.6，真实 7.4）——这是 B 的核心价值，
也是 §4.2 #4 那个空缺的答案。

**但它有一个我刚测出来的严重代价**：纵深从 25.6 掉到 **12.8m**，**过冲了**。
原因是粗暴的 cap 把**全队**（`for i in 7..=0` 保序）一起压到越位线以下，
**整队塌成一条线**——真实球队不是这样，真实是"锋线贴线、后面各档依次展开"。

**修正方向（必须写进实现）**：越位 cap 只能作用于**最前 1–2 人**，
且被压下来的人要**沿链向后重新分配间距**（与 A 的链式分配联动），
而不是把后面所有人一起推下去。**这再次印证 §3 的结论：B 必须与 A 组合，
单用 B 会把队形压扁。**
| **纵深** | 略降（2–4m） | 锋线被锚下来，块的上沿降低 |
| **弹性** | **降低** ✅ | 锋线上限由对方防线决定（它是慢变量），不再随球剧烈伸缩。**这是本方案最漂亮的副作用** |
| 相邻次序间距 | 断层**可能搬家** ⚠️ | `probeJ` 的 M2 证实：单靠越位锚定，断层从 8→9 搬到 4→5（12.7m）。**B 单独不足以修断层** |
| 紧凑度 | 略降 | 锋线压回使块变短 |
| 宽度 | 不变 | 只动 x |

#### B.4 预期副作用

- **⚠️ 最大风险：越位线是"对方"的隐含函数，会引入正反馈。**
  我的锋线压低 → 对方防线可以放心前压（防线也参考球/我） → 我的锋线进一步被压 → …
  真实足球里这个反馈**由越位规则本身终止**（防线不敢越过球太远，否则身后空当被反越位）。
  引擎里**没有越位判罚**，所以必须显式给出"防线不得越过球"的下界——
  现存的 `tx_full.min(ball.0).max(base.0)` 恰好是它。**不要把这条 clamp 一起删掉。**
- **会被"摆大巴"式反馈放大**：如果对方全线退到禁区，我方锋线被压到中场，
  可能产出一段比赛里两队 20 人全部挤在半场。真实比赛这会导致反击空间。**需要实测。**
- **影响射门机会**：锋线被压低 → `nearest_teammate` 的接球点更靠后 → 推进链变长 →
  射门数可能下降。这是**必须实测**的副作用（P29 的射门 hazard 对几何敏感）。
- **`offside_line` 每 tick 被 22 人各调一次** → 需要缓存（见 B.6）。

#### B.5 hack 自评

**低到中**。它不是我"想调这个数字所以加这个机制"——我是**先发现真实数据里这把耦合存在
（R²=0.20 / lag r=0.43）**，再把它加进引擎。即使 P36 的指标全部不存在，
"进攻线受对方防线约束"也是足球规则（越位）的直接后果，是对的。

**但必须诚实标注两个泄漏**：
1. `OFFSIDE_MARGIN` 的取值我会看着"真实越位余量中位 +1.5m"来定。这**是**拟合。
   辩护：越位余量有明确的规则语义（越位即犯规），量级由"盯线但不越线"决定，
   不是自由参数。但仍应在 design 里记为**标定量**并把它的敏感性跑出来。
2. **我还没有验证"引擎里加了这个耦合之后，它真的会带来真实侧那种 R²"**——
   我只能验证真实数据里有这个规律，不能验证引擎实现后能复现。这需要实现后回归。

#### B.6 实现代价

- 新增 `offside_line`（~15 行，含缓存）、`apply_offside_cap`（~10 行）、1 个常数。
- 改 `formation_target`：末尾加 `tx = apply_offside_cap(st, id, tx)`。
- **新增状态**：`offside_line` 的每 tick 缓存（`Option<(u32, f64, f64)>`——按 team 存），
  否则 22 人 × 每 tick 一次排序 = O(22·n log n)，虽然 n=10 可忽略，但洁癖上该缓存。
  **或者**：在 `tick` 开头算一次、存进 `MatchState` 两个字段。这是本方案唯一的**新状态**。
- 改动面比 A 小得多（A 要重排第一遍循环，B 只是末尾加一行）。

### 方案 C：块级弹性（球员↔全队整体）—— 用"整体平移"替代"逐线随球"

#### C.1 机制

**改什么**：把现在**按线分别响应球位**的写法（防线有 `DEFENSE_PUSH_FACTOR=0.12` 的 push，
其他人没有），换成**整队共享一个"块高度"**变量，所有球员的目标 = 块高度 + 各自在块内的相对档位。

```rust
/// 本队块中心的高度（归一化 x），随球位平移。
/// g = 平移增益（实测真实 ≈ 0.59），own_goal_x 是本方门线。
fn block_center(st: &MatchState, team: u32) -> f64;

/// 块内相对档位：把 [0,1] 的 10 个档位映射到该球员的角色档。
fn block_slot(id: i32) -> f64;
```

**足球语言**：真实球队的纵深结构近似**刚体平移**——球在前场，整条块往前挪；球回后场，
整块往回挪，**块内的相对形状大体不变**（只是线间距被压缩/放宽）。

**数据支持**（`probeC`）：真实的"块中心 ~ 球位"回归斜率 = **0.589**（r=0.861），
而"块内跨度 ~ 块中心"斜率只有 0.153（r=0.319）——**平移是主项，伸缩是次项**。
引擎是 0.200 与 −0.393：**平移只有真实的三分之一，且伸缩是负的**（块越高反而越扁，方向反了）。

#### C.2 为什么符合足球规律

真实球队的移动是**整体块移动**：教练说的是"防线压上 10 米、中场跟 10 米、锋线跟 10 米"，
即整个块平移；而不是"防线压上 20 米、中场不动、锋线不动"。后者是引擎现在的行为
（只有防线有 push 项），它把块**撕开**——这正是 §1.2 那个 21m 断层的动力学来源。

#### C.3 预期指标效果

| 指标 | 预期 | 为什么 |
|---|---|---|
| **弹性** | 23.9/31.6 → **~10m** ✅✅ | 弹性的定义就是"纵深随球位的跨度"。块是刚体，球移动时纵深**几乎不变** |
| 纵深 | 略降 | 块内跨度由档位决定，不由球位决定 |
| 重心间距 | 略降 | 两队都整体平移，相对位置由"谁控球"决定 |
| 相邻次序间距 | **断层搬家** ⚠️ | 平移是仿射变换，保留线结构（§1.3 的 M1 实测：断层 11.5m） |
| 紧凑度 | 略降 | |

#### C.4 预期副作用

- **`DEFENSE_PUSH_FACTOR` 与 `PRESS_UP_OFFSET` 的角色被吞并**——需要确认删掉它们后
  原有的方向性单测（`p5` 系列）如何迁移。这是**白盒测试的破坏性改动**。
- **块尾（防线）与球的关系需要重新定义**：现在防线被 `min(ball).max(base)` 双向 clamp，
  这是 P7 观感补丁。改成块模型后，块的**下界**由什么定？建议保留 clamp 作为块的**下界约束**，
  但这会让"块"不是刚体——需要明确取舍。
- **球在对方半场时块压得太高**：g=0.59 意味着球在对方禁区时块中心推到 ~0.6+
  加上块深一半 → 前锋顶到 0.9（现在的 clamp 上限）。**真实的 g=0.59 是在真实块深
  （32m）下测的**；若块深仍是 46m，同样 g 会让前锋冲出门线。**A 必须先于 C。**

#### C.5 hack 自评

**中**。`g=0.59` 是从真实数据回归出来的**系数**——虽然它有足球语义（"全队跟着球移动的比例"），
但取值本身是拟合。好在它是一个**有量纲意义**的量（不是自由参数），且
**只靠 C 会让断层搬家**（§1.3 已证），所以它**不可能被单独用来调数字**——
这反而是它的清白证明：它不是一条"调绿指标"的捷径。
如果真实数据没测过弹性，C 还会是对的吗？**会**——"全队整体平移"是足球的基本事实
（转播镜头里最直观的一件事），不依赖任何指标。

#### C.6 实现代价

- 新增 `block_center`（~10 行）、`block_slot`（~10 行）、1 个常数。
- 改 `formation_target`：删掉 `is_defender` 分支里的独立 push，改为共享块中心。
- **需要新状态**：无（块中心由球位算出）。
- **破坏面最大**：`is_defender` / `DEFENSE_PUSH_FACTOR` / `home_defenders` /
  `away_defenders` 的角色会大幅弱化，牵动 P5 的多个单测。
  **这一条是最贵的**——需要把"防线"从角色概念改成次序概念，与 A 的方向一致。

## 3. 三个方案的关系：它们**必须组合**，且顺序固定

这是本轮最重要的设计判断，也是 `probeJ` 直接逼出来的：

```
C（块平移） —— 负责【弹性】：让纵深不随球剧烈伸缩
   ↓ 但 C 单独做：断层从 8→9 搬到 4→5，仍是 11.5m（仿射变换保留线结构）
A（深度链） —— 负责【消除断层】：让 9 个间距落在 4–6m，纵深自然落到 26–29m
   ↓ 但 A 单独做：链锚在块尾，块尾位置仍由球的 clamp 决定 → 整条链被拖到错高度
B（越位锚定）—— 负责【重心间距 + 弹性上限】：让锋线跟对方的防线，而不是跟球
```

**推荐实施顺序：A → C → B**，每一步都有独立可验收的结构判据：

| 步骤 | 结构判据（真实值） | 预期 |
|---|---|---|
| 现状 | 断层 19.1m / 纵深 40.4 / g=0.18 | — |
| +A | **断层 ≤ 6m**（真实 5.3） | 最重要的单步 |
| +C | **g ≈ 0.59**（真实 0.596）、弹性 ≤ 12m | 弹性归位 |
| +B | **越位余量中位 ≈ +1.5m**（真实） | 队际耦合 |

**任何一步都不能只看"四项指标全绿"**——§1.3 的 M1 已经演示了四项全绿而断层 11.5m 的反例。
