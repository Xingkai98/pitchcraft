# P38 队形真实度：方案设计（甲）

> 独立设计，未与方案乙互通。所有数字由本文件作者**自己跑探针复现**（探针源码与原始输出见 §9），
> 未照抄任务书。与任务书数字有出入处已在 §2 显式标出。
> 状态：设计稿，未实现。落盘时间 2026-09-19。

---

## 1. 摘要

引擎与真实的差距不是一个数字，是**四类独立的机制缺陷**叠加。我把它们分开之后，三条候选
路线各自对应其中一类，且三者的**状态变量不同**（对手 / 球 / 自身支撑结构），因此不是同一
想法的变体：

| 方案 | 状态变量 | 一句话 | 主要修哪类缺陷 |
|---|---|---|---|
| **甲 1** 越位线 + 对偶盯人 | **对手的位置** | 后防线的高度由对方最前的人决定，不由模板决定 | D：防线与对手解耦 |
| **甲 2** 球锚定块 | **球的位置** | 角色只决定「在块里的次序」，位置由块算；块由球锚定 | A+B：模板断层 + 无球侧压缩 |
| **甲 3** 覆盖链（去线化） | **队友之间的距离** | 不建模「线」，建模「覆盖链」：每个人的位置是链上前一人的偏移 | B+C：平行线刚性与间距结构 |

三者都**不**拟合静态常数：改的是「位置从哪里算出来」，不是「把坐标乘一个系数」。
判别三者的可证伪实验见 §7。

## 2. 探针复现：确认了什么、修正了什么

### 2.1 确认（与任务书一致）

`probe2-order-stats.mjs` 逐位复现任务书的相邻次序间距：

```
真实  2.9 / 3.0 / 3.3 / 4.1 / 3.2 / 3.4 / 3.5 / 5.2 / 3.9   （均匀）
引擎  3.3 / 1.2 / 4.7 / 19.2 / 4.1 / 2.8 / 2.1 / 6.3 / 6.0   （第 4→5 处断裂 19.2m）
```

`probe3-clamp-hypothesis.mjs` 确认锋线不回防（球 x∈[0,11)m：真实前 2 人 39.3m / 引擎 51.3m）
与弹性过大（纵深随球跨度 真实 10.3m / 引擎 31.6m）。

### 2.2 修正（任务书的表述需要改）

**修正 ①：「断层就是模板间隙」不成立。** 任务书推测 19.2m 的断层来自 `default_lineup`
的 0.20 模板间隙（≈21m）。实测不是：模板基线 0.175（=18.4m），但引擎后 4 人的**实测**均值是
25.5m（`probe2` 分块），已被 `press + push` 抬高；若断层就是模板间隙，它应当 ≈25.7m 而不是
19.2m。真实机制是：**次序 1–4 被 push 抬高、次序 5 由模板 0.42 定住，断层 = 两者之差**。
数字偶然接近，因果不同。这一点很重要——按「缩小模板间隙」去改，会改错地方。

**修正 ②：引擎的纵深不是「后防太深」，是「中场到处跑」。** `probe12` 的窗内逐 id 标准差：

| | x 方向 sd | y 方向 sd |
|---|---|---|
| 真实 | 18.9m | 10.7m |
| 引擎 | 17.1m | **4.6m** |
| 比值 | 1.11× | **2.34×** |

引擎球员**沿场地长度的移动量基本正确**（差 11%），横向前后差 2.3 倍。再看逐槽位：

```
真实  16.5/17.4/18.7/19.7 / 20.0/20.8/21.2/21.3 / 19.7/19.2   （各槽位接近）
引擎   9.8/10.3/10.2/10.4 / 24.6/23.2/22.2/21.9 / 20.0/17.5   （后防 10m，中场 24m）
```

**引擎的后防移动量只有真实的一半，纵深却更大——靠的是中场两倍于常态的纵向摆幅撑出来的。**
（`probe5` B：引擎 id 5–8 的 x p95 = 102.9m，即中场的 5% 的帧已经跑到对方门线上。）

**修正 ③：真实队的纵向分布是「近似均匀带单调增长」，不是「均匀」。**
真实相邻间距 2.9→5.2m 是**单调递增**的（后场密、前场疏），不是常数。方案甲 3 必须模拟这个
梯度，不能做成等距。

**修正 ④：任务书说「引擎没有球队整体压缩」。** 准确说：引擎没有**压缩**，但有一个弱得多的
**整体平移**（`SIDE_SHIFT_FACTOR` 同时作用于 x，见下）。真实的块中心 vs 球位斜率是
**0.596**（`probe9` B），引擎是 0.458——两者的「整体跟随球」其实接近，差的不是整体跟随，
是**块的长度**和**横向**。

### 2.3 我这一轮新测出的四条（任务书未提，且是设计的关键依据）

**新证据 A：真实的防线高度主要由「对方在哪」决定，引擎主要由「球在哪」决定。**

`probe11` 做偏回归（控制球位后看对方锋线的增量解释力）：

| | M0: 后4 ~ 球位 | M1: 后4 ~ 球位 + 对方前2 | 增量 R² | 偏相关 |
|---|---|---|---|---|
| 真实 | β=0.542, R²=0.731 | **β_球=0.115**, β_对方=−0.770 | **0.193** | −0.848 |
| 引擎 | β=0.261, R²=0.764 | **β_球=0.191**, β_对方=−0.154 | 0.032 | −0.368 |

真实：一旦知道对方在哪，球位几乎不再提供信息（β 从 0.542 掉到 0.115）。引擎：球位解释力
基本不动（0.261→0.191），对方只贡献 3% 的额外 R²。**这是两套模型最本质的差别。**

反面证据（我做了但**不能作为依据**）：我把「对方前 2」替换成「对方全队重心」作安慰剂对照，
真实侧增量 R² = 0.188，几乎一样（0.193）。说明这份数据**无法区分**「盯住对方的锋线」与
「跟着对方的整条块走」——两者高度共线。所以「越位线」是**足球法理上的机制解释**，
**不是**这个探针能单独证明的事实。见 §8 不确定清单。

**新证据 B：真实的覆盖链是单调放大的，引擎的链在防线→中场处断裂。**
`probe6` (b)，从本方最深的外场出发逐个跳到最近的未访问队友，链节长度（米）：

```
真实  10.8 / 10.6 / 10.4 / 10.9 / 12.0 / 13.0 / 14.1 / 17.1 / 20.0   ← 单调
引擎   6.4 / 10.0 / 16.8 / 23.1 / 10.2 / 11.5 / 12.6 / 15.3 / 19.9   ← 非单调，23.1 处断裂
```

**「线」是引擎的异常，不是真实的结构。** 这是甲 3 的核心依据。

**新证据 C：重开几何贡献了引擎约 4.3m 的纵深，对真实零贡献。**
`probe10`：剔除「某队 ≥4 人位于对方最后 10m」的帧后，引擎 41.2m → 36.9m（−4.3m），
真实 26.4m → 26.5m（±0.1m）。引擎每 5400s 仅 ~3 次角球，但角球准备期把 5 名进攻方
球员放到 x∈[0.92,0.98]（`corner_setup_target` 的 `zone_x1=0.98`），一帧就把纵深拉到 90m+。
**这是纯几何噪声，不是足球行为**（真实的角球包抄同样极端，但真实数据里它被平均掉了；
引擎里它占比过高，因为引擎的开放比赛纵深本来就大、角球又集中）。

**新证据 D（口径）**：`probe10` 里「主队最前者 x 分位」：p90 = 0.97 → 95.6m。这**超出**
`formation_target` 的 `clamp(0.04, 0.9)`（=94.5m），说明引擎的深度尾巴有一部分来自
**非队形目标**（carrier 带球推进、`corner_setup_target`、`close_down` 追球）。
即：纵深的一部分不由队形产生，由**持球者与重开**产生。任何只改 `formation_target` 的方案
都会留下这条尾巴（见 §6）。

### 2.4 「拟合数字」的实物对照（A/B 实测，`probe13`）

工作树里恰好出现了一个**纯粹的拟合式改动**（另一个进程改的 `default_lineup`：三条线的 x
全部按比例压缩）。我把它编译成独立 wasm（**没有覆盖 `viewer/engine.wasm`**），跑同一套
探针做 A/B。这是把「hack 反例」从思想实验变成**实测**的机会：

| | 真实 | 基线 | 模板压缩 | 相对真实的偏差（基线 → 压缩） |
|---|---|---|---|---|
| 纵深（主） | 25.9 | 41.9 | **21.2** | +15.9 → **−4.7**（改善） |
| 紧凑度 | 15.4 | 20.1 | **13.6** | +4.7 → **−1.8**（改善） |
| 宽度（主） | 39.6 | 32.4 | **41.0** | −7.2 → **+1.4**（改善） |
| 重心间距 | 8.3 | 14.5 | **25.7** | +6.1 → **+17.4（恶化 3 倍）** |
| 弹性 Δ | 4.7 | 13.3 | **−1.3** | +8.6 → **−6.0（过冲，符号翻反）** |

总绝对偏差 42.5 → 31.2（改善 26.5%）。**五项里三项明显改善。**

**我原以为「压缩模板一定不改善宽度」——实测推翻了：宽度从 32.4 改善到 41.0，几乎正中真实。**
（原因：真实模板下后防的 `DEFENSE_PUSH_FACTOR` 把后 4 压得很低，压制了宽度；
抬高模板基准后后防整体前移，宽度随之打开。这是我没预见的耦合。）
**我为这个错误预判记一笔——它说明「不加实测就下判断」在本题上不可靠，包括我的判断。**

真正证伪它的不是均值，是**结构**：

```
相邻次序间距（米）
真实          2.9  3.0  3.3  4.1  3.2  3.4  3.5  5.2  3.9
基线          3.3  1.2  4.7 19.2  4.1  2.8  2.1  6.3  6.0   ← 断层在 4→5
模板压缩      2.1  0.1  1.4  0.7  0.7  1.3  3.2 13.3  2.3   ← 断层搬到 8→9
```

**19.2m 的断层没有被消除，它从 4→5 搬到了 8→9**——正是 §2.2 修正① 预测的
「只会整体平移」。同时：

```
纵深随球位（m）   球位 5    16    26    37    47    58    68    79    89   100
真实           23.2  21.8  24.3  23.9  24.8  24.9  25.9  27.8  30.4  34.1   ← 单调升
模板压缩        22.0  20.9  23.2  22.6  21.7  20.6  21.0  21.6  15.6  15.9   ← 攻到前场反而塌了
```

真实球队**压上进攻时纵深变大**（30.4/34.1），压缩后的引擎**反而塌到 15.6/15.9**——方向反了。
`重心间距` 从 14.5 涨到 25.7（真实 8.3）的机制很清楚：home 模板压在 x∈[0.24,0.52]（中心 0.38）、
away 镜像在 [0.48,0.76]（中心 0.62），两个**块心**被推到相距 0.24×105 ≈ 25m——
比原来还远。**把队形压扁，等于把两队推开。**

**这就是「拟合数字」的完整病理**：均值能对上（3/5 项改善、总偏差降 26.5%），
但 ①结构缺陷只是搬家 ②一个关键量恶化 3 倍 ③比赛状态依赖的行为方向反了。
**任何只对均值的验收都会把这个改动判为「成功」。** 这是本设计 §11.2 要求
「验收必须是结构性的」的直接实证依据。

## 4. 方案甲 1：越位线 + 对偶盯人（对手驱动）

### 4.1 机制

把「后防线的高度」这一唯一决定变量，从**模板基准**换成**越位线**。

```rust
/// 越位线（在 home 的「攻向 x=1」坐标下，离本方门线的距离占比）。
/// 定义 = 对方第 2 靠后的外场球员所在的 x —— 这就是越位规则本身。
fn offside_line_own(st: &MatchState, home: bool) -> f64

/// 防线的退防量：球越深，整条线越退（真实 4.1m 的 gain，见上表）
fn line_drop_from_ball(st: &MatchState, home: bool) -> f64
```

`formation_target` 里 `is_defender` 分支改为：

```rust
let offside = offside_line_own(st, home);           // 越位线（我方可到的最高位置）
let drop    = line_drop_from_ball(st, home);        // 球深 → 退
let base_x  = (offside - OFF_LINE_GAP - drop).clamp(REAR_FLOOR, offside);
tx = base_x;   // 不再是 base.0 + 一堆偏移
```

同时**中场与锋线的纵深上限也锚到同一条线**（`tx.min(offside + band_i)`），
这样「整队随越位线压扁/拉开」是同一个自由度，而不是后防单独动。

### 4.2 足球依据

越位规则**就是**「防守方的最后一条线由上：对方第 2 后队员的位置决定」。整条后防横移保持
平齐（"holding the line"）是每一种现代防守训练的科目，因为任何一个人掉队就制造出反越位的
缺口。这是**比赛规则**，不是观感偏好——所以它不依赖「真实数据是否量过这个指标」。

### 4.3 预期指标效果

| 指标 | 方向 | 为什么 |
|---|---|---|
| 纵深 | **↓↓**（41.9 → 大概率 30m 附近） | 防线上限被对方锋线钉住，块长不再由模板决定 |
| 重心间距 | **↓** | 两队同时被同一条线约束 → 两队重心互相牵引 |
| 紧凑度 | ↓ | 同上的次生效果 |
| 宽度 | 基本不变 | 这是 x 方向机制 |
| 弹性 | **↓↓** | 越位线自身随球移动，防线不再是 `0.12×球位` 的独立振荡器 |
| 4→5 断层 | **↓↓** | 后 4 被拉到越位线，模板间隙不再是决定项 |

### 4.4 副作用（严重，必须直视）

1. **系统可能没有不动点。** `probe9` (D) 我把「防线 = 对方锋线 + 偏移」写成迭代映射跑了一下：
   每步增益 = `对方块长 + OFF + OFF_opp`。当块长 > 偏移时增益 > 0，我方退 → 对方进 → 我方再退，
   单调推到边界（我的简化模型 30 → 53 → 76 → 95 → 95 …）。**必须有界**：下限（`REAR_FLOOR`，
   建议 16.5m = 禁区线外沿）与上限（球位）。没有这两个约束，改完会比现在更糟。
2. **会改变** `second_nearest_defender_m` **→ 直接进射门几何**。这是 L3 硬门所在的量
   （记忆：`p34-swept-separation-tradeoff`：detector 归零需拍内扫掠，但 carrier 必须豁免，
   否则破 L3 射门几何）。让防线整条随对手上下，会系统性改变「carrier 到最近防守者」的分布。
3. **引擎没有越位规则。** 把防线钉在越位线上，在**没有越位判罚**的引擎里语义是「后卫自动
   退到对方最前的人之前」——这会让反越位直塞（现在能成功）变成不可能，传球/射门分布会变。
   这是**模型语义**的变化，不只是几何。

### 4.5 hack 自评：低（但有代价）

机制本身是比赛规则，不是拟合。若真实数据没测过「后 4 vs 对方前 2」这个指标，它**仍然**是
对的——因为它能对着《足球竞赛规则》第 11 条验，而不是对着数字验。
**但是**：`OFF_LINE_GAP`、`REAR_FLOOR`、`band_i` 这些常数是在拟合「贴线多近」，
这一层是拟合；而且 §2.3 的证据 A 无法把「越位线」与「跟整条对方块」分开。
诚实结论：**机制合法，参数拟合，且机制本身在这份数据上不可证伪**。

### 4.6 实现代价

- 新函数 2 个（`offside_line_own` / `line_drop_from_ball`），`formation_target` 的 defensive 分支重写。
- 新常数 3–5 个（`OFF_LINE_GAP` / `REAR_FLOOR` / `LINE_DROP_GAIN` / 各线 `band_i`）。
- **不需要新状态**：`formation_target(st, id)` 已经拿得到全场位置。
- `is_defender` / `home_defenders` 保留（本方案仍需要角色分组）。
- 风险等级：**高**（改的是两队耦合的自由度，且触碰射门几何）。

## 5. 方案甲 2：球锚定块（球驱动）

### 5.1 机制

把 `base`（模板坐标）**降级为纯次序信息**，位置由「块」算：

```rust
/// 球队块的纵向边界（离本方门线，归一化）。
/// 块中心 ~ 球位（实测真实斜率 0.596，偏回归后 0.115——本方案取中间，见下）
fn block_bounds(st: &MatchState, home: bool) -> (f64, f64) {
    let ball_own = if home { st.ball_pos.0 } else { 1.0 - st.ball_pos.0 };
    let phase = phase_of(st, home);        // +1 控球 / 0 争夺 / -1 丢球（transition 加强）
    let centre = BALL_ANCHOR_C + BALL_ANCHOR_K * ball_own + PHASE_OFFSET * phase;
    let band   = BAND_BASE + BAND_OPEN * phase.max(0.0) + BAND_CLOSE * (-phase).max(0.0);
    ((centre - band * 0.5).clamp(REAR_FLOOR, 0.9), band)
}

/// 角色 → 块内的相对深度 s ∈ [0,1]（0 = 最后，1 = 最前）。
/// **软曲线**（后场密、前场疏，复现实测的 2.9→5.2m 单调放大），不是四段台阶。
fn rank_schedule(id: i32) -> f64
```

```rust
// formation_target 主体
let (rear, band) = block_bounds(st, home);
let s = rank_schedule(id);
let tx = rear + band * s;                     // 纵向：在块内的位置
let lane = st.ball_pos.1 + (base.1 - 0.5) * FAR_SIDE_SPAN;   // 横向：围绕球的走廊
let ty = lane.clamp(st.ball_pos.1 - SIDE_CAP, st.ball_pos.1 + SIDE_CAP);
```

**关键**：`tx` 里没有 `base.0`。模板只通过 `rank_schedule`（次序）进入。

### 5.2 足球依据

「围绕球收拢、远端保持宽度」是防守组织的第一性原理（ball-oriented compactness）。
它单独解释了这组看似矛盾的数字：

| | 到最近队友 | <2.2m 占比 | 全队宽度 |
|---|---|---|---|
| 真实 | 9.8m | 4.7% | 39.6m |
| 引擎 | 8.9m | **2.9%** | 32.4m |

真实队**整体更宽**（39.6 > 32.4），但**局部更不挤**（<2.2m 只有 4.7%）。这两件事同一个原因：
真实球员在**离球远处散开、离球近处收拢**；引擎是均匀铺开的四条平行线，所以又窄又挤。
真实 \|Δy\|/\|Δx\| = 0.77 vs 引擎 0.36——**引擎的横向运动量只有真实的一半**，
这也是引擎「宽度不够」的动力学解释，而不是「模板 y 值不够大」。

### 5.3 预期指标效果

| 指标 | 方向 | 为什么 |
|---|---|---|
| 纵深 | **↓↓** | `band` 是有界自由变量，不再由 0.20 的模板间隙决定 |
| 宽度 | **↑**（32.4 → 36-40m） | `FAR_SIDE_SPAN` + `SIDE_CAP` 让远端随球走廊张开；**这是唯一与「纵深变窄」同向正确的方案** |
| 紧凑度 | ↓ | 横向有序化（球侧密、远端疏）会降低平均到重心距离 |
| 重心间距 | ↓ | 两队 block 都由同一个球位锚定，中心自然靠拢 |
| 弹性 | **↓↓** | 真实的弹性来自**相位**（攻/守切换块长），引擎的来自**球位**（clamp 伪影）。本方案把相位项显式化、把球位项降为块中心平移（块长不变），纵深对球位的一阶依赖消失 |
| 4→5 断层 | **↓↓** | 不存在「线」了 |

### 5.4 副作用

1. **局部过挤 → 二次分离放大。** 引擎已有同队 ≥2.2m 的分离约束（P34 `separate_pair_m`），
   且 <2.2m 触发率 2.9%。若球侧收拢过头，`separate_pair_m` 会在每个 tick 推开大量配对，
   把「收拢」中和掉，还会通过 `commit_beat_positions` 的扫掠侧推污染射门几何。
   **必须先量触发率，再定 `SIDE_CAP`。**
2. **传球网络改变。** `nearest_teammate` 决定传球目标；块压缩会缩短平均传球距离 →
   `open_play_pass_risk` 下降 → 传球成功率上升、出界率下降、`out_channel_hits` 下降。
   这是可观测的、必须回归的。
3. **横向位移增大 → 移速上限成为约束。** `probe12` 显示引擎横向 sd 只有 4.6m；本方案要把
   它推向 10m 量级，意味着球员横向目标变化更快。`RUN_SPEED_MS = 4.0` 与
   `DEAD_ZONE_METERS = 2.0`（死区）会成为限制——**可能改了机制却看不到效果**，
   因为死区把目标微动全部吃掉。这是实现期的第一风险。

### 5.5 hack 自评：低

机制是「位置从球算，不从身份算」，可用**与均值无关的结构预测**证伪：
① 相邻次序间距应变成单调递增（当前是 4→5 断层）；② 宽度与局部拥挤度应**同时**朝
真实方向走（任何单一缩放在这两项上方向必然相反）。
`BALL_ANCHOR_K` 是拟合量，但有非拟合的约束：球的传递速度远大于球员跑速，所以长期
平均的团队位移必然小于球位移，K < 1 有物理理由。若真实数据没测过「块长随球位」，
本方案**仍然**对——因为「防守时收紧、进攻时展开」是教练共识，可查。

### 5.6 实现代价

- 重写 `formation_target`（~30 行 → ~45 行）；新函数 3 个（`block_bounds` / `rank_schedule` / `phase_of`）。
- 新常数 7 个左右（`BALL_ANCHOR_C/K` / `PHASE_OFFSET` / `BAND_BASE/OPEN/CLOSE` /
  `FAR_SIDE_SPAN` / `SIDE_CAP` / `REAR_FLOOR`）。**这是三个方案里常数最多的**，
  也是它最需要「不许调参拟合」的纪律。
- **不需要新状态**（`possession` / `transition` / `ball_pos` 都已存在）。
- `is_defender` / `home_defenders` 退化为死代码（唯一调用点就是 `formation_target`，
  grep 已确认）——**应当一并删除**，否则留下一个「还能判防线」的陷阱。
- 风险等级：**中**（改面大但局部；主要风险是分离约束与死区的交互）。

## 6. 方案甲 3：覆盖链（去线化，自身驱动）

### 6.1 机制：先质疑「用线建模队形」这件事

`probe6` 的链节长度是最直接的证据：真实的覆盖链**单调放大**（10.8→20.0m），
引擎的是 `6.4 / 10.0 / 16.8 / 23.1 / 10.2 / …`——**先在防线内部裂开 23.1m，再缩回 10.2m**。
「四条平行线」这个建模本身制造了这个双峰结构：线内 2-4m（因为同一条线的 y 间距 8-9m，
x 几乎相同），线间 19-25m。真实的 10 个非门将**是一串链**，不是四排点。

模型改为「一条骨架 + 球的形变」：

```rust
/// 覆盖链骨架：链上第 i 人相对链首的（纵向累计偏移, 横向偏移），开局算一次、全场不变。
/// 次序 = 4 后卫 / 4 中场 / 2 前锋，但**纵向偏移是单调递增的软曲线**，不是四段台阶。
/// 横向偏移按「蛇形」排布（后卫线内 y 依次 0.2/0.4/0.6/0.8 …），保证链上相邻者既换 y 也换 x。
fn chain_skeleton() -> [(f64, f64); 10]

/// 每个链节对球的**支撑增益**：越靠后的链节越不跟球（保持越位线），越靠前越跟球。
fn support_gain(i: usize) -> f64
```

```rust
// formation_target 主体
let (dx_i, dy_i) = CHAIN_SKELETON[i];
let anchor = if home { 0.02 } else { 0.98 };          // 链首贴本方门线
let pull = support_gain(i) * (st.ball_pos.0 - anchor);
tx = anchor + dx_i + pull + attack_dir * press;
ty = CHAIN_ANCHOR_Y.y + dy_i + (st.ball_pos.1 - 0.5) * SIDE_SHIFT_FACTOR * gain(i);
```

链首（最深的后卫）**保持在本方门线附近不跟球**，链尾（前锋）跟球最多——
`support_gain` 的单调性直接复现「防线少动、锋线多动」这个实测事实
（`probe12`：真实后防 x sd 16.5–19.7 vs 引擎 9.8–10.4；中场真实 20.0–21.3 vs 引擎 24.6）。

### 6.2 足球依据

球员之间的**覆盖关系**（"cover / balance / support distance"）是防守站位的基本组织原则：
每个球员的站位由他与最近队友的距离和角度决定（"one man covers, one man balances"）。
真实数据三条一致：① 覆盖链单调放大；② 到最近队友 9.8m、到最近第 2 人 13.3m、
到最近第 3 人 16.2m —— **有序的支撑梯度**，不是「同线 8m / 跨线 25m」的双峰；
③ 到球的最近防守者 5.2m（真实）vs 3.0m（引擎）——真实保持**压迫距离**，
引擎贴得更紧。这些都不是「线的位置」能表达的，是**链上距离关系**。

### 6.3 预期指标效果

| 指标 | 方向 | 为什么 |
|---|---|---|
| 纵深 | **↓↓**（最大幅度） | 链的纵向累计偏移直接可控；引擎当前 49.5m 全跨度 → 目标 32.5m |
| 4→5 断层 | **消失** | 结构上不存在断层（骨架单调） |
| 紧凑度 | ↓↓ | 支撑梯度取代双峰 |
| 重心间距 | ↓ | 同上（两队都用同一骨架） |
| 宽度 | ↑ | 蛇形骨架 y 跨度 + 全局侧移 |
| 弹性 | ↓ | 只有链尾的 `support_gain` 大，整队纵深随球的摆幅自然变小 |

### 6.4 副作用（最大）

1. **改的是全队 10 人的位置生成方式**，影响面覆盖所有依赖位置的下游：
   `nearest_defender`（射门/传球拦截）、`second_nearest_defender_m`（射门质量）、
   `nearest_teammate`（传球网络）、`pick_close_down_players`（逼抢选择）、
   `attacking_forward`（转换前插）。**几乎所有 event-stream 行为都会漂移。**
2. **蛇形骨架的 y 顺序是硬编码的阵型表达** —— 换阵型（4-3-3）时要重写骨架。
   这比甲 1/甲 2 更「写死」。
3. **链首钉在门线附近会与 `REAR_FLOOR` 冲突**：真实后防 x sd 16.5–19.7 意味着后防**也在动**，
   不是钉死的。骨架需要一个「后防整体平移」的自由度，否则会走到另一个极端
   （后防完全钉死 → 越位线不存在 → 长传身后球永远成功）。
4. 我的 `probe6` 链是**贪心最近邻**构造的，它本身带一个偏差：贪心链偏好短的下一步，
   因此**系统性地低估长链节**。真实链的 20.0m 尾节是贪心给的下界。用这个骨架去拟合
   会把「贪心的伪影」当成「真实的支撑梯度」。**这是本方案最大的方法学风险。**

### 6.5 hack 自评：中（取决于常数从哪来）

- 若 `chain_skeleton` 的纵向偏移是**从足球原则推出来的**（后场密前场疏 + 单位是
  「覆盖距离」而非「米」），则是机制，hack 程度低。
- 若把 `10.8/10.6/10.4/10.9/12.0/13.0/14.1/17.1/20.0` **直接抄进常数表**，那是纯拟合，
  而且拟合的是**贪心链的伪影**。**这条红线必须在实现前写进 spec 的禁止项。**
- 若真实数据没测过覆盖链，本方案**部分失效**——「单调放大」这个具体形状是我从这一次
  测量里得到的，没有独立的足球法理支撑它一定要单调（只能说「后场密前场疏」有共识）。

### 6.6 实现代价

- 最高。新函数 3 个（`chain_skeleton` / `support_gain` / 链全局平移项）；
  `formation_target` 全重写；`is_defender` / `home_defenders` 删除。
- 骨架可在 `MatchState::new` 算一次（**不需要每 tick 新状态**，但需要一个
  `chain_anchor: f64` 之类的全局平移量——若做成状态，就要处理它与 `lineup` 事件的
  一致性，避免开局瞬移）。
- 新常数 5–8 个，但**结构性常数**（骨架形状）与**可调常数**（增益）应当分开放在
  不同位置，让审阅能一眼看出哪些是「阵型定义」哪些是「参数」。
- 风险等级：**最高**（改全队位置生成 + 与分离约束/死区/射速上限的三重交互）。

## 7. 三方案的判别实验（先做这个，再决定实现哪个）

三个方案对**同一个可观测量**给出**不同的预测**。先花一次实验把这三点测出来，比先实现更省：

| 实验 | 甲 1 预测 | 甲 2 预测 | 甲 3 预测 | 怎么测 |
|---|---|---|---|---|
| **控制球位后，防线高度对「对方锋线」的偏相关** | 升到 ≈ −0.85（对齐真实） | 变化不大（仍以球为主） | 略升 | `probe11` 的回归，换引擎 |
| **块长（全跨度）随球位的单调性** | 改善但非单调 | **单调**（块长只由相位定） | 改善但非单调 | `probe9` B 的分箱 |
| **横向 sd（逐 id 窗内）** | 不变（4.6m） | **升到 8-10m** | 升到 8-10m | `probe12` 的逐 id |
| **覆盖链的单调性** | 仍非单调 | 仍非单调 | **单调** | `probe6` 的链节 |
| **分离约束触发率（<2.2m）** | 不变 | **升**（这是甲 2 的主要风险） | 升 | `probe9` C |

**结论性的判别量是第 1 行**：甲 1 是唯一会改变「防线↔对手」耦合的机制。
若第 1 行的偏相关修不上去，说明「对手耦合」不是纵深问题的主因，甲 1 应当被否。

## 8. 不确定的地方（明确写出）

1. **证据 A 的因果方向不明。** 偏相关 −0.848 说明「后防高度」与「对方锋线高度」强耦合，
   但**无法区分**：是防守方在盯越位线，还是**进攻方在压防守方**（前锋跟着后卫走）；
   还是两队都被第三个量（球/比赛状态）驱动。安慰剂对照（换成对方全队重心，增量 R² 0.188≈0.193）
   **削弱**了「越位线特异」的解释。我倾向「两队深度互相锁定」，但这不等于「越位线」。
2. **`probe11` 最后一个对照（随机配对间隙 = 1.6m 与真实配对完全相同）是坏的。**
   我的确定性伪随机配对 `(i*7919) % len` 因为 `cutWindows` 的窗结构而落在了邻近帧上，
   没有真正打乱。**该对照无效，不作为证据。**
3. **`probe6` 的贪心最近邻链有系统性偏差**（偏好短下一步，低估长链节）。真实的链节分布
   需要另一种构造（例如以「最小生成树」或「固定角色」的链）来交叉验证。甲 3 的骨架
   若直接抄这组数字，就是在拟合贪心伪影。
4. **真实侧只有 2 场（Metrica）**。所有「真实 vs 引擎」的回归系数都建立在这 2 场上。
   SkillCorner 20 场的基线显示纵深 18.3m（主口径）远低于 Metrica 的 25.9m——
   **两个真实数据集本身差 7.6m**。我把目标定在 Metrica 的 25.9m，但如果 SkillCorner
   更接近真相，则引擎需要压到更小，三方案的强度都要加大。**这个选择会改变所有常数。**
5. **我没验证「引擎中场为什么会跑到 x=0.98」。** `probe5` B 的 p95=102.9m 超出
   `formation_target` 的 `clamp(0.04, 0.9)`，一定是非队形路径（carrier 推进 /
   `corner_setup_target` 的 0.98 / `close_down`）。我用「≥4 人在对方最后 10m」近似
   分摊出 4.3m（`probe10`），但**没有逐路径归因**。若这条尾巴占比比 4.3m 大，
   所有方案的收益都会打折。
6. **`DEAD_ZONE_METERS = 2.0` 的影响未量化。** 甲 2/甲 3 都要增加横向目标变化，
   而 2m 死区会把小目标变化全部吃掉。我没有测「多少目标变化被死区吞掉」。
7. **弹性口径本身不稳**（`match-metrics.js` 头部已自陈：换重心口径后真实 −0.1m）。
   所以「弹性跨度 10.3 vs 31.6」这个数字本身对口径敏感，我在 §5.3 里用「纵深随球位的
   10 桶曲线单调性」替代它作为判据，更稳。
8. **不需要重生成基线。** `benchmark-baseline.json` 只含真实数据，其陈旧性校验绑定
   `match-metrics.js` 的 sha256——本 change 不动指标模块，基线保持有效。这是 P38 的
   有利条件：**改完立刻可对照**。

状态。复现时请先确认 `engine.wasm` 对应的源码版本。

这个并发改动恰好是本文要判定的**「hack 反例」的实物**，所以我在 §2.4 把它编译出来做了
A/B 对照。**结论部分推翻了我自己的预判**，见下。

### 复现口径（与 `match-metrics.js` 一致）

- 引擎：`BENCHMARK_SEEDS.slice(0,3)` × 5400s → `sampleEngineFrames`（0.2s）→ `cutWindows`
  （300s 窗 / 900s 步长）→ 27000 帧；真实：Metrica 2 场 → 19500 帧。
- 非门将 = `!KEEPER_IDS.includes(id)`；客队统一镜像到「攻向 x=1」坐标。
- 相位用 `possessionProxy`（**代理**，非真实持球权）；球相关量只用 `isRawBallFrame`。

### 正式口径下的头条（`probe8`，供 P38 验收对照）

| 指标 | 真实 Metrica | 引擎 | 差 |
|---|---|---|---|
| 纵深（主） | 25.9m | 41.9m | +16.0 |

## 10. 我建议的取舍（供对抗审阅挑战）

三方案不是互斥的，但**不应同时上**——每一条都会动射门几何与传球网络，叠加后无法归因。

- **若只做一个**：**甲 2**。它同时改善纵深与宽度（唯一方向正确的），常数虽多但都是
  「行为参数」而非「拟合数字」，且可用两条与均值无关的结构预测证伪（§5.5）。
- **甲 1 的风险最高**：它把两队耦合起来，而我在 §8.1 里已经说明这份数据**无法**证明
  耦合的因果方向。在没有更多真实数据（SkillCorner 20 场可提供）之前，我**不**建议先做甲 1。
- **甲 3 的建模质疑是对的**（链节证据很硬），但它的实现面最大、且骨架常数的来源有
  方法学风险（§8.3）。建议作为**第二步**：先用甲 2 把「块」建起来，再考虑是否把「块内的
  次序排布」换成链。
- **无论选哪个，`corner_setup_target` 的 `zone_x1 = 0.98` 都应当单独审视**（§2.3 C）：
  它贡献 4.3m 纵深且是纯几何噪声，且与队形机制无关。

## 11. 与 P38 spec 的接口建议

若本设计被采纳，spec 里应当固化（否则实现期必然漂移）：

1. **禁止项**：不得把实测的真实数字（10.8/10.6/… 或 0.596 斜率）直接写成常数；
   常数必须是**行为单位**（米、秒、比例），且每个常数在 spec 里写明「它模拟什么行为」。
2. **验收必须是结构性的**，不能只对均值：至少包含
   ① 相邻次序间距的单峰性/单调性；② 宽度与局部拥挤度**同时**朝真实方向；
   ③ 纵深随球位的 10 桶曲线单调。三条都是**与均值无关**的判据。
3. **零引擎改动原则不适用**（P36/P37 是标尺，P38 是引擎改动），
   但 `match-metrics.js` 必须**零改动**——任何为了让数字好看而改口径的行为都是 hack。
4. 判据用 **Metrica 25.9m 还是 SkillCorner 18.3m**（§8.4）必须在 spec 里拍板一次，
   否则实现者会来回试。
