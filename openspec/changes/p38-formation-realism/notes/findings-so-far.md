## 0. 一句话结论

引擎的队形问题**不是"太深"**，是**球员基本不动**——尤其是横向。而"把四项指标调绿"
已经被证明可以用一个常数做到，但结构全错。**四指标全绿 ≠ 修好了。**

## 1. 指标现状（干净 main，5 种子 × 6 窗）

| 指标 | 引擎 | 真实 Metrica | 真实 SkillCorner（主口径） | 结论 |
|---|---|---|---|---|
| 主队纵深 q10–q90 | 40.40 | 25.94 | 18.31 | 偏高 +56% / +121% |
| 紧凑度 | 18.65 | 15.24 | 12.76 | 偏高 +22% / +46% |
| 两队重心间距 | **23.53** | 8.32 | 5.24 | 偏高 **+183% / +349%** |
| 宽度（主队） | 40.85 | 39.58 | 35.96 | **落在范围内**（+3% / +14%） |

⚠️ **宽度不是问题**——早先"宽度偏窄 9.8%"的说法来自被污染的基线（见 §4），已作废。

## 2. 结构判据：引擎真正的病（这才是关键）

用**不在 P36 三项采用指标里**的结构量对比（真实 = Metrica，引擎 = 干净 main）：

| 结构量 | 真实 | 引擎 | 差距 |
|---|---|---|---|
| 最大相邻次序间距（断层） | **5.2m** | **19.2m** | 3.7 倍 |
| 断层出现在次序 | 8 | 8（另有 14.1m 在 4→5） | 引擎有**两个**洞 |
| 后防横向移动（y-sd） | **14.7m** | **0.6m** | **24 倍** |
| 后防纵向移动（x-sd） | 19.7m | ~5m | 4 倍 |
| 球在本方后场时最前一人 | 44.1m | 62.4m | 不回防 |
| 块跨度随球位 | 31.9→39.5（近平） | 47.0→54.9（整体偏大且更陡） | |

**相邻次序间距序列**（每帧 10 名非门将按纵深排序，相邻次序的平均间距）：

```
真实  2.9 / 3.0 / 3.3 / 4.1 / 3.2 / 3.4 / 3.5 / 5.2 / 3.9   ← 均匀
引擎  4.1 / 0.1 / 2.3 / 14.1 / 0.3 / 1.8 / 2.0 / 19.2 / 3.0   ← 两个大洞
```

**机制解释（已读代码确认）**：
- **横向**：`formation_target` 里 y 只有一项 `base.1 + (ball.1-0.5)*SIDE_SHIFT_FACTOR*0.6`，
  而 `SIDE_SHIFT_FACTOR=0.06` → 最大横向位移 **0.06×0.5×0.6 = 0.018 归一化 ≈ 1.2m**。
  即**引擎的横向移动在构造上就几乎不存在**——没有边路职责、没有套边、没有肋部跑动。
  这解释了 y-sd 0.6m 与真实 14.7m 的 24 倍差距，也是"不像真实足球"最可能的主因。
- **纵向**：后防线被双向 clamp（`tx_full.min(ball.0).max(base.0)`）钉住；
  模板本身后卫↔中场间隙 0.20≈21m。

## 3. hack 的机械判据（本轮最有价值的产出）

**实验：只改一个常数 `DEFENSE_PUSH_FACTOR` 0.12 → 0.45**

| | 纵深 | 紧凑度 | 重心距 | 宽度 | 判定 |
|---|---|---|---|---|---|
| 目标（Metrica） | 25.94 | 15.24 | 8.32 | 39.58 | |
| 该常数改动 | **25.34** ✅ | **14.29** ✅ | 9.95 ~ | **40.79** ✅ | **四项全绿** |

**若只看这四个数字，它会被判为成功。** 结构判据全部识破：

| 结构判据 | 真实 | 该改动 | |
|---|---|---|---|
| 断层 | 5.2m | **14.7m** | 没消失，**搬到了另一处** |
| 中场/后防移动比 | 1.08 | **0.35** | 后防被推得比中场还死 |
| 后防横向移动 | 14.7m | **1.0m** | 横向归零 |
| 锋线回防 | 44.1m | 49.8m | 仍不回防 |

**这是后面所有方案验收必须用的判据**：拟合均值的改动会让断层**搬家**而不是消失。

另一个反例（模板整体压缩，agent 甲实测）：五项里三项改善、总偏差降 26.5%，
但断层同样只是从 4→5 搬到 8→9，且弹性符号翻反。

## 4. ⚠️ 基线完整性问题（影响仓库对外数字，需单独跟进）

**冻结基线（`viewer/data/benchmark-baseline.json`）的引擎列不可从 main 复现。**

证据：
- 用 main 源码重建 wasm → `benchmark-compare` 报 gap 漂移 **+55.8%**、宽度 40.85
- 换成主仓库 `viewer/engine.wasm`（demo 分支构建的）→ 漂移 **+0.0%**，全部吻合
- `tools/benchmark-engine.mjs`（main）传 `off_ball_movement_demo: true`，
  但 **main 的 `engine/src/lib.rs` 里没有这个字段**（0 处），demo 分支工作树里有 37 处
- demo 分支工作树对 `engine/src/lib.rs` 有 **1145 行未提交改动**

**结论**：P37 基线生成时，worktree 的 `viewer/engine.wasm` 是从主仓库工作目录拷的，
而那里停在一个**未合入的 demo 分支**。所以 README/CLAUDE.md 里的引擎侧数字
（"重心间距 +82%/+189%"、"宽度 −9.8%"）来自一个未合入的分支。

**影响**：真实侧（Metrica/SkillCorner）数字不受影响；引擎侧目标数字需要重算。
任何校准目标都必须以**可从 main 复现**的基线为准。

**教训**：这正是 P37 自己立的"基线陈旧性哨兵"该抓的场景，但哨兵只校验
**指标模块**与**转换器源码**的哈希，**不校验引擎 wasm 的来源**。
