# Proposal: 体积重标定——把引擎从「压缩态标定」里放出来（#104）

## Why

引擎的**事件量级**是按「压缩态」标定的，而 L1 门是**按那个压缩态写的**。两件事互相锁死：

- **射门**：干净 main 普通射门 **7.755/场**，真实 **21.64/场**
  （StatsBomb Open Data **大五联赛子集 n=170**，mean 21.64 / sd 5.03，本票实测）。
  引擎只有真实的 **0.36×**。
  ⚠️ **锚点说明**：Metrica 2 场的 16.51 **不构成反驳**——主 session 复核（`.scratch/anchor-verify/`）
  证明它是 2 场抽样落在第 23 百分位（从 170 场分布随机抽 2 场、均值 ≤17.5 的概率 13.7%）；
  西甲（Metrica 自己的联赛）115 场 = 21.76，排除赛事构成解释。
- **抢断**：干净 main **9.41/场**，真实 **36.90/场**（同上的大五子集 n=170，
  StatsBomb `Duel` 中 `type=="Tackle"`，**含成功与失败两态**——与引擎 `tackle` 事件同口径）。
  引擎只有真实的 **0.26×**。
  ⚠️ WhoScored 的「~30（15-17/队）」是**成功抢断**口径，**不与 36.90 并排当真实区间**。
- **犯规**：干净 main 23.53/场，真实 ~20–21/场——**这一条本来就对**，不是缺口。

`notes/volume-compensation.md` §2.4 已经证明：**体积不是一个缺口，是一组缺口**——
只抬射门会让 `shot/tackle` 比值越界（17.65/9.17 = 1.925 ∉ [0.5,1.5]），
因为分子翻倍而分母没动。**射门与抢断必须一起抬。**

P38 #102 的教训（同一族最简解没试完就下结论）在本票的直接应用是：
**先试参数最少的方案**——能不能只用「改常量/重标桶」把体积抬到真实量级，
而不引入任何新机制？本票的实测答案是**能**（见 `design.md` §2 的最简竞争解）。

## What Changes

### 1. 引擎：三个常量（零新机制）

| 常量 | 干净 main | 改为 | 语义 |
|---|---|---|---|
| `OPEN_PLAY_SHOT_ENGAGE_SHIFT` | −4.3 | **−3.4** | 射门推进档的 hazard 平移（射门频率） |
| `BASE_DEF_TACKLE` | −1.10 | **−0.65** | 抢断打分基线（抢断倾向） |
| `BASE_DEF_FOUL` | −0.10 | **−0.06** | 犯规打分基线（犯规倾向，补偿被抢断切走的份额） |

**没有新机制、没有新状态、没有新 RNG 消耗**——三个都是既有常量重标。
（`BASE_DEF_TACKLE` / `BASE_DEF_FOUL` 是 P30 打分选一的既有基线；本票只改数值。）

### 2. L1 门：随体积重标 —— **新带按真实侧分布推导，不照候选配**

两轮用户拍板已定（`design.md` `## User Confirmation`）：

| 带 | 新值 | 推导 |
|---|---|---|
| 普通射门/场 | **`[14, 29]`** | StatsBomb 大五 n=170：mean 21.64 / sd 5.03，`±1.5·sd` = [14.09, 29.18] |
| 抢断/场（**新立**） | **`[24, 50]`** | 同上子集 `Duel/Tackle`：mean 36.90 / sd 8.87，`±1.5·sd` = [23.60, 50.21] |
| 主队进球/场 | **`[0.85, 1.60]`** | **原带相对容差保留法**（非真实侧分布推导）：原带中心 0.565/半宽 0.185 套到**引擎实测新中心 1.188** → `[0.80,1.59]`，取整沿用拍板值（`gh > ga`、`ga_pm ≥ 0.30` **方向断言不动**） |
| 单场角球上界 | **`≤15`** | 3000 场定值；干净 main max=12、本方案 max=13 |

实测（cargo L1 权威，方案 ③ 读数实测于 wasm `13b0263a`，见 `design.md` §D0）：**6 绿 3 红**，红名单逐条：
```
realism.rs:684  →  普通射门/场 17.09 ∉ [6,11]           ← 按压缩态标定的体量带
realism.rs:846  →  主队进球/场 1.188 ∉ [0.38,0.75]     ← 按压缩态标定的绝对量带
realism.rs:779  →  单场角球 13 超硬上界 12               ← 射门抬升本身带来的长尾（非抢断）
```

> ⚠️ **与任务书预期的两处实质偏差（如实报出，grill 独立确认）**：
> 1. 任务书列的第三条必重标是 **shot/tackle `[0.5,1.5]`**。实测**不需要改这条带**——
>    只要抢断一起抬，`shot/tackle = 0.563` 就落在**原带内**（正是 §2.4「要一起抬」的正面验证）。
>    任务书的红值 1.785 来自**只抬射门**的配置。
> 2. **`l3_shot_ratios` 三条比率带也不需要重标**——实测三条全过。真凶是**角球单场上界**。
>
> **另有三条任务书完全没预见的既有红门**（grill 的 B1，本 session 独立复现）：
> 默认 `cargo test` 的 `v2_tackle_frequency_in_target_range`（P7 槽位时代遗留 `[3,14]`）
> 与 `p30_window_foul_cancels_without_shot`（打分序变更使构造几何失效），
> 以及 `l2_sent_off_kickoff_seeds`（RNG 重排使定向 seed 空跑）。
> 完整清单见 `design.md` §D10。

### 3. 模型版本、golden 与标尺基线

序列化行为改变 → `MODEL_VERSION` 6→7，新增 `engine/tests/golden-v7/`，v1–v6 保留不覆盖
（沿用 P34 的处置）。

另需**重生成** `viewer/data/benchmark-baseline.json`（入库文件）——它记的 `engineFingerprint`
会让 `tools/benchmark-baseline.test.mjs` 在引擎行为变更而基线未重生成时硬失败
（实测：hd −0.265 / gap −0.288 等，全部 ≫ 容差）。**任务书未列，本票实测发现。**

## Capabilities

### Modified Capabilities

- `match-engine`：射门/抢断的**体量带**从「压缩态标定」改为「真实量级」（新带按真实侧分布推导）；
  主队进球带与角球单场上界随之重标；新增抢断体量带；
  两条**机制守卫**（抢断频率体量、犯规取消射门的几何前提）改语义/重构造；
  `MODEL_VERSION` 与 golden 基线升级。

### 不改的

- **队形/跑位**：本票零改动（P38 §2.2 已证队形与体积在两根独立轴上）。
- **转化率机制**（`shot_bucket` 的 15/30、7/22、4/11）：不动。P38 §1.3 已证它本来就对。
- **犯规量级**：`BASE_DEF_FOUL` 只做**补偿**（把被抢断切走的份额拉回 ~20），
  不把犯规当缺口修——它本来就在 `[16,30]` 内。

## Impact

- `engine/src/lib.rs`：3 个常量 + `MODEL_VERSION` 6→7
- `engine/tests/realism.rs`：3 条体量带重标 + 1 条新带 + 3 条中断测试修复 + `golden_dir` 加 v7 + legacy 扩 v1–v6
- `engine/tests/golden-v7/`：新增（`ACCEPT_GOLDEN=1` 生成，提交前人工审查 diff）
- `openspec/specs/match-engine/spec.md`：**4 条** requirement（2 ADDED + 2 MODIFIED），与 delta 逐字一致
- **不改** `viewer/` 任何 JS（无浏览器缓存版本号需要更新）
