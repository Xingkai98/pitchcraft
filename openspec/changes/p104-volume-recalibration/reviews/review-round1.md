### M1. 交付源码里的 wasm 哈希指向一个**交付产物不是**的二进制

**严重度：MAJOR**（溯源缺陷；不影响行为）

  d71f7b0 的 engine/src/lib.rs（含 #104 注释）                → b12fa58c

  两者**数值行为逐位相同**（我在 `b12fa58c` 上重测，得到与文档完全一致的 17.095/30.38/20.55/0.563）。

  `notes/scheme-comparison.md`、`notes/REPORT-to-main-session.md`、`reviews/grill-verification-round2.md`

  `viewer/data/benchmark-baseline.json` 的 `engineFingerprint.wasmSha256` 也是 **`b12fa58c`**。

**为什么算问题**：本仓为「wasm 来源」专门立过哨兵（P38 #87：基线曾用未合入分支的 wasm 生成，

### M2. 主队进球带的「新中心 ~1.22」引错了数——那是真实侧**客队**锚点，不是引擎实测

**严重度：MAJOR**（带重标的合法性论证有误；带值本身安全且用户已拍板）

**证据**：
- `engine/tests/realism.rs:901`：「新中心 ~1.22（**引擎实测**，与真实主 1.53 同量级）按同一相对容差 → `[0.82, 1.62]`，取整 `[0.85, 1.60]`」。同样措辞见 `proposal.md:48`、`openspec/specs/match-engine/spec.md:93-94`。
- 但**引擎实测的主队进球是 1.188**（`design.md` §D4.1 自己的表就写着 1.188；我在 600 seed 上复现 1.1883）。
- **1.22 出现在同表的**下一行**：`| 客队进球/场 | 0.993 | 1.22 |`——即**真实侧客队锚点**（`realism.rs:890`
  "真实参考：主 1.53 / 客 1.22"）。`realism.rs:931` 也把 1.22 用作真实客队参照。
- 结果：按所述方法以**真实读数 1.188** 重算，应为 `[0.80, 1.58]`，而非 `[0.85, 1.60]`；
  且实际带的相对容差是**下 −28.5% / 上 +34.7%**（非所称 ±33%）。
- 同时，commit message 写「门重标（**新带按真实侧分布推导，不照引擎现状配**）」并列了四条带——
  但主队进球带的推导是「原带相对容差套到**引擎**新中心」，**恰恰是照引擎现状配**。
  （`design.md` §D5 的标题其实只涵盖三条带、措辞是准确的；是 commit message 与这段推导正文过度声称。）

**为什么算问题**：本审阅的核心问题就是「门重标是否合法」。这条带的**值**没问题（用户第 1 轮 Q3
已拍板 `[0.85,1.60]`，且引擎读数 1.188 距下界 0.338 / 上界 0.412，余量充足），但**推导链复现不出来**
（引的 1.22 对不上任何引擎读数），且被冠以它并未采用的「真实侧推导」名义。

**建议**：把三处的「新中心 ~1.22（引擎实测）」改为「**新中心 1.188（引擎实测，600 seed）**」，
并如实写明：本带用**相对容差保留法**（沿用原带 ±33% 半宽，重新居中到引擎新读数），
**不是**真实侧分布推导——这正是它与 §D5 三条带的方法差异，应当明写而不是并入同一句声称。
带宽可按 1.188 重算为 `[0.80,1.58]` 或保留现值并注明「取整后上下界与原相对容差有 ≤0.05 的偏差」。

### M3. spec 的角球 scenario 把**运行时门**写成 3000 seed，实现是 200 seed

**严重度：MAJOR**（spec 与实现的口径不一致；门本身健全）

**证据**：
- `openspec/specs/match-engine/spec.md`（及 delta 同文）「Scenario: 单场角球上界」：
  「**GIVEN** 引擎以 **3000** 个 seed × 90 分钟模拟（上界是极值统计量，200 场的 max 系统性低估）——
  **THEN** 单场角球计数 SHALL ≤ 15」。
- 但实现的门在 `engine/tests/realism.rs::l1_tackle_dilution_and_slot_mix`，用 `l1_stats()` →
  `run_many(SEEDS_L1)` = **200** 个 seed（401..600）；`max_single` 取的是这 200 场的 max。
- 3000 seed 是**定界值时的分析口径**（`design.md` §D5.3「依据必须用 3000 场定」），
  不是运行时门的口径。实测交付 wasm：200 seed max = **13**、3000 seed max = **13**，
  两者都 ≤ 15，故门在两口径下都健全——**问题只在 spec 把两者混写**。

**建议**：把该 scenario 的 GIVEN 改为 200 seed（与实现一致），并另起一句说明
「上界值 15 由 3000 seed 的极值分析定（干净 main 12 / 本 change 13），
运行时门因 L1 窗口固定为 200 seed 而按 200 seed 评估」。
