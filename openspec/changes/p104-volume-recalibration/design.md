## D0. ⚠️ 本 change 实测发现：**wasm 文件的 sha 会随「注释行数」变化**

> **这条影响所有引用 wasm 哈希的地方，必须先读。**

审阅 round1 的 M1 指出：交付源码里注释的哈希 `13b0263a` 与交付产物对不上。
本 session 追查后发现**根本原因不是笔误，而是一个容易反复踩的坑**：

⚠️ **机制（初版写成「调试行号表」，是错的——grill 第 3 轮解析 section 表后更正，本 session 已复核）**：
交付 wasm **没有任何 `.debug_*` 段**（`Cargo.toml` 也没开 debuginfo）。真实机制是**两处静态数据**：

1. **`data` 段**：rustc 把 `panic!` 的 **`Location{file, line, col}` 作为静态常量**嵌进去，
   注释行平移 → 每处 `line` **恰好 +1**（本 session 实测：加 1 行注释 → 133 处字节差，
   `data` 段部分全为 `+1`，如 `0x4A→0x4B`）；
2. **`name` 段**：Rust 内部符号名带 **LLVM 内容哈希**（如 `llvm.4657078260010199458`
   → `llvm.1742829092740475183`）。

两处都变 → **wasm 文件哈希变，而行为完全不变**。实测（同一组常量）：

| 构建 | wasm sha8 | 60 seed 流哈希 |
|---|---|---|
| 三常量（`6f5827f` 源码 + 三条常量；`MODEL_VERSION` 仍 6、两条测试仍旧版） | `13b0263a` | `44599dcead734d86` |
| 三常量，**含** #104 注释块 | `b12fa58c` → `13e2d9a2` → `67515c05` → `824644da`† | `44599dcead734d86` |

† 含注释的构建哈希自己也在变（每改一次注释就变一次）——本票过程中它依次是
`b12fa58c` → `13e2d9a2` → `67515c05` → `824644da` → `fb201b59`。
**每一个都是同一份行为**（流哈希恒为 `44599dcead734d86`）。
⚠️ **不要在这里写「当前交付」**——那正是本条警告的自指哈希坑（写了就过期，本处初版就踩了）。
**当前交付以 `progress.md` 与基线 `engineFingerprint` 为准。**

**两条后果（都已落到本票）**：
1. **源码文件不能引用自己的构建哈希**——那是不动点问题（写了哈希就改了行号，哈希又变）。
   → `engine/src/lib.rs` 的注释改为**只引「读数实测于哪个哈希」+ 流哈希作行为见证**，
   明确写出「本文件不引用自己的构建哈希」。
   ⚠️ **精确定位**（审阅 round2 指出本处初版措辞过度声称）：基线 `engineFingerprint` 里
   **真正被强制的是 `sourceSha256` + 行为比对**；`wasmSha256` 在
   `tools/benchmark-baseline.mjs` 里被标注为**取证信息、不作判据**——这恰好与本条新认识一致
   （文件哈希随注释变、不能当身份）。所以「指纹以基线为准」应读作
   **「以 `sourceSha256` + 行为为准，`wasmSha256` 只留痕」**。
2. **跨文档的哈希表必须标明它指的是哪一次构建**。本票 §D3.4/§D4 的读数实测于 `13b0263a`
   = **`6f5827f` 源码 + 三条常量**（⚠️ **不是**「交付源码去掉注释块」——它还带
   `MODEL_VERSION=6` 与改动前的两条测试；但因那两条在**测试模块内**不进产物、
   `MODEL_VERSION` 不参与模拟，**行为与交付构建逐位相同**，流哈希为证）。
   **不要**把「读数所属构建」与「交付产物」当成同一个哈希。

> 这不是本票引入的问题——任何改注释的 change 都会遇到。P38 #87 立的
> `engineFingerprint` 哨兵（基线记 wasm + lib.rs 双哈希）是**正确**的应对：
> 它由 `tools/benchmark-baseline.mjs` 重生成，天然与产物一致。**本 change 已重生成。**

> ⚠️ **没有便宜的构建配置能消除它**（grill 第 3 轮提出，本 session 用**独立清空 `target/`** 的
> 受控实验复核，防后人来试）：
> `-C strip=symbols` → 底哈希变（`7dcf6bf1`）但**加注释后仍变**（→ `dfa50e02`）；
> `-C panic=abort` → 与默认**同哈希**（wasm release 本就用 abort）且仍变。
> **所以「源码不引自身哈希 + 基线指纹为准」是正确且唯一可行的应对**——
> 不要去关 debuginfo（本来就没开）或试 `strip`。
>
### D0b. ⚠️ 同类坑：**注释里不能出现源码扫描测试盯的字面量**

`lib.rs` 里有几条测试**扫描自己的源文件文本**（`include_str!("lib.rs")` +
`src.split("#[cfg(test)]").next()`）来守「删干净、无残留」。
（**只有 `lib.rs` 有这类守卫**——`engine/tests/realism.rs` 实测 `include_str!`/`cfg(test)` **0 命中**，
它只 `read_to_string` golden JSON，故改它的注释不受此坑影响。）

本 session 在修 M1 时，在注释里写了**字面量 `#[cfg(test)]`**（解释「那两条改动在测试模块内」）——
结果 `split` **提前截断**，三条测试在生产段里扫不到东西、全红：
```
p31_landing_error_only_in_open_play_passes   （sample_pass_landing 命中数 0，应为 2）
p31_liveness_section_never_emits_events
p31_slot_layer_is_gone
```
**注释里的字面量会被算进扫描**——这是「源码扫描型测试」的固有脆弱性。
处置：注释改写成「**测试模块内**」（不写字面 token）；并审计了本票新增注释是否含
其它被扫 token（`events.push` / `emit_` / `Vec<Event>` / `Event {` / 各 slot 符号）——**均无**。

> **教训（与 §D0 同族）**：本仓用「读自己源码」的方式立守卫，**任何写进源码的文本都可能被守卫吃到**。
> 改注释后**必须重跑默认套件**——它不只是「行为没变所以会过」。

> **不需要为本坑新立哨兵**：`benchmark-baseline.test.mjs` 的 `engineFingerprint`
> **已经就是**它的哨兵（靠源码哈希漂移发现）。已在 `CLAUDE.md`「比赛标尺」一节加一句
> 文档级提示（改注释也会改 wasm 哈希 → 读数请引流哈希/基线指纹、勿引构建哈希）。

## D3. 抢断体积：机制、可动轴、两方案判定

### D3.1 机制：抢断选的是一块**有界的饼**

`select_defensive_action` 对 `tackle / foul / contain / jockey` **打分取最高**（零 RNG）。
**机会点总数与打分无关**（局部成立）→ 四者份额之和有界 → 抬抢断只能从另外三者里切：
contain/jockey 不产事件，所以**主要的切法**是切犯规。

> ⚠️ **grill 的修正（接受）**：设计初版写「**只能**切犯规」，措辞过强。实测
> 方案 ② 的 `tackle+foul` 之和 = 25.60+16.98 = 42.58 > 基线的 9.00+23.77 = 32.77，

> 「固定饼」只在**单个机会点**上成立，不是全局守恒。措辞已改。
