# Grill Design: P0 事件流到球场（event-to-pitch）

> 使用 batch-grill-me skill，按轮次采访用户，敲定 P0 的设计细节。
> 用户在 Open Questions 全部确认前，不写实现代码。

## Round 1: 设计树 frontier

P0 的设计树前沿决策（已定决策：Rust 引擎、JS Canvas、B 内嵌引擎、演绎参数由引擎给、第一版简单、节奏配置化——不再问）。

### Q1: P0 引擎的模拟深度

P0 引擎要"真实到什么程度"？

- **A（推荐）纯随机事件流**：引擎用种子随机生成"合理的事件序列"（传球、带球、射门），事件类型/方向/位置随机但受简单约束（如传球在附近球员间、射门在对方半场）。不做球员 AI/决策。
- **B 极简决策**：每个持球球员做一次简单决策（随机选传球/带球/射门，带简单位置逻辑）。

理由：P0 目标是验证"引擎→事件流→画面"链路，不是真实比赛逻辑。A 最省，链路验证足够。

### Q2: 时间推进模型（票据 03）

P0 引擎用哪种时间模型？

- **A（推荐）事件驱动**：没有固定 tick，直接"算到下一个事件"，事件之间时间跳变（由引擎给出 t）。
- **B 固定 tick**：每 1/8s 一个逻辑 tick，tick 内产生事件（仿 FM slice）。
- **C 混合**：逻辑 tick + 决策点触发。

理由：P0 最小，事件驱动最省——引擎只需按"下一个事件"推进，画面按事件 t 播放。

### Q3: 球场模型（票据 04）

P0 用什么球场模型？

- **A（推荐）纯连续坐标**：事件直接带归一化坐标（0-1），引擎按简单规则把事件放在合理位置（传球在附近、射门在球门附近）。不分区。
- **B 5区+连续**：宏观分区（己方禁区→对方禁区）+ 每个事件定位到区内坐标。

理由：P0 纯连续坐标最简，分区是 P1 战术系统的活。

### Q4: 能力值模型（票据 05）

P0 要不要球员能力值？

- **A（推荐）不要**：P0 不引入能力值，所有球员等价，事件随机。能力值在 P1 加（届时对齐社区实测结论：物理属性主导）。
- **B 最小集**：P0 就给每个球员 2-3 个属性（如速度、传球），影响事件概率。

理由：P0 验证链路，能力值是引擎复杂度的主要来源，留到 P1。

### Q5: 确定性策略（票据 06）

P0 确定性做到什么程度？

- **A（推荐）种子 RNG + 可复现**：引擎用种子驱动随机，同种子 → 同事件流。不做定点数。
- **B 完整**：种子 + 定点数 + 带标签 RNG 流。

理由：P0 只需"可复现"（调试、回放），定点数在 P1 做。注意坐标精度：P0 用 float，P1 定定点数时改。

### Q6: WASM 交互方式

引擎怎么把事件流给 JS？

- **A（推荐）一次性产出**：WASM 引擎 `simulate(seed, config) → 整场事件流(JSON)`，一次传给 JS 播放。
- **B 流式/分步**：引擎逐步产出事件，JS 按需拉取。

理由：P0 一次性产出最简单，链路验证足够。流式是 P1 做实时/长比赛时的事。

### Q7: 画面播放控制

P0 画面层要不要播放控制？

- **A（推荐）基本控制**：播放/暂停/速度（1x/2x/4x）+ 进度条。
- **B 纯自动**：加载后自动播放，无控制。

理由：看比赛需要控制，尤其调试时。基本控制不复杂。

### Q8: 展示形态

P0 在浏览器里怎么展示？

- **A（推荐）固定种子 + 刷新重播**：页面加载用固定种子模拟一场，自动播放；点"重播"刷新。
- **B 可选种子**：一个种子输入框，输入种子重新模拟播放。

理由：A 最简，验证链路够用；B 的种子输入框在 P1 加（配合确定性调试）。

### Q8b: 阵型系统（用户 Round 2 提出）

P0 要不要做球员阵型系统？

- **A（推荐）不要**：P0 不做阵型系统，用"固定默认站位"（开球时 22 人站合理位置：门将门前/后卫后场/中场中圈/前锋前场），比赛开始后靠事件驱动移动。阵型是战术层，依赖球场模型完善，留到 P1/P2（归属票据 04 或新战术票据）。
- B 做：P0 就做站位/角色/攻防跑位。

理由：P0 验证链路，阵型是引擎复杂度大头；固定默认站位足够"看起来像开球"。

## Round 2: 设计树下一层 frontier

Round 1 决策解锁的下一层细节（Q9-Q15），以及用户新提出的 Q8b。

### Q9: 事件坐标合理性（因 Q1 纯随机而起）

纯随机事件流，怎么让事件位置"看起来像足球"？

- **A（推荐）简单约束**：传球发生在最近队友方向、射门在对方半场（球门附近）、带球朝向对方球门。位置仍随机但受约束。
- **B 完全随机**：任何事件任何位置。最省，但画面会很怪。

理由：A 用"随机但受约束"低成本获得"像球赛"的画面，是纯随机和真实之间的甜点。

### Q10: 事件量（因 Q1 纯随机而起）

P0 一场最小比赛产生多少事件？

- **A（推荐）人工设定节奏**：比如 45 分钟（半场）约 100-200 条事件（每 15-20 秒一次动作），引擎按此节奏随机生成。
- **B 随性**：引擎随意决定事件量。

理由：事件密度直接决定画面节奏。太少稀稀拉拉，太多画面乱。A 让 P0 画面有"像比赛"的节奏。

### Q11: 引擎与画面代码组织（因 Q6 一次性产出而起）

Rust 引擎和 JS 画面怎么组织在一个仓库？

- **A（推荐）monorepo**：`engine/`（Rust crate）+ `viewer/`（JS）+ 根 `README`，各自独立构建，WASM 产物给 viewer 用。
- **B 分开仓库**：引擎和画面两个独立仓库。

理由：P0 单仓库最简，引擎编译的 WASM 直接给 viewer 用，一体化调试。

### Q12: 球员与队伍数据（因 Q3 连续坐标、Q4 无能力值、Q8b 无阵型而起）

P0 的 22 个球员从哪来？

- **A（推荐）硬编码 22 个占位球员**：两队各 11 人（home#1-11 / away#1-11），固定默认站位（门将/后卫/中场/前锋简略位置），无能力值。
- **B 配置文件定义**。

理由：P0 硬编码 + 固定默认站位最简；配置文件在 P1 加。

### Q13: 画面坐标映射（因 Q3 连续坐标而起）

归一化坐标怎么映射到 Canvas？

- **A（推荐）等比映射**：Canvas 保持球场比例（如 700×450），坐标乘以宽高得到像素，球门/白线按比例画。
- **B 拉伸填充**：填满整个 Canvas。

理由：A 保持真实球场比例，画面"像球场"；B 会让球场变形。

### Q14: 演绎节奏配置文件（票据 09 已定要配置化）

配置文件放哪、什么格式？

- **A（推荐）viewer 内一个 `config.js`**（或 JSON），定义各事件的 phase 时长、人球分离量。
- **B 独立 JSON 文件 + 加载逻辑**。

理由：P0 用 JS 模块最简，后续再抽独立配置。

### Q15: 验证协议怎么记录（因 Q6 一次性产出而起）

协议接缝顺不顺，P0 怎么收集依据？

- **A（推荐）跑通后写一份"协议验证笔记"**：记录哪些字段顺、哪些别扭、哪些该加/改，作为票据 02 定稿的依据。
- **B 仅口头观察**。

理由：A 把"验证"变成可追溯的产出，正是票据 02 需要的。

## Pre-Implementation Check（对抗性完整性检查，2026-08-04）

写代码前用对抗性检查发现的 gaps（来自第一个检查视角"任务↔规格一致性"；另两个视角会话中断未完成，本次以已得结果为准）：

### Blocker
- **B1（spec-gap）画面层无法知道 22 个球员的任意时刻位置**：事件流只携带事件主体（subject）的 x/y（传球才有 from/to）。pitch-viewer 要求"渲染 22 个球员圆点"，但没有开球/首发阵容消息携带初始站位，任务 4.2 无法实现——除非 viewer 自造状态，这违反"画面层只消费事件流"（单一接缝）。
  → 修复：**引擎在事件流开头发一条初始站位消息**（扩展 kickoff 或新增 lineup/positions 事件，携带 22 个 {id, team, x, y}），viewer 纯从事件流渲染。

### Should-fix
- **S1（spec-gap）事件 subject id 没有队伍编码**：坐标是中立的（x=0 左门线），viewer 无法从位置推断主客队，任务 4.2 需要主客队颜色但无映射规则。
  → 修复：**协议定义 id 方案**（如 0-10 = home，11-21 = away，或事件带 team 字段）。
- **S2（missing-task）viewer 如何加载/实例化 WASM 未定义**：task 3.5 编译 WASM，5.1 说浏览器加载，但 fetch + instantiate 的机制、.wasm 如何 serve（file:// 下 fetch .wasm 失败）都没写。
  → 修复：**补任务**：viewer fetch engine.wasm 并实例化，从 app.js 调用 simulate；注明需本地 HTTP server。
- **S3（spec-gap）simulate(seed, config) 的 config 形状未定义**：确定性要求"同 seed 同 config"，但 config 是什么没人知道（比赛时长？阵型？占位？）。
  → 修复：**spec 里定义最小 config**（如 { match_duration_seconds } 或明确 P0 为占位空对象）。
- **S4（silent-assumption）引擎给参数 vs 画面 config 的边界未定**：per-event speed/lead/touch_freq 必须来自事件，config 里又是 phase 时长/人球分离量。哪个归哪个没写清。
  → 修复：**明确分工**：per-event 速度/提前量/触球频率来自事件载荷；config 只放动画时序（phase 时长、人球分离量）。事件值优先。
