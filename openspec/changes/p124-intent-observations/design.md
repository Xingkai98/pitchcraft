## 2. 要接出的信号（引擎内已有，sidecar 没有）

### 2.1 起脚窗口（`ShotSetup`）

| 字段 | 语义 | 为什么是「意图」 |
|---|---|---|
| `in_window` | 是否已进入起脚窗口 | 这是**进攻意图的显式状态**：球队已推进到射程并**决定可否起脚** |
| `window_ticks` | 窗口内已消耗的决策 tick | 窗口内的**犹豫时长**——「到了射程但没起脚」是战术信号 |
| `drive_ticks_left` | 推进预算剩余 | 还在推进 vs 已耗尽 |
| `committed` | 是否已提交射门 | 意图**落定**的时刻（提交后防守不再能抢断） |
| `entry_pressure_bucket` | 进窗时的压迫桶 | 「在多大压力下决定起脚」 |

**注意**：`shot_setup` 是**单场单例**（`st.shot_setup: Option<ShotSetup>`），
即任一时刻最多一个持球者在起脚序列中——采样时取当下值即可。

### 2.2 防守动作与压迫（`DefensiveAction`）

| 量 | 语义 |
|---|---|
| `DefensiveAction` ∈ {Tackle, Foul, Contain, Jockey, None} | 防守方的**意图类型**（抢 / 犯规 / 封堵 / 跟防 / 无） |
| `pressure_state`（或 `pressure_state_ticks`） | 持球者当前受压程度 |

⚠️ **只在能确定取值时记**；**不得从位置反推意图**（那是 P16 已证不足的做法）。

### 2.3 与 G1 同法

采样点复用 P16 的 `tick` 返回之后（**拍 = tick，不是 beat**）。
recorder 新增 `observe_intent(...)`（或扩 `observe_state`），**传值语义**——
保持 `observation.rs` 模块头「本文件不引用 `MatchState`」的承诺。

## 3. 必须先做的前置：重新净化 motif 混淆

P16 已指出未净化变量（`build_up` 与 `progression` 在「传球数」与「是否重开」上**同时不同**）。
主 session 在 P16 交付前跑过一轮净化（30 seed，`forward_m/s`）：

| 臂 | 定义 | AUC |
|---|---|---|
| 当前定义 | 重开 + 传球数同时不同 | 0.461 |
| 抽掉「是否重开」 | 只留传球数 | 0.437 |
| 抽掉「传球数」 | 只留是否重开 | 0.490 |
| 两个都抽掉 | 空对照 | **0.500** |

⇒ P16 的裁决**不是混淆造成的假象**；但**接入新信号后必须再净化一次**——
否则分不清「分开是因为意图」还是「因为传球数/重开」。

## 4. 探针纪律（P16 的血泪，必须继承）

⚠️ **P16 期间，探针本身出过两次假证据**：
1. 比较函数对数组误用 `.x`/`.y` 得 `NaN`，而 `NaN > max` 恒假 ⇒ 打出「`max|Δ| = 0.000000`」；
2. 主 session 在净化探针里用 `flatten()` 丢 `None` ⇒ **压缩索引空间**，参考集下标与特征下标错位，
   `final_third` 从 0.855 被算成 **0.493**。

**⇒ 本 change 的探针必须**：
- **NaN / 非有限值显式判红**（不得依赖 `>`/`max` 的静默语义）；
- **报「跳过几个 / 比较几个」**，不只报分母；
- **带反证条**：一条「已知应给高分」的对照（如 `final_third` ≈ 0.855）先跑通，
  否则探针坏了结论不可信；
- **参考集下标与特征下标同处一个索引空间**（不得 `flatten`、不得混口径）。

## 5. 验收

1. **新信号进 sidecar**：只读；`simulate()` 逐字节一致门仍绿；不改 `ControlFact` 闭集；
2. **意图类特征**：每条给定义 + 覆盖率 + 缺失原因分类（同 P16 口径）；
3. **重跑 gate**：三档 AUC，与 P16 基线并列对照；
4. **重新净化混淆**（§3），带反证条；
5. **明确裁决**（二选一，均须证据）：
   - **够** → 三档各自的可执行谓词（供 15B），且**不得**退化成「区域 = 阶段」；
   - **不够** → 点名**还缺哪类观测**，以及 15B 应保留 `unknown` 还是换路线。
6. **不得**用区域/坐标冒充战术阶段；几何代理须命名为**证据**，不得复用 `Phase`。

### §6.1 粒度：**两条通道，按「是不是引擎状态」分（已定）**

**判据不是「稀疏省事」，是「这个量在采样时刻是否真的存在」。**

| 通道 | 量 | 粒度 | 理由（读代码得出） |
|---|---|---|---|
| `intent_snapshots` | `ShotSetup` 状态 + `pressure_state_ticks` | **逐 tick**（与位置同拍） | 二者都是 `MatchState` 的**显式字段**，任一拍都有确定取值；「窗口持续多久」由逐拍序列**直接可读**（无需重建） |
| `defensive_intents` | `DefensiveAction` | **稀疏**（每个被执行的机会一条） | 它不是引擎状态，是**决策输出**；引擎只在 tally 里留累计计数，不留「上一拍选了什么」。逐 tick 记会得到 ~99% 占位值**且丢掉分母**（分不清「没机会」与「选了 None」） |

- **两条通道的分工与对齐**：逐 tick 通道与 `state_snapshots` **同拍同 `t`**
  （测试 `intent_export_is_tick_aligned_with_positions` 逐拍断言）；
  稀疏通道**自描述时间**（每条带 `t`），归因靠时间落进 episode 区间，**不靠下标**。
- **为什么不给 `ShotSetup` 也做稀疏变化记录**：那样「窗口内犹豫时长」（design §2.1
  点名的意图信号）需要**重建**——而逐 tick 记让它直接可读。逐 tick 的代价（重复值多）
  由「只在变化时聚合」的**下游特征**承担，不由采集端承担（采集端只做无损记录）。
- ⚠️ **逐 tick 通道里 `committed` 恒为 `false`**（实测 seed 1..=5 全 0）——机制：
  `shot_window_plan` 的提交分支是 `st.shot_setup = None;` **紧接**执行，提交与序列销毁
  **同一 tick**，而采样点在 `tick()` 返回之后 ⇒ 该字段在采样点上**不可观测**。
  它作为「引擎字段的如实投影」保留（不是死字段，是**投影**），但下游**不得**用它构造
  意图特征——已由 `committed_is_not_observable_at_the_per_tick_sampling_point` 钉住。

### §6.2 `pressure_state` 语义：**剩余保持 tick 数（倒计时），不在此归一（已定）**

读代码定死（`MatchState.pressure_state_ticks` + `ShotOpportunityFeatures::defensive_pressure`）：

- 它是**倒计时**：防守动作结算为 `Contain`/`Jockey`（无事件防守）时置为满值
  （`PRESSURE_STATE_HOLD_TICKS`），此后**每 tick 衰减 1**，归 0 = 无压迫状态。
- **不是「压迫强度」**，是「**距上次无事件防守的 tick 数（饱和）**」。
- 引擎侧唯一的消费点是射门 hazard 的 `defensive_pressure` 因子，
  那里**先除以满值归一**再乘权重。⇒ 归一化只有那一个落点。
- ⇒ **sidecar 记原始 tick 数**（`IntentState::pressure_state_ticks`），**不在此归一**——
  两处各自归一必然分叉（本仓「结论对但机制错」的同型风险）。下游要强度时
  自己除，且必须**显式声明**用的是同一个满值常量。

### §6.3–6.4 意图特征怎么进 gate / 若仍判不了怎么办

**留到 Slice 4**（依赖实测）。原则先记两条：
- 意图特征进 gate 时**必须与 P16 的空间特征分开成列**，否则「改善来自意图」与
  「改善来自重跑」分不开；
- 若 gate 仍判不了，**不得**为了「有产出」而降低判据（那是 #19 调参的活）。
