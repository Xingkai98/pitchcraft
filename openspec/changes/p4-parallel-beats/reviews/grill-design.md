# Grill Design: P4 并行节拍事件流（parallel-beats）

> 使用 batch-grill-me skill，按轮次采访用户，敲定 P4 的设计细节。
> 用户在 Open Questions 全部确认前，不写实现代码。

## 背景（facts，已从代码确认）

- 当前引擎事件驱动：`while t < dur` 每轮产单事件（pass/dribble/shot/tackle），控球间隔内 `fill_with_off_ball` 产单球员 off_ball_run。
- Event 结构体：`subject`（主球员）+ 少量参数；`players` 数组仅 lineup 初始站位用。
- viewer `interpretEvent` 逐事件产锚点；`_interpolateAnchors` 连续模式插值。
- 用户确认方向（2026-08-07）：固定 tick 产"节拍"，每拍含可选 `main`（带球/传球/射门焦点）+ `movers`（并行跑位）；关键时刻保留高亮事件。

## Round 1: P4 设计树 frontier

### Q1: tick 粒度（固定时间间隔）

引擎每 tick 推进多少比赛时间？

- **A（推荐）1 秒**：2700s ≈ 2700 拍。数据量可控，圆点画面够用；关键时刻（传球飞行 1.2s）跨 2 拍，球在拍间插值。
- **B 0.5 秒**：更平滑，但数据量翻倍（5400 拍），对圆点画面可能过度。
- **C 2 秒**：数据量减半，但动作看起来"跳步"。

理由：1s 是圆点比赛画面的甜点；观感不好再加密。

### Q2: 节拍 vs 高亮事件的关系

关键时刻（传球/射门/进球）怎么呈现？

- **A（推荐）高亮事件叠加在节拍流上**：节拍流只描述"每个人在干嘛"（带球/跑位/卡位），传球/射门/抢断是独立事件（有球轨迹、门将扑救、传跑节奏），按自己的时序叠加。关键时刻戏剧性保留，普通时刻全员动。
- **B 每 tick 内嵌 main**：传球那几拍每拍带 `main:{type:'pass'}`，球在帧间插值。关键时刻被 tick 化，可能失去"事件驱动的节奏感"。

理由：A 保留 P1-P3 打磨的戏剧演绎（射门扑救、传跑配合），B 会把它们拉平到 tick 节奏。

### Q3: movers 数据——增量 vs 全量

节拍的 movers 数组发哪些球员？

- **A（推荐）增量（只发移动的球员）**：每个节拍只列正在移动的球员（带球者、跑位者、门将移动等），静止的人不发，viewer 让他们 hold。数据量小（普通时刻 5-12 人动）。
- **B 全量（每拍 22 人）**：每个节拍列全部 22 人位置（含静止）。viewer 简单，但数据量大（5400×22）。

理由：增量符合"事件流只描述变化"的精神，数据量可控；静止球员 hold 即可。

### Q4: 关键时刻跨 tick——球的位置

传球飞行跨多个 tick，球的位置怎么给？

- **A（推荐）高亮事件带球轨迹**：传球事件带 `x/y → x2/y2` + 球速，viewer 在事件时序内插值球位置（现状已如此）。tick 流不含球位置，球位置完全由高亮事件驱动。
- **B 每拍带球位置**：节拍里带球当前坐标，viewer 在拍间插值球。tick 流需要维护球位置。

理由：A 让球轨迹和关键时刻绑定（有弧线、有节奏），现状已有；B 把球位置摊进 tick，球轨迹变简单线性。

### Q5: 节拍事件类型——独立 type 还是复用？

节拍在协议里怎么表达？

- **A（推荐）新 type `beat`**：每个节拍一条 `{t, type:'beat', movers:[...], main?:{...}}`。清晰表达"这是并行节拍"。
- **B 复用 off_ball_run + 扩展**：off_ball_run 加 movers 数组承载并行。改动小但语义混乱（off_ball_run 原意单球员）。

理由：A 语义清晰，协议版本化时容易区分；B 是 hack。

### Q6: 主事件（main）何时有

节拍的 `main` 字段什么时候有内容？

- **A（推荐）当持球者有焦点动作时**：持球者带球/传球/射门/抢断时，节拍带 `main` 描述焦点；否则节拍只有 movers（普通跑位）。
- **B 永远有 main**：每个节拍都指定一个焦点（即使只是"持球者 hold"）。

理由：A 更简洁——普通时刻节拍只有 movers，焦点时刻才有 main；B 会让每拍都强制一个焦点，意义不大。

### Q7: 引擎状态模型

引擎怎么维护全员位置？

- **A（推荐）持续维护 pos[]（22 人）+ 每 tick 更新移动者**：引擎每 tick 为每个球员决策目标（持球者带球、队友跑位/卡位、门将回位），更新 pos[]，产节拍。这是 FM slice 模型。
- **B 事件驱动生成节拍**：保持事件驱动产生关键事件，节拍从事件间隙填充（当前 fill_with_off_ball 的扩展）。

理由：A 是真正的"全员每刻决策"，符合目标；B 仍是事件驱动的补丁。

### Q8: 战术/角色站位

无球跑位的目标怎么定？

- **A（推荐）引入角色基准点**：每个球员有"角色站位"（后卫/中场/前锋的基准位置），无球跑位向基准点附近调整/移动，偏离时回位。这是"卡位/回位"的基础。
- **B 随机小幅移动**：继续当前"随机方向挪一小步"，只是并行化。

理由：A 让无球跑位有方向感（回位、拉开、压上），画面更真实；B 随机挪动观感仍乱。但 A 是引擎 AI 的起点，复杂度增加——可作为本 change 的增强或后续。

### Q9: 关键时刻频率

一场比赛多少关键时刻（传球/射门/抢断）？

- **A（推荐）保持当前节奏**：传球/带球/射门/抢断仍按战术随机（约 200 次/场），节拍流填充间隙。关键时刻是"高光"，普通时刻是"流动"。
- **B 关键时刻更密**：增加事件频率，减少纯跑位间隙。

理由：A 保留"关键时刻有戏"的观感，节拍流让普通时刻也活；B 会让画面太密。

### Q10: 向后兼容

协议变化怎么处理？

- **A（推荐）协议 v2（新增 beat 类型）**：保留 v1 事件（pass/dribble/shot 等），新增 beat 节拍。viewer 兼容两者。
- **B 替换 v1**：直接改成节拍流，废弃旧事件。

理由：A 平滑过渡，旧事件（高亮）继续用，beat 补充并行；B 风险大且没必要。

## User Confirmation（2026-08-07，batch-grill-me）

- **Q1**：用户答复：**1 秒**（tick 粒度，2700 拍/场，数据量可控，关键时刻跨拍靠插值）。
