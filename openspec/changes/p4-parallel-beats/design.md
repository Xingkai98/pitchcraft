# Design: 并行节拍事件流（parallel-beats）

## Context

P3 之后连续播放成立，但事件流是"串行"的：每条事件只描述一个球员的动作，同一时刻只有 1-2 人有数据，其他 21 人站桩。用户反馈：真实比赛是 22 人每一刻都在同时动（有人带球、有人插上、有人卡位、有人回撤），当前"一个动作一个动作顺序播放"很不合理。

本 change 把事件流从"串行动作"重构为"并行节拍"：**固定 tick（1s）产节拍事件**，每拍描述所有在移动的球员的并行动作；关键时刻（传球/射门/抢断）保留为高亮事件叠加在节拍流上。

## Goals / Non-Goals

**Goals:**
- 固定 tick（1s）推进，每 tick 更新全员位置/动作状态，产节拍事件（main + movers）。
- 节拍 movers 增量（只发移动球员），viewer 对静止球员 hold。
- 关键时刻（pass/shot/tackle）保留为高亮事件，有球轨迹/门将扑救/传跑节奏。
- 角色基准点：无球跑位向角色站位调整/回位，有方向感。
- 协议 v2 新增 beat 类型，向后兼容 v1 事件。

**Non-Goals:**
- 不做完整球员 AI（决策打分/能力值）——票据 05。
- 不做战术系统（阵型/指令）——票据 04。
- 不做带标签 RNG 流完整化/定点数——票据 06。
- 不做完整比赛规则（越位/界外球等）——之后。

## Decisions

### D1: 固定 tick 1s（Q1）
- 引擎按固定 1s 推进（slice 模型），每 tick 产一个节拍事件。
- 关键时刻（传球/射门）跨多 tick：球轨迹由高亮事件驱动，viewer 在事件时序内插值。
- **为什么**：1s 是圆点画面的甜点；固定节奏让"全员每刻决策"成为可能。

### D2: 高亮事件叠加（Q2）
- 节拍流描述"每个人在干嘛"（带球/跑位/卡位）；传球/射门/抢断是独立高亮事件，按自己的时序叠加。
- **为什么**：保留 P1-P3 打磨的戏剧演绎（射门扑救、传跑配合），关键时刻不被 tick 拉平。

### D3: movers 增量（Q3）
- 节拍 `movers` 只列正在移动的球员（带球者、跑位者、门将移动等），静止球员不发，viewer hold。
- **为什么**：数据量可控（普通时刻 5-12 人动），符合"事件流只描述变化"。

### D4: 球位置由高亮事件驱动（Q4）
- 传球/射门事件带 `x/y → x2/y2` + 球速，viewer 在事件时序内插值球位置。tick 流不含球位置。
- **为什么**：球轨迹与关键时刻绑定，有弧线/节奏；现状已如此，复用。

### D5: 新 type 'beat'（Q5）
- 每拍 `{t, type:'beat', movers:[{id, from_x, from_y, to_x, to_y, speed, action}], main?:{...}}`。
- **为什么**：语义清晰，协议版本化易区分；不 hack off_ball_run。

### D6: main 在持球者焦点动作时出现（Q6）
- 持球者带球/传球/射门/抢断时，节拍带 `main` 描述焦点；普通跑位只有 movers。
- **为什么**：简洁——焦点时刻才有 main，普通时刻纯并行跑位。

### D7: 全员状态逐 tick 更新（Q7）
- 引擎维护 `pos[22]`，每 tick 为每个球员决策目标：持球者带球、队友向角色基准点跑位/卡位、门将回位。更新 pos[]，产节拍。
- **为什么**：FM slice 模型，真正的"全员每刻决策"。

### D8: 球相关队形目标（Q8，升级——替代静态角色基准点）

> 升级说明（2026-08-07）：三视角审阅确认"静态 home 回位"会产生 11 个独立人偶，不产生队形平移，且结构性阻碍反击。故升级为球相关队形目标。

- 每球员目标位置 = **角色基准 + 队形偏移**。队形偏移是 `(球位置, 控球阶段, 球侧)` 的公式：
  - 后卫线随球前压/回撤（防守线 push up / drop back）
  - 全队随球侧平移（ball-side shift，球在左半场全队偏左）
  - 控球阶段压上（己方持球时整体前压，对方持球时回收）
- 每个开放比赛时刻，球员目标随球/阶段实时变化，而非静止 home。
- **为什么**：这是"像足球"的最大真实感来源——阵型伸缩/平移。是公式（非战术系统票据 04），投入产出比最高。

### D9: 关键时刻保持当前节奏（Q9）
- 传球/带球/射门/抢断仍按战术随机（约 200 次/场），节拍流填充间隙。
- **为什么**：关键时刻是"高光"，普通时刻是"流动"。

### D10: 协议 v2 新增 beat，向后兼容（Q10）
- 保留 v1 事件（pass/dribble/shot 等），新增 beat 节拍。viewer 兼容两者。
- **为什么**：平滑过渡，旧事件（高亮）继续用，beat 补充并行。

### D11: 控球阶段 + 攻防转换（升级，新增）

> 新增说明（2026-08-07）：审阅确认"攻防转换/突然反击"是最像足球的时刻，缺失则画面被动。

- 引擎维护每队 `phase`（attack / defend / transition）。
- 抢断成功/拦截/扑救 → 球权易主 → 触发短 transition 窗口：新进攻方持球者高速前插、队友整体前压（队形偏移放大）；新防守方整体回撤 + 就近 1-2 人向持球者收缩（盯人/逼抢的雏形）。
- **为什么**：粗糙的 transition 也能产生"突然反击"画面，是真实感关键杠杆。

### D12: 球所有权 + beat↔高亮合成规则（升级，新增）

> 新增说明（2026-08-07）：审阅标为"FUNDAMENTAL"与"最大技术风险"。必须定死，否则球冻结/双重移动。

- **球有且只有一个驱动者**（每个开放比赛时刻）：
  - 节拍 stretch（无高亮）：持球者带球 → `main` 带球轨迹（x/y→x2/y2+speed），球由 main 驱动。
  - 高亮期间：球由高亮事件（pass/shot）驱动。
  - 无持球者（松散球）：beat 带 `ball` 坐标（`loose:true`），viewer 可读松散球追逐。
- **高亮期间参与者从 beat movers 排除**：pass 的接球者/传球者、shot 的门将/射手、tackle 的双方，在其高亮时序内不在 beat movers（或与高亮精确一致）。引擎 pos[] 对账到高亮结束位置。
- **main 只管带球/控球**：pass/shot/tackle 只走高亮事件，不进 main（避免双播）。
- **为什么**：消除"球无人驾驶""同一球员双重移动"两类致命缺陷。

## Risks / Trade-offs

- **[数据量]**: 固定 tick + 全员，用增量 movers 控制；若仍大换紧凑格式。
- **[队形公式复杂度]**: 球相关队形目标是公式（非战术系统），复杂度可控，但需调参避免"橡皮筋"。
- **[高亮与节拍合成]**: 所有权规则（D12）是最大技术风险；viewer 需两层合成（高亮覆盖 beat）。
- **[向后兼容]**: viewer 需同时处理 beat 与 v1 事件；协议校验扩展。
- **[性能]**: ~2700 beat + ~200 高亮锚点数量级增大，viewer 插值需从线性扫描改时间索引。

## Migration Plan

- 引擎：主循环重构为固定 tick + 全员状态更新 + 队形目标 + 阶段转换 + 节拍产出；高亮事件仍产。
- 协议：新增 beat 类型 + movers 结构 + ball 所有权字段；viewer protocol 支持。
- viewer：beat 演绎（movers 批量插值）+ 高亮叠加（两层合成，所有权排除）+ 球可见性。
- 测试：引擎节拍确定性/队形/阶段；viewer beat 插值/合成/无 snap。

## Open Questions

- 队形偏移公式的具体参数（防线前压幅度、球侧平移量）——实施时定义并调参。
- 静止球员 micro-motion（小幅重心调整避免冻结）——viewer 层实现，作为 P4 增强。
- viewer：interpretEvent 支持 beat（movers 批量插值）+ 高亮叠加。
- 测试：引擎节拍确定性/全员移动；viewer beat 插值。

## Open Questions

- 角色基准点的具体分配（每球员 home 位置）——实施时定义。
- 高亮事件与节拍如何避免冲突（同一 tick 焦点 vs 跑位）——实施时细化。
