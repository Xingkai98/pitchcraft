# Proposal: 并行节拍事件流（parallel-beats）

## Why

P3 之后连续播放已成立（事件驱动、整场推进、无 snap），但观感有根本缺陷：**事件流是"串行"的**——每条事件只描述一个球员的动作（`off_ball_run` 一次只让一人挪 1-2m），同一时刻只有 1-2 人有数据，其他 21 人只能站桩。

用户反馈（2026-08-07）：真实比赛是**所有 22 人每一刻都在同时动**——有人带球、有人插上、有人卡位、有人回撤。当前串行事件流"一个动作一个动作顺序播放，每个人只有动作时移动，其他人站在原地"很不合理。

目标：改成**固定时间间隔（tick）产"节拍"事件**，每个节拍描述**所有在移动的球员的并行动作**；关键时刻（传球/射门/抢断）保留为高亮事件叠加在节拍流上。这样普通时刻"一群人在动"，关键时刻"有戏"。

## What Changes

- **引擎时间模型**：从"事件驱动（动作时长推进）"改为"固定 tick 推进（如每 1s 一拍）"，每 tick 更新全部 22 人位置/动作状态。
- **节拍事件**：每个 tick 产一个节拍，含可选 `main`（带球/传球/射门等焦点）+ `movers`（并行跑位，增量——只含移动的球员）。
- **关键时刻高亮事件**：传球/射门/进球保留为独立事件（有球轨迹、门将扑救、传跑配合的戏剧节奏），叠加在节拍流上。
- **viewer**：每拍插值所有球员（有数据的人动，没数据的 hold）；高亮事件在节拍背景上播。
- **协议**：新事件结构（节拍含 movers 数组），向后兼容或新版本。

## Capabilities

### New Capabilities

无（重构既有能力）。

### Modified Capabilities

- `match-engine`: 时间模型从事件驱动改为固定 tick + 全员状态更新；产节拍事件（main + movers）。
- `event-stream-protocol`: 节拍事件结构（可选 main + movers 并行数组）。
- `pitch-viewer`: 每拍插值全员 + 高亮事件叠加播放。

## Impact

- 引擎主循环重构（时间推进、全员状态、节拍产出）。
- 协议扩展（movers 数组 / 节拍结构）。
- viewer 插值层适配（批量 movers + 高亮叠加）。
- 数据量变化（固定 tick + 全员，需增量控制）。

## 关联票据（wayfinder）

- `03` 时间推进模型 → 本 change 落地固定 tick（slice 模型）。
- `06` 确定性与回放 → 节拍流 + 固定种子仍可回放。
