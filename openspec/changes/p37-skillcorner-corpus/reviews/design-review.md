## 2. 结论摘要

**设计方向正确、可实现，但其中一条核心论证（D2）不成立，且它被指定为「硬门」的 D7
在任何数据上都只有约 25% 的通过率——按现状实现会让本 change 无法收尾。**

- **D2（外推点口径）站不住**：design 声称「默认跳过外推点」让两侧可比。实测证明它
  反而制造了**另一种不可比**：trim1 是**顺序统计量**，其期望依赖参与人数 n；Metrica 每帧
  恒为 10 名非门将，SkillCorner「仅真检测」的中位数是 8（范围 0–10）。单场实测把
  ~8.5m 的口径差拆开：**约 5.2m 是纯粹的 n 效应（机械偏差）**，只有 ~3.3m 与「外推 vs 观测」
  有关。这与 P36 D3 立下的「口径分叉 = 数字不可比」是同一条原则，design 引用了它，然后违反了它。
- **D7（half-split 硬门）站不住**：对 iid 数据，min/max 包含门的通过率 =
  `n(n−1)/((n+m)(n+m−1))`，n=m=70 时 **0.248**；蒙特卡洛 0.247。**这个概率与样本量无关**
  （2 场/半 → 0.241，200 场/半 → 0.250）。「更多样本会让门可信」对 min/max 门不成立。
  `verify.sh` 全绿是项目收尾条件，这个门首日即红且长期红。
- **D3 部分站得住**：「引擎 5400s 不含中场」**核实为真**（`engine/src/lib.rs:251` + 主循环
  2388–2391 连续跑到 5400，全场**没有任何中场哨**，唯一 whistle 在 `dur` 且被标成
  `"half_time"`）。但「拼接处会产生一个 ~190s 正向间隙」**是错的**——实测接缝间隙
  **0.00s**；且由数据极值算 shift 的做法在 P1/P2 首尾有缺口时会静默失真，而源数据里
  本来就有权威的半场边界字段（`match_periods`）design 完全没提。
- **D4 在本次语境下站不住**：每点偏差 ≤1% 算得对，但取舍论证拿错了尺子——它对比的是
  P36 那个 13.4m 宽的区间，而本 change 的产物（仅真检测下的 hd）区间只有 ~4.9m 宽，
  且偏差按球场尺寸**系统性**分组（4 场 104m 一律放大、6 场 106m 一律缩小），
  跨 20 场折合约 2.4m 的系统性散布。而「复杂度不成比例」的理由不成立：spec 已经强制
  `meta.pitchMeters` 入库，指标层拿到它只差一次乘法。

**其余**：D1/D5/D6/D8 方向可用，但有若干数字错误与遗漏（见 P3 与第 5 节）。
两处值得单独提：**D2 给外推标记选的字段形状在 JSON 往返后会静默消失**（P1-5，
与 spec「SHALL NOT 静默丢弃该标记」直接冲突）；**ball 的 `is_detected` 完全没被 D2 覆盖**
是实质性缺口（P2-6）。

**问题计数**：P1 × 5，P2 × 6，P3 × 5。

## 3. 问题清单

### P1（阻断）——不修就无法正确实现 / 会导致方向性错误

---

#### P1-1 ｜ D2 的「可比性」论证不成立：trim1 是顺序统计量，跳过外推点换来的不是可比，而是另一种不可比

**问题**

design D2 主张：Metrica 的缺失是 `null`（不参与计算），SkillCorner 的外推点「看起来正常
但是假的」，所以默认跳过外推点 → **两侧可比**。这个论证忽略了一个事实：**trim1 的值本身
取决于参与计算的人数 n**。跳过外推点会让 n 从恒定的 10 变成浮动的 0–10，而 Metrica 侧
永远是 10。于是两侧跑的不是同一个估计量。

**证据**

1. Metrica 侧每帧恒定 10 名非门将——直接从主仓库转换产物实测：

   ```
   game1: frames=29002  home outfield n dist: {10: 29002}
   game2: frames=28232  home outfield n dist: {10: 28232}
   ```

2. SkillCorner（场 1874553，5Hz 抽样 22,122 帧）「仅真检测」下主队非门将人数分布：
   `0:3054, 1:6, 2:215, 3:429, 4:852, 5:1858, 6:3196, 7:3286, 8:3340, 9:3368, 10:2518`，
   **中位数 8**；客队几乎对称（`0:3065 … 10:1810`）。两队各自低于 7 的帧各占 ~43%，
   而「两队都 ≥7」的帧占 45%——说明两队的检测率强相关（同好同坏）。

3. 在**同一批帧**上分解口径差（场 1874553，主队纵深 trim1，均值）：

   | 口径 | 均值 | n |
   |---|---|---|
   | A：`trim1(全部 10 点)` | **24.09 m** | 22122 |
   | B：`trim1(仅真检测子集)` | **15.62 m** | 12512（子集中位数 8） |
   | C*：`trim1(从全部 10 点里随机取 7)`，20 次平均 | **18.93 m** | 22122 |
   | Cm：`trim1(从全部 10 点里随机取 n=该帧真检测数)`，20 次平均 | **18.88 m** | 12512 |

   → **机械 n 效应（A→Cm）= 5.21 m**；**超出 n 的「检测」效应（Cm→B）= 3.26 m**。

4. 直接对照（只取「恰好 7 个真检测」的 3286 帧，n 完全对齐）：

   | 同一批帧 | 均值 |
   |---|---|
   | `trim1(那 7 个真检测点)` | **13.05 m** |
   | `trim1(从同样 10 点里随机取 7)` | **20.09 m** |
   | `trim1(同样 10 点全取)` | 25.64 m |

   即使 n 锁死为 7，真检测点仍比随机子集**系统性更紧凑** 7.0 m。原因是检测本身有选择性
   （远离镜头/被遮挡的球员更容易变成外推），所以「仅真检测」子集不是「全员的无偏抽样」。

**结论**：design D2 表格里「全点 20.5–28.8 → 仅真检测 12.6–17.5，差 ~7m（约 40%）」
把它归因为「外推启发式 vs 真实观测」。实测表明这个差**主要由 n 效应构成（5.2/8.5 ≈ 61%）**，
而 n 效应是**转换器/口径自己造出来的**，不是数据里的信号。把这个数当「真实侧观测范围」
去和引擎（恒 10 人）对比，是把一个口径伪影当成了物理量。

**修法（三选一，建议 (i)）**

- **(i) 让估计量对 n 不变**：把 trim1 从「掐固定 1 人」改成「掐固定**比例**」，例如每侧
  `max(1, round(0.1·n))`。n=10 时退化为现有的掐 1 人（**保持 P36 基线口径不变**），
  n=7 时掐 1 人、n=4 时掐 1 人（或直接用插值分位 + 明确的约定写死）。
  注意 P36 D3 明确否决过 `p10–p90`，理由是「约定歧义」——所以选比例修剪时**必须把
  离散化规则一句话写死**（如「每侧掐 `max(1, round(0.1n))` 人」），并由测试守护。
- **(ii) 锁 n**：只在「真检测数 == 10」的帧上计算。代价极大——实测该口径下几乎无帧可用。
- **(iii) 若两侧都改用「掐比例」**：必须**同步重算 P36 基线**（口径变更 → `hashMetricsModule`
  陈旧性校验会强制），并且设计里要写明这是本 change 已知的口径变更。
- **无论选哪个，都必须把上面第 3/4 条的「n 效应 vs 检测效应」分解作为报告项输出**
  （它正是 design 想要的「报告对照」，但比 design 提的「全点 vs 仅真检测」更有信息量：
  后者把两个混淆的效应混在一起）。**并且这一步应该在**立项期**就做**——我在单场上
  几分钟就跑完了；design 把它推给实现期（P1.5），代价是 D2 的结论建立在未分解的数字上。

#### P1-2 ｜ D2 点名「最大风险」的量级被低估且定位错了：minFrames 不是真风险，帧密度和价值才是

**问题**

design 把风险写成「某队可能只剩 4–5 人 → 低于 7 → 丢帧 → 某些窗口可能落入
`minFrames=100` 之下而整窗消失」，并据此说「每窗 236–932 帧，仍远超 minFrames=100，
**切窗不受影响**」。这条推理有三处错：

**(a) `minFrames` 管不到这件事。** `cutWindows`（`viewer/match-metrics.js:112-123`）
过滤的是**原始帧数**，SkillCorner 每 300s 窗的原始帧数实测 995–1326（远超 100）；
「仅真检测」的筛选发生在 `windowMetrics` 内部（`match-metrics.js:193-210`），
它只在 `frameCount === 0` 时返回 `null`。所以「窗口因帧数不足而消失」这条路径
**在数值上不可能发生**，design 的风险描述指向了一个不会触发的机制。

**(b) 真正的失败模式是「窗口产出 null 后链路崩/静默丢」，而代码没处理。**
`tools/benchmark-baseline.mjs:57` 是 `metrics.push(windowMetrics(w))`，可以是 `null`；
`match-metrics.js:266` 是 `metricsList.map((m) => m[k])`——**m 为 null 时抛 TypeError**。
Metrica 侧因每窗恒 1500 帧，这条路径从未被走到；D2 引入了「整窗 0 可用帧」的可能，
却没有在实现计划里处理这个新失败模式。必须在 P2.1 一并修（`windowMetrics` 为 null 时
记录并跳过，而不是让 `summarizeWindowMetrics` 崩）。

**(c) 「超过 minFrames 就没问题」是量纲错误。** `minFrames` 是**丢帧安全网**，不是
统计功效阈值。实测「仅真检测」下每窗可用帧：

```
场 1874553（拼接后 T=6017s，5Hz，300s 窗 / 900s 步长）：
 窗起点    原始帧  全点可用  仅真检测可用
 0         1326    1326      236
 900       1178    1178      376
 1800       995     995      552
 2700       995     995      536
 3600      1150    1150      419
 4500      1126    1126      459
 5400      1056    1056      455
```

对比 P36 基线的 Metrica：`frameCount {avg:1500, min:1500, max:1500}`——**每个窗恒 1500 帧**。
即本 change 的产物是「139 个窗，每窗 ~400 个有效帧」，而对照物是「13 个窗，每窗 1500 个帧」。
**每窗样本量降到 1/4～1/6**，直接放大窗口均值的方差，进而放大 D7 门所依赖的 min/max 区间宽度。
design 只说了「可用帧降到 45%」，没有把它换算成「每窗有效样本」这个真正影响结论的量。

**(d) 数字本身取自一个有 bug 的探针。** 见 P3-2：`236–932` 里的 `932` 来自 archive 里
**未实现 D3 要求的 shift** 的 `analyze.py`（该探针把 P1/P2 叠在一起，窗 2700 收了 1853 帧）。
按 D3 的拼接口径，真实范围是 **236–552**。

**修法**

1. 把任务 P1.5 从「实现期量化」**提到 P0**（或至少与 D2 拍板同时）：在 20 场上跑
   ——(i) 每窗可用帧分布、(ii) 因 `MIN_OUTFIELD_PLAYERS` 丢弃的帧占比、(iii) 每队检测数
   分布、(iv) P1-1 的 n 效应分解。这四件事都不依赖转换器落地，用探针脚本就能做完。
2. 在 design 里把风险改写为「每窗有效帧从 1500 降到 ~400，窗口均值的抽样方差上升 X%」，
   并给出**判据**：若中位每窗可用帧 < 500，则须重新考虑默认口径（回到备选 (a)，或改用
   P1-1 的 n 不变量）。
3. P2.1 必须显式处理 `windowMetrics` 返回 null 的路径，并**逐窗记录「可用帧数」**
   （design 说的 `ok_det`），否则「139 个窗」这个数字无法审计——读者看不出其中有多少窗
   其实是「勉强可用」。
4. 顺带：`benchmark-baseline.mjs:55` 的 `durationSec = w.length / hz` 在 SkillCorner 上会
   算出 ~199s（一个 300s 窗），把「帧数」当成了「时长」。这字段对 Metrica 是对的
   （无缺口），对本 change 会变成误导性数字。改成记录窗口的名义跨度（`sizeSec`），
   或改名以示区分。

#### P1-3 ｜ D7 的 half-split 作为「硬门」在任何样本量下都只有约 25% 通过率——它不是门，是掷硬币

**问题**

D7 把「20 场随机分半，用一半导出的观测范围检查另一半的窗口**全部**落得进去」立为**硬门**
（失败即红）。对 min/max 包含门，这个条件的通过概率有闭式解：

```
P(n 个样本的 min/max 容纳全部 m 个另一样本) = n(n−1) / ((n+m)(n+m−1))
```

**证据**

| 每半场次数 | 每半窗口数 n=m | P(通过) |
|---|---|---|
| 2 | 14 | 0.241 |
| 5 | 35 | 0.246 |
| 10（本 change） | 70 | **0.248** |
| 20 | 140 | 0.249 |
| 200 | 1400 | 0.250 |

蒙特卡洛（n=m=70，20,000 次）实测 **0.247**，与解析解一致。
**概率与样本量无关**——这正是「用某些样本的范围去包含另一些样本」这一操作的内在性质，
不是数据不够。issue #78 的原始现象（「game1 的范围只容纳 game2 的 3/6 个窗口」）
就是这件事，P36 D5 已经诊断过并因此把标尺降级为报告期；**本 change 把同一个结构重新
立成了红绿门**。

**design 的两条相关论证也是错的：**

- 「LOO 更严格（19 场的范围更窄），**若通过则 half-split 必然通过**」
  → 见下：LOO 的全绿概率 0.128 < half-split 的 0.248，LOO **比 half-split 更容易红**。
  两者不是包含关系，是两个不同的（且同样脆的）判据。

- 「LOO 会因**单个异常场**而失败，不适合当门；单场异常**不影响** half-split（只影响 LOO）」
  → **这是断言，不是论证，而且不成立**。一场异常必然落在某一半里：若它落在 A 半，它撑大
  A 的范围（B 更容易被容纳，门更松）；若它落在 B 半，它把 B 的值推到 A 的范围之外（门更紧）。
  即异常场对 half-split 的影响是**方向随机的、幅度等于异常幅度**——既不免疫，也不可控。
  LOO 之所以看起来更脆，只是因为它每折的对照样本更少（7 个点 vs 70 个点），
  不是因为异常场对它的影响机制不同。

**修法（建议 B 或 C）**

- **A. 容差带**：A 半范围 ± ε（每指标预先注册一个 ε）。模拟：ε=+3m → P≈0.60；
  ε=+6m → P≈0.85。**ε 必须在看到结果前定死并记录**，否则它就是一个调参旋钮。
- **B. 换成有明确失败预算的统计量**：例如「B 半 ≥95% 的窗口落在 A 半范围内」，
  或「A 半的 p5–p95 容纳 B 半的 p5–p95」。通过率由此可控。
- **C（推荐，最省事）**：**换判据方向**——不问「A 是否包含 B」，而问「两半的摘要是否
  统计上不可区分」（如 |median_A − median_B| 落在预先注册的带宽内，或置换检验 α=0.05）。
  这类判据的假阳性率按构造是已知的，这才是「门」需要的性质。
- **无论选哪个**：门的**零分布必须先被刻画再宣布为硬门**。一个在「数据完全正常」时
  通过率 25% 的门，会在首日变红、然后被关掉——那会直接破坏项目「verify 全绿才收尾」
  的既有流程。
- 若采纳，spec 里那条 scenario（「一半导出的范围容纳另一半的窗口；不满足则验证失败」）
  必须在本 change 内一并改掉，否则 spec 与实现分叉。

#### P1-4 ｜ D7 的失败语义未定义，而 change 自身的合入前提是「CI 绿」——三者互锁

**问题**

D7 只写了「half-split 通过 = 绿，不通过 = 红」，没写红**意味着什么**：
是数据问题（异常场）、口径问题（P1-1 的估计量错配）、还是真发现（足球本身重尾）？
三种含义对应三种完全不同的动作，design 一种都没给。

同时 tasks P3.4 写「实测运行并记录结果：20 场 half-split 是否通过」——即 change 自己
**已经准备好记录一次红灯**；而 P4.5 的合入前置条件是「CI 绿」。给定 P1-3（正常数据的
通过率 ~25%），最可能的结局是：P3.4 记录到红 → P4.5 无法合入 → change 卡死。

**design 的核心辩护也不成立**：D7 说「这是真实侧内部的自洽性检验，不涉及引擎，
因此不受『校准目标未定』的阻塞——可以立为硬门」。这个辩护把「不受什么阻塞」搞错了对象：
它不受**校准目标**阻塞，但它受**门的零分布未被刻画**阻塞。后者与校准目标无关，
是纯粹的统计学前提。P36 D5b 用户拍板「校准目标未定前只报警不判定」的实质理由
（在不知道判据分布时先建立观测能力），在这里同样适用。

**修法**

1. 本 change 把交叉验证落成**报告项**：打印 half-split 与 LOO 的数字、逐指标落空率、
   哪个指标最易落空。这是有真实诊断价值的（design D7 自己也这么说 LOO）。
2. **在后续 change 里升格为门**，前置条件是：(a) 零分布已刻画（用置换/自助法给出
   正常数据下的通过率）；(b) 容差 ε 已预先注册；(c) 失败语义已定义（三种原因各自的
   处置动作）。这三件事都是小工作量，但要单独做、单独审。
3. 如果用户坚持本 change 就要门，那它必须是**容差门**，且失败信息必须能区分
   「数据异常」/「口径错配」/「真重尾」。在 P1-1 未解决前，这个区分做不到。

#### P1-5 ｜ D2 指定的字段形状（`players[i].extrapolated = true`）在 JSON 序列化后会静默消失——与 spec 的核心要求直接冲突

**问题**

design D2 第 1 条写：转换器把标记写进帧序列，形如 `players[i].extrapolated = true`。
但帧序列里的 `players[i]` 是**数组**（`[x, y]`，见 `match-metrics.js:9` 的 schema 注释与
`fromTrackingFrame` 的 `p[0]/p[1]`）。**给数组挂自定义属性在 JSON 往返后必然丢失**——
实测：

```js
const p = [0.5, 0.3]; p.extrapolated = true;
JSON.stringify({players: [p]})   // → {"players":[[0.5,0.3]]}
JSON.parse(...).players[0].extrapolated   // → undefined
```

而转换器的产物**就是要落盘成 JSON 再读回来的**（`viewer/data/*.json`，由
`fromTrackingFrame` 消费）。所以按 D2 的字面实现，外推标记会在**写出文件的那一刻**
消失，下游拿到的是一个「看起来完全正常」的帧序列——**这正是 spec 里那条
「SHALL NOT 静默丢弃质量标记」要求禁止的结果**，而且是所有失败模式里最难查的一种：
不报错、不告警、只是标记没了。

design 并非没有意识到形状问题——tasks P1.3 把它列为待定项（「建议 `[x,y,extrapolated?]`
或并列 `extrapolatedIds` 数组——选择须考虑 `fromTrackingFrame` 的改动量与向后兼容」），
但 **design D2 的正文已经先行把答案写成了 `players[i].extrapolated = true`**，
而 D2 是「待用户确认」的决策项。两者不一致，且正文那个是错的。

**修法**

- 把 D2 正文改成引用 P1.3 的待定项，或直接写定一种**能落盘**的形状。两种可行：

  | 方案 | 形状 | `fromTrackingFrame` 改动 | 兼容性 |
  |---|---|---|---|
  | **A（推荐）** | `players[i] = [x, y, 1]`（第三位=1 表示外推） | 需读 `p[2]`，把 `extrapolated: p[2] === 1` 放进统一帧 | Metrica 产物是 `[x,y]`，`p[2]` 为 `undefined` → 自然表示「非外推」，**向后兼容** |
  | B | 并列 `extrapolatedIds: [id, ...]` | 需在 `fromTrackingFrame` 里额外查一个集合 | 老产物无此字段 → 空集，兼容 |

- **A 的额外好处**：`[x,y]` 与 `[x,y,1]` 在同一个数组里，读者无法忽略它的存在；
  B 的并列数组容易被漏读（schema 里多一个可选键，谁都不会注意到）。
- **无论选哪个**：P2.2 的口径守护测试**必须包含一次 JSON 往返**
  （`JSON.parse(JSON.stringify(frames))`）后再断言标记仍在——否则测试会在内存对象上通过，
  而真实链路丢标记。这是本项目 P28/P36 已经总结过的教训（「守卫要绑模块执行层」）
  在序列化边界上的同一条应用。

> **实现侧备注**：审阅期间出现的未跟踪文件 `tools/convert-skillcorner-to-frames.mjs`
> 采用的是 A 方案（`players[toId(slot)] = extrapolated ? [x, y, EXTRAPOLATED_FLAG] : norm`），
> 球的处理则在 `ballFill` 上取值 `'extrapolated'`（对应本报告 P2-6）。这两处**独立绕开了
> 本报告指出的缺陷**——但 D2 正文与 spec 仍应改，否则设计文档与实现分叉，
> 下一个照文档实现的人会踩回来。

#### P2-1 ｜ D3：接缝间隙实测为 0.00s，不是 190s；且「同构」说法过头，shift 的稳健性未论证

**问题 a（事实错误）**：design 说「拼接处（半场交界）会产生一个 ~190s 的正向间隙」。

实测（场 1874553）：P1 末帧原始时钟 2890.90，P2 首帧原始 2700.00，shift=190.90 后为
2890.90 → **接缝间隙 0.00s**。190.9 是**回跳量**，不是**间隙**；平移恰好把回跳补平，
接缝处两帧落在同一瞬间。design 把「回跳 190.9s」这个观察直接搬成了「间隙 ~190s」。

**问题 b（与风险节的账目冲突）**：design 风险节说「61 处间隙，最大 143s，合计 1599s，
占全长约 27%」。实测这 1599s **全部来自回放/特写**，接缝贡献 0。结论数值仍大致成立
（1599/6017 = 26.6%），但归因是错的，而读者会以为其中含一段中场。

**问题 c（同构过头）**：design 说「压缩到一点反而保持同构」。核实：引擎侧确实
**完全没有中场**——`engine/src/lib.rs:251` `match_duration_seconds: 5400.0`，主循环
`while t < dur { tick(...) }`（2388–2391）连续跑完，全场唯一 whistle 在 `dur`
（2430）且 detail 是 `"half_time"`——引擎把**终场**哨标成了 half_time，中场根本不存在。
所以「5400s 不含中场死时间」**为真**。但「同构」只能到此为止：引擎不建模半场，
SkillCorner 拼接后仍保留半场切换那一刻（只是把间隔压成 0）；真实 P1 实测 2891s、
引擎半程是 2700s，**相位在 P1 内部就已经错开**。这不影响 min/max 区间（窗口只是固定
偏移的 300s 切片），但 design 不该声称相位同构。建议把「保持同构」改成
「两侧都不含中场死时间；窗口偏移仍按名义秒数取，故相位不严格对齐」。

**问题 d（shift 稳健性——真问题）**：`shift = max(P1.t) − min(P2.t)` 用的是**观测极值**。
只要 P1 尾部或 P2 头部有缺失（本数据 27% 的时段无帧，首尾完全可能缺），缺失的时长会
被静默吸收进 shift，接缝间隙随之非零，而没有任何记录。

实测证据：场 1886347（104m）在**截断**下载上算出的 shift 是 **77.9s**（而非 ~190s），
因为 P2 尾部被截断——说明这个量确实对「观测到的极值」敏感，不是常数。

**修法（便宜且确定）**：源数据本来就有权威边界——`match.json.match_periods[]`，
实测 **20 场全部有 2 条**，每条带 `period` / `start_frame` / `end_frame` /
`duration_frames` / `duration_minutes`：

```json
[{"period":1,"start_frame":10,"end_frame":28990,"duration_frames":28980,"duration_minutes":48.3},
 {"period":2,"start_frame":29000,"end_frame":60300,"duration_frames":31300,"duration_minutes":52.17}]
```

用 `match_periods` 定边界（或至少用它交叉校验）、并把**结果接缝间隙**写进
`meta.coverage`，问题就消失了。**design/tasks/spec 三处都没提 `match_periods`**——
这是本 change 最实质的一处遗漏（见第 5 节）。

> **实现侧备注**：审阅期间出现的 `tools/convert-skillcorner-to-frames.mjs` 的
> `stitchTimeline` 同样采用观测极值（`Math.max(...p1.map(f => f.clock)) − Math.min(...)`），
> 因此**这条问题在实现里仍然存在**——它加了 `out.sort()` 兜底（防回跳），但排序解决不了
> 「极值缺帧 → shift 偏小 → 接缝留缝」的问题。建议按上面改用 `match_periods`，
> 并把 `shiftSec` 改成「由 `match_periods` 推出」+「由观测极值算出」两个值并列记录，
> 二者不一致即说明该场首尾有缺口——这本身就是一个有用的质量信号。

#### P2-2 ｜ D4：每点偏差算得对，但取舍的「尺子」拿错了——本 change 自己的区间只有 ~4.9m 宽

**问题**

design 说偏差「量级（<1%，约 0.25m）远小于本 change 要看的信号（数十米）与口径分歧
（D2 的 ~7m）」。逐点算：104m → 105/104 = 1.0096（25.0m 读成 25.24m）；
106m → 105/106 = 0.9906（25.0m 读成 24.76m）。**「≤1%」准确**。

但取舍用的是**点值**的尺子，而这个 change 的产物是**区间**。把尺子换成区间：

| 对照物 | 区间宽度 | ±0.25m 占宽度 |
|---|---|---|
| P36 Metrica hd [16.16, 29.57] | 13.41 m | 1.9% |
| 本 change 仅真检测 hd [12.6, 17.5]（场 1874553） | **4.9 m** | **~5%** |

而且偏差**按球场尺寸分组、方向固定**：4 场 104m 一律放大、6 场 106m 一律缩小
（**注意：design 写的「104 有 5 场、106 有 5 场、105 有 10 场」是错的，实测 4/10/6**）。
跨 20 场折算，这些系统性偏差贡献约 **±0.25m × 两侧 ≈ 2.4m 的散布**，落在一个 ~4.9m 宽的
区间里。**对「导出区间当门槛」这个用途来说，这不是噪声，是门槛本身的偏置。**

**「复杂度不成比例」的论证不成立**：spec 已经强制 `meta.pitchMeters` 逐场入库
（「球场尺寸 SHALL 逐场记录」）。指标层拿到它只差一次乘法——`teamShape` 里的
`p.x * PITCH_LENGTH_M` 改成 `p.x * (pitchMeters?.[0] ?? PITCH_LENGTH_M)`，
把 `pitchMeters` 从帧/窗口透传进来即可。这不是「指标层、基线、引擎侧全部支持可变场地」，
是给同一个函数加一个可选参数。

**修法（二选一，建议 A）**

- **A**：把 `pitchMeters` 透传到 `frameMetrics`/`teamShape`，换算用逐场尺寸。
  P36 口径在「引擎侧与 Metrica（105×68）」上**完全不变**，改动是纯增量的。
- **B**：若坚持统一按 105×68，则必须把偏差**相对本 change 自己的区间宽度**量化，
  并作为**预先声明的扰动预算**写入基线 `declarations`，而不是只写「<1%」。

#### P2-3 ｜ D5：「与 P36 可比」只在窗口定义上成立，在帧密度上不成立；且 140 窗实为 139

**问题 a（数字）**：design/tasks 多处写「20 场 **140 窗**」。实测按
`match_periods` 推的总时长，900s 步长下：**19 场 7 窗、1 场 6 窗（2013725，T≈5679s）
= 139 窗**。300s 步长同理不是 400 而是 **384**（5 场 20 窗、14 场 19 窗、1 场 18 窗）。

**问题 b（可比性的边界）**：design 的理由是「900s 步长让新旧基线可以直接对照
（样本从 13 窗扩到 140 窗后，观测范围是变宽还是变窄本身就是一个重要发现）」。
但两侧的**每窗有效帧密度**差了 3–6 倍（Metrica 恒 1500 / SkillCorner 仅真检测 ~236–552）。
区间变宽/变窄的候选机制至少有三个：① 样本增加暴露更多变异（design 已声明）；
② 每窗样本量下降导致窗口均值方差上升；③ 口径错配（P1-1）。design 只预告了 ①，
实际最可能主导的是 ② 和 ③。**「新旧基线可直接对照」这句需要降级为「窗口定义相同，
帧密度不同」。**

**修法**：见 P1-2 的修法 2/3；并在基线 `declarations` 里把两个数据集的
「窗数 / 每窗有效帧（中位与全距）」并列打印。

#### P2-4 ｜ D6 声称「跨数据集可比性这个更有价值的诊断」，但没有把它操作化；而它恰恰是本 change 的价值主张

**问题**

D6 说分开报告「保留了『跨数据集可比性』这个更有价值的诊断（留一交叉验证的跨集版本）」，
但全篇没有定义这个诊断是什么、输出什么、怎么读。spec 只要求「若给出合并包络，
SHALL 显式标注为参考」——合并包络是两区间取并，没有任何统计含义。

而真正有信息量的检查是：**Metrica（25Hz 人工标注、恒 10 人/帧）导出的范围，是否落在
SkillCorner（10fps CV、检测中位数 8 人/帧）导出的范围内？** 这是本 change 相对
「再接 2 场 Metrica」的唯一增量价值。给定 P1-1 与 P1-2，预期答案是「不落」——
那本身是一个必须被记录、且会直接影响 D2 拍板的发现。

同样地，**D7 的门只在 SkillCorner 内部，对跨数据集可比性零信息**。

**修法**：把「Metrica 范围 vs SkillCorner 范围」作为一条**显式的报告项**输出
（逐指标给出方向与余量，复用 `benchmark-compare.mjs` 的 `compareMetric` 即可），
并把它的预期结果写进 design（预期不重叠，因为帧密度与估计量都不同）。

#### P2-5 ｜ D2 的三个备选方案在**错误的轴上**——没有一个触及 n 错配

**问题**

(a) 全点口径 + 报告对照；(b) 仅真检测、不报告全点；(c) 默认过滤 + 透传 + 对照。
三者变化的都是**「用不用外推点」**；没有一个变化**「估计量如何控制 n」**。
给定 P1-1，三个选项都解决不了它们声称要解决的问题——(c) 的推荐理由
（「两侧可比」）本身不成立。

另外 design 对 (b) 的描述「最干净，但看不到外推的影响量级」把代价说成了信息量问题；
真正的代价是 (b) 连 (c) 那点「对照」都没有，而对照恰恰是唯一能暴露口径错配的东西。

**修法**：选项集补上第四个轴——**估计量形态**（固定修剪 vs 比例修剪 vs 锁 n）——
并把它与「用不用外推点」做叉积。推荐组合：**默认 = 比例修剪 + 仅真检测 + 透传**，
对照 = 同估计量下的全点结果 + **随机 k 子集的控制**（P1-1 第 3/4 条的方法）。

#### P2-6 ｜ **球**的 `is_detected` 完全未被 D2 覆盖——同一个口径分叉在球上原样重演

**问题**

D2 只处理 `player_data[].is_detected`。但 `ball_data` **也有 `is_detected`**，实测
在**有球坐标的帧里 17.7% 是外推值**（场 1874553：有坐标 44,244 帧，真检测 36,401 = 82.3%）。

而指标层的「原始球帧」口径（P36 D2 的审阅 P2-6）**只认 `ballFill`**
（`match-metrics.js:79-81` `isRawBallFrame(frame) { return frame.ballFill == null }`）。
`ballFill` 是 Metrica 转换器的**缺失补全**标记，语义是「这一帧原本没有球坐标」。
SkillCorner 的球坐标**从不缺失**（实测：44,244 个有 `player_data` 的帧**全部**有球坐标；
16,057 个空帧**全部**没有球坐标——所以球坐标的有无与 `player_data` 的有无完全同步），
**缺的只是「是不是真检测」**——这是 `ballFill` 表达不了的另一种来源。

后果：在 SkillCorner 上，「只用原始球帧」这个主口径会把 17.7% 的**外推球位**当成
真实观测，`possessionProxy`（控球代理）、`ballDist`、`elasticity` 三个量全部受污染。
design 反复引用 P36 的「口径分叉 = 数字不可比」，却在球上放过了同一件事。

**证据**（场 1874553 实测）：

```
有 player_data 的帧: 44244，其中球有坐标: 44244 (100%)，球真检测: 36401 (82.3%)
空 player_data 的帧: 16057，其中有球坐标: 0
```

即：SkillCorner 的球**不存在缺失**（`ballFill` 永远不会被触发），
**只存在外推**（`ballFill` 无法表达）。

**修法**

- 转换器把球的来源也如实透传。两种可行做法：
  **(i)** 扩 `ballFill` 的取值域（`ballFill: 'extrapolated'`）——**指标层零改动**
  （`isRawBallFrame` 只判 `ballFill == null`，`'extrapolated'` 自动落进「非原始」），
  代价是 `ballFill` 这个字段名同时表达「补全到某球员」和「源数据外推」两种语义；
  **(ii)** 加并列字段（`ballExtrapolated: true`）——语义更干净，但**需要同步改
  `isRawBallFrame`**，否则外推球会被当原始观测。
- spec 的「转换器保留源数据的质量标记」requirement 里补一条：**球员与球两处都要透传**。
- `meta.coverage` 增加 **`ballExtrapolatedPct`**——现有字段只有 `ballMissingPct`，
  在 SkillCorner 上会恒为 0，读者会误以为球的质量完美。

> **实现侧备注**：审阅期间出现的 `tools/convert-skillcorner-to-frames.mjs` 采用了做法 (i)
> （第 337 行 `ballFill = 'extrapolated'`，并在注释里说明了这正是为了让

### P3（次要）——表述、完备性、可维护性

**P3-1 ｜ 三处数字错误（均可一键复算）**

| design 原文 | 实测 | 位置 |
|---|---|---|
| `pitch_length` 104/105/106 = **5/10/5** 场 | **4/10/6** 场 | design 上下文 #2、D4 |

第一项尤其值得修：D4 的整个论证依赖「三种尺寸的场次数」，而 design 给的分布

说成了对称的。

**P3-2 ｜ 「每窗 236–932 帧」取自一个与 D3 矛盾的探针；归档探针内部不自洽**

`reviews/probes/analyze.py`（= probe1）**完全没有实现 design D3 要求的半场平移**，
P1/P2 的时间戳直接叠在一起，于是窗 2700 收了 1853 帧（300s / 5Hz 的物理上限是 1500），
其「仅真检测可用」正是 **932**；`analyze2.py`（= probe2）实现了平移，同一窗是 536。

design D2 引用的是**未平移**的 932，而同一节表格里的指标范围（20.5–28.8 / 12.6–17.5）
又与**已平移**的 probe2 一致——**design 在同一段里混用了两条不同时间轴的探针输出**。

`reviews/probes/README.md` 把两支脚本并列为「让 design.md 里的数字可复现」，
但没说明哪支产出哪个数字，读者无法判断该复现哪个。

**修法**：给 `analyze.py` 补上平移（或删掉 design 里的 932，改为 236–552）；
在 probes/README 里逐条标注「design 的哪个数字出自哪支脚本的哪一段」。**归档探针是
「可复现」承诺的载体，它内部不自洽会让这个承诺失效。**

**P3-3 ｜ D2 表格里「仅真检测」的 gap 上界不可复现**

design D2 表：仅真检测 `gap 3.9 – 5.3 m`。按 probe2（已平移）实跑：
`gap_det = 6.6, 4.4, 4.7, 4.8, 3.9, 4.8, 5.3` → 全距 **3.9 – 6.6**。
`5.3` 是末窗的值，不是最小值以外那个极值。两处探针都给不出 `5.3` 这个上界。

**P3-4 ｜ 语料里有一场 `status = not_started`，design/tasks 未提任何过滤或标注**

20 场里 **1953632 的 `status` 是 `"not_started"`**（比分 1-1，其余 19 场是 `closed`）。
它的 tracking 有完整两个半场，会被静默计入 20 场。

**修法**：要么按 `status` 排除并记录理由，要么在基线里逐场记录 `status` 并声明
「不按 status 过滤」——但**必须显式**，不能不说。这是 P36 立下的「未覆盖维度须显式声明」
（`declarations.notCovered`）的同一条规矩。

**P3-5 ｜ P1.6 的「两转换器产物结构相同」断言与 P1.3 的外推标记互斥**

tasks P1.6 要求「一条断言同时跑 Metrica 与 SkillCorner 转换器，断言两者产物结构相同」。
但 P1.3 要给 SkillCorner 的 `players[i]` 加外推标记，Metrica 没有这个字段——
两者产物**不可能结构相同**。

**修法**：把断言写成**公共核 + 可选扩展**：`{ meta, frames:[{t, players, ball}] }` 是公共核，
逐字段断言；扩展字段（外推标记）断言「存在时形状正确、不存在时不报错」。
否则 P1.6 这条任务要么写不出来，要么会在实现时被悄悄降级成弱断言。

## 4. 对四项审阅重点的逐条回应

### D2 外推点口径 —— **站不住**

- **「可比性」论证不成立**。核心反证：trim1 是顺序统计量，值依赖 n；Metrica 恒 10，
  SkillCorner 仅真检测中位数 8、范围 0–10。同一批帧上实测分解：
  全 10 点 24.09m → 随机取 n（n=该帧检测数）18.88m → 仅真检测 15.62m。
  「仅真检测」相对「全点」的 8.5m 差里，**5.2m 是纯 n 效应**。
  锁死 n=7 再比（同一批帧）：真检测点 13.05m vs 随机 7 点 20.09m——仍有 7.0m 差，
  但那部分来自**检测的选择性**（被遮挡者更易外推），不是「外推启发式 vs 观测」。
  两种效应 design 都没识别。
- **最大风险被低估且定位错**：`minFrames=100` 这条路径对本数据**不可能触发**
  （原始帧 995–1326/窗）；真正的代价是每窗有效帧从 1500 降到 ~236–552（1/4～1/6），
  直接放大 D7 所依赖的区间宽度。另外 `windowMetrics` 返回 null 的路径
  （`benchmark-baseline.mjs:57` → `match-metrics.js:266`）未被处理，会抛 TypeError。
- **更早能做的判断有**：P1-1 的两张分解表我在单场几分钟内跑完；design 把它推给实现期
  （P1.5）是不必要的。**建议把它作为 D2 拍板的前置输入。**
- **三个备选的取舍没讲清「轴」**：(a)/(b)/(c) 只变「用不用外推点」，
  不变「估计量如何控制 n」；推荐项 (c) 的所有理由都建立在那个不成立的论证上。

### D3 时间轴拼接 —— **部分站得住**

- ✅ **「引擎 5400s 不含中场」核实为真**：`engine/src/lib.rs:251` 默认 5400.0，
  主循环 2388–2391 连续跑到 `dur`，**全场无中场哨**；唯一 whistle 在 `dur`（2430）
  且 detail 标为 `"half_time"`（引擎把终场哨叫 half_time）。不换边亦属实
  （循环里没有任何换边逻辑）。design 对 P36 D5b 的引用**成立**。
- ❌ **「拼接处会产生 ~190s 正向间隙」是错的**：实测接缝间隙 **0.00s**。
  190.9s 是回跳量，平移恰好补平。
- ❌ **「压缩到一点保持同构」过头**：引擎不建模半场，真实 P1 实测 2891s，
  相位在 P1 内部即错开。对 min/max 无害，但表述应改。
- ⚠️ **61 处缺口 / 1599s / 27% 的账目正确但归因错**：1599s 全来自回放/特写，
  接缝贡献 0。
- ❌ **shift 由观测极值算出，不稳**：P1 尾或 P2 头有缺口会把缺失时长静默吸收进 shift
  （截断场次的 shift 实测 77.9s vs 本应 ~190s）。**源数据已有权威边界
  `match.json.match_periods`（20 场全有，含 `start_frame`/`end_frame`/`duration_frames`），
  design/tasks/spec 三处都没提**——这是本 change 最实质的遗漏。

### D4 球场尺寸偏差 —— **在本 change 语境下站不住**

- 逐点算术正确：104m → 放大 0.96%，106m → 缩小 0.94%，**「≤1%」属实**。
- 但取舍拿错了尺子：偏差要对照的是**本 change 自己的区间宽度**（仅真检测 hd 约
  4.9m 宽，±0.25m ≈ 5%），而不是 P36 的 13.4m。且偏差**按尺寸系统性分组、方向固定**，
  跨 20 场折算约 ±2.4m 的系统性散布——对一个要被当作门槛的区间来说，这是偏置不是噪声。
- 「复杂度与收益不成比例」不成立：spec 已强制 `meta.pitchMeters` 入库，
  指标层拿到它只差一次乘法（`teamShape` 里 `PITCH_LENGTH_M` 换成逐场值），
  P36 口径在 105×68 的数据上完全不变。
- 场次分布也写错了：**4/10/6**，不是 5/10/5。

### D7 half-split 硬门 —— **站不住**

- **门的性质错了**：min/max 包含门的通过率 `n(n−1)/((n+m)(n+m−1))`，n=m=70 时 **0.248**，
  蒙特卡洛 0.247；**与样本量无关**（2 场/半 0.241，200 场/半 0.250）。
  这不是「样本还不够」的问题，是判据形态的问题。
- **「单场异常不影响 half-split（只影响 LOO）」是断言且错误**：异常场必落在某一半，
  影响方向随机（撑大本半 → 门松；撑破对半 → 门紧）。
- **「LOO 更严格，若通过则 half-split 必通过」错误**：LOO 全绿概率 0.128，
  half-split 0.248——LOO 更容易红，两者无包含关系。
- **失败语义未定义**，且与 P4.5 的「CI 绿」前提互锁：change 自己准备好记录红灯，
  但红灯时无法合入。design 的辩护（「不受校准目标未定阻塞」）混淆了阻塞源——
  真正的阻塞是**门的零分布未刻画**，与校准目标无关。
- **修法**：本 change 落报告项；升格为门需先做 (a) 零分布刻画、(b) 预先注册容差 ε、
  (c) 失败语义定义（数据 / 口径 / 真重尾三分类）。

## 5. 遗漏检查（design 未提但实现会撞上）

以下均**实测确认**，不是推测。

**5.1 `match.json.match_periods` —— 权威的半场边界，全篇未提（最重要的一条）**

20 场**全部**具有 2 条记录，字段 `period` / `start_frame` / `end_frame` /
`duration_frames` / `duration_minutes`。它直接给出 D3 所需的半场边界，比
`max(P1.t) − min(P2.t)` 这种观测极值法稳健得多，还能用来交叉校验 shift、
以及判断「P1/P2 首尾是否缺帧」。**建议 D3 改用（或至少并列记录）它。**

**5.2 `match.json.status` —— 一场 `not_started`**

1953632 = `not_started`，其余 19 场 = `closed`。会被静默计入 20 场。

**5.3 `period` 可以是 `null`，而 design 的朝向规则会直接下标到它**（后果有限，但要显式处理）

实测场 1874553 全量：`period` 计数 `{1: 28981, 2: 31301, None: 19}`。
tasks P1.2 写「朝向：`match.json.home_team_side[period-1]`」——`period=null` 时
`home_team_side[null-1]` 在 JS 里是 `home_team_side[NaN]` → `undefined`，
不会报错，但会静默按「不翻转」处理。

**但实际影响比初看小**（我把这 19 帧定位到了）：这一场的 `period=null` 帧
**全部是 `player_data` 为空的帧**——实测「有 `player_data` 且 `period` 为 null」的帧数
为 **0**（另抽查 1886347 / 1996436 / 1959846，同为 0）。既然转换器第一步就
`if (!Array.isArray(pd) || pd.length === 0) continue`，这些帧根本进不了下游。

**仍然建议显式写死**（一行判断），理由与 P36「宁可报错也不猜方向」的立场一致：
现在的安全性依赖一个**未被声明的、只在 4 场上抽查过**的性质（「空帧 ⟺ period=null」）。
把它写成显式的 `period ∉ {1,2} → skip + 计入 coverage` 就消除了这个隐含依赖。

**5.4 换人：每队 16 名球员上场、同时在场 11 名——「沿用 Metrica 的 `assignIds` 思路」是退步**

实测：tracking 里每帧**恒 11 主队 + 11 客队**（44,244 帧全部如此，不只是前 50 帧），
但整场下来每队出现 **16 个不同 `player_id`**（36 名球员 / 每队 18，其中 4 人未上场）。
所以「替补顶槽位」的需求是真实的（tasks P1.2 已列）。

但 tasks 说「沿用 Metrica 转换器的 `assignIds` 思路」——Metrica 的 `assignIds`
是**几何启发式**（按出场帧数 + 平均纵深排序推门将和槽位），那是因为 Metrica 的 CSV
**不给身份**。SkillCorner **给了**：`player_role.name`、`start_time`/`end_time`、
以及 `dynamic_events.csv` 里的换人事件。用几何启发式在这里是**主动降级**且更脆——
换人后几何排序会变，槽位可能跳变（P36 已在 Metrica 上踩过「静默镜像」这类难查的问题）。
**建议**：起手 11 个槽位由首发（或首帧）一次性确定，替补按 `dynamic_events` 的换人
事件接管被换下者的槽位。这条应作为 D1/P1.2 的一个明确设计点，而不是「沿用思路」。

**5.5 `player_id` 全非空、坐标全非空、`is_detected` 全存在——「裁判/球混进 `player_data`」不发生**

审阅要求核实的几个假设，实测结论：

- `player_data` 里 `player_id` 为 null 的条数：**0**（全量 973,368 个点）。
- `x` 或 `y` 为 null 的点：**0**。
- 缺 `is_detected` 键的点：**0**。
- 同帧内 `player_id` 重复：**0** 帧。
- `player_data` 长度分布：**恒 22**（44,244 帧全为 22，其余 16,057 帧完全为空数组）。

即「每帧固定 22 个球员点」**精确为真**，而没有非球员目标混入。审阅要求里设想的
「裁判/球」出现在 `player_data` 的情况**不存在**。`position_group = "Other"` 的 6 人
是球员（含 2 名门将 + 其他角色），不是裁判——实测门将恰好 2 名且
`player_role.name == 'Goalkeeper'` 都能识别（`position_group` 对他们是 `"Other"`，
design 的告警**正确**）。

**5.6 朝向规则 `right_to_left → 翻 x` 经验证成立**

场 1874553 声明 `['left_to_right', 'right_to_left']`。实测主队门将平均原始 x：
P1 = **−38.48m**（左门）、P2 = **+40.78m**（右门）；客队对称（P1 +38.00、P2 −35.88）。
即 P1 主队攻向 +x（右），与 `left_to_right` 一致，不翻；P2 翻。**design 的规则正确。**
但 design 没写它验证过、怎么验证的——建议把这条经验证据写进 D2/tasks，因为「硬编码
会让一半比赛整体镜像」是 design 自己点名的风险，值得留下判据。

**5.7 球的缺失与外推（对应 P2-6，此处补数据）**

- 球坐标的有无与 `player_data` 的有无**完全同步**：44,244 个有球员数据的帧**全部**有球坐标；
  16,057 个空帧**全部**没有。
- 因此 SkillCorner 的 `ballFill`（缺失补全）机制**永远不会被触发**，
  `meta.coverage.ballMissingPct` 会恒为 **0**——读者会以为球质量完美，
  而实际上 **17.7% 的球位是外推**。
- 这解释了 design 上下文表里那句「球有坐标帧 100%（因空帧已被过滤）；其中真检测 82.3%
  ——报告口径不同（其 26.6% 含空帧）」。这个澄清是对的，但它没有推进到
  「那 `ballFill` 怎么办、`isRawBallFrame` 怎么办」。

**5.8 `home_team_side` 恒为长度 2 的数组（20 场全部），`pitch_width` 恒 68**

数组长度分布 `{2: 20}`，宽度分布 `{68: 20}`。design 说的「按 period 索引」可行，
但见 5.3 的 null period 问题。另外**没有加时赛/点球的数据**（`match_periods` 恒 2 条），
所以 period 只可能是 1/2/null——这让 5.3 的处理更简单（`period === 1 ? ... : period === 2 ? ... : skip`）。

**5.9 `referees` 为空数组**

`match.json.referees = []`（场 1874553）。无裁判轨迹需要过滤。

**5.10 帧数与「每场 7 窗」假设**

`match_periods` 推出的总时长在 5679–6128s 之间；900s 步长下 **1 场（2013725）
只有 6 窗**。design 多处按「每场 7 窗」表述（含 D8 的体积估算）。见 P3-1。

## 6. 对「Open Questions」三项的独立建议

### 6.1 D2 外推点口径

**不要在原 (a)/(b)/(c) 里选。** 选 (c) 的**结构**（透传 + 默认过滤 + 对照），
但**先改估计量**，否则 (c) 的推荐理由不成立：

1. 让 trim1 对 n 不变（比例修剪，每侧 `max(1, round(0.1n))`；n=10 时与 P36 完全一致），
   或明确锁 n。**这是拍板前必须解决的问题**——否则拿一个 n 依赖的量去和恒 n=10 的
   引擎侧对比，等于把口径伪影当物理量。
2. 默认 = 比例修剪 + 仅真检测 + 透传；对照 = **同估计量下的全点结果** +
   **随机 k 子集控制**（区分 n 效应与检测效应，见 P1-1）。
3. **拍板前**在 20 场上跑完 P1-1 的分解。如果比例修剪后「仅真检测 vs 全点」的差
   从 8.5m 缩到 ~3m，D2 的整张表都要重写——而那是好事，因为它把 5m 的伪影
   从「真实侧观测范围」里拿掉了。

### 6.2 D5 窗口步长

**保持 900s**——理由（与 P36 的窗口定义可比）值得那 2.6 倍的窗数损失，
而且 300s 步长增加的确实只是每场采样密度，不是独立样本（design 这点说对了）。
但两处要改：

1. 「与 P36 基线可比」降级为「**窗口定义相同**（300s/900s），**帧密度不同**」，
   并在基线里把两个数据集的「窗数 / 每窗有效帧中位与全距」并列。
2. 数字修正：**139 窗**（不是 140），**384 窗**（不是 400）。

另外建议把「对照报告 300s 步长」这条保留——design 说的「廉价的稳健性检验」是对的，
但读法要改：若两种步长导出的范围差异大，第一嫌疑应是 P1-1 的 n 效应（每窗有效帧
随步长变化），而不是「窗口口径不稳」。

### 6.3 D6 样本组合

**保留两套、分别报告（design 的推荐是对的）**，但补两件事：

1. **把跨数据集检查操作化**：显式输出「Metrica 的范围是否落在 SkillCorner 范围内」
   （逐指标 + 方向 + 余量，复用 `compareMetric`）。这是本 change 真正的价值主张，
   而 D7 的门对它零信息。**预期答案是「不落」**——若确实不落，那是必须记录的发现，
   它会直接反馈到 D2（因为两侧的差有 60% 来自 n 效应）。
2. **合并包络要么删掉、要么说清它只是并集**。两个不同生成过程的 min/max 并集
   没有任何统计含义；design 说它「保留了跨数据集可比性这个更有价值的诊断」，
   但没定义这个诊断是什么。定义它（见 1），或者删掉它。
