# Design: 真实比赛对照

## 上下文

引擎的比赛画面像不像足球，此前只能靠人眼与形容词判断。本 change 引入**真实比赛 tracking 数据
作为参照物**：同一块球场、同一套渲染，切换数据源即可背靠背对比。

核心判断：tracking 数据与引擎的 `beat` 事件**结构同构**（都是"若干球员在若干时刻的位置"），
所以对照通路**不经过事件流、不经过演绎层**——直接把 tracking 插值喂给 `renderFrame`。

## Goals / Non-Goals

**Goals**
- 把公开 tracking 数据转成与事件协议**同一 id 方案**（0-10 主队 / 11-21 客队）的帧序列，
  使两边能直接用同一渲染层播放、直接对照。
- 转换过程对数据的错位与缺陷**不静默处理**：能检测的检测，检测不了或无法判断的报错或如实标注。
- 数据源切换在异步加载下保持 UI 与画面一致。
- 全部验收无视觉依赖（纯逻辑/像素断言），可进 `verify.sh` 与 CI。

**Non-Goals**
- **不做**"真实比赛 → 事件流"的逆向识别（possession/传球识别是一整个研究领域，投入大、
  误差不可控，且会丢掉对照价值——见下）。
- **不做**量化指标对比（阵型宽度/纵深等）。那是下一个 change；本 change 只稳定其依赖的接口。
- **不做**广播视频 → 2D 俯视图的 CV 管道。SkillCorner 等数据集本身就是这条管道的产物，
  自建需 GPU 与大量环境成本，且转播机位移动导致固定 homography 只在镜头静止时有效。
- **不打开** tracking 模式下的观察采集（采集链路读引擎 `game`，语义不匹配）。
- 不支持 Metrica Sample Game 3（EPTS/FIFA 纯文本格式）；不支持 SkillCorner / Last Row
  （接入点已留在 `fetch-tracking-data.mjs` 的 `DATASETS` 表）。

## 决策

### D1: 旁路而非转事件流 —— 绕过引擎与演绎层

**选择**：`tracking JSON → TrackingPlayer → renderFrame`，不产生事件流、不经过 `Game`。

**理由**：对照的价值恰在于它是**没经过我们引擎加工**的原始行为。一旦经演绎层渲染，
看到的又变成"我们的引擎认为比赛该怎样"，失去参照意义。代价是 tracking 模式下没有事件
（导航、采集、纪律牌等概念不适用），这是刻意接受的——`TrackingPlayer` 保持最小面
（插值 + 播放控制），不引入事件相关概念。

**替代方案**：把 tracking 逆向成事件流再走现有链路。否决——possession/传球识别误差不可控，
且经过演绎层后参照意义消失。

### D2: 半场方向从数据检测，且必须用全量帧

**问题**：Metrica 的 x 是固定球场坐标、上下半场换边；引擎约定「主队永远从 x=0 攻向 x=1」。
**实测两场比赛的起始方向约定相反**：

| | P1 主队门将 | P2 主队门将 |
|---|---|---|
| Sample_Game_1 | x≈0.12（左） | x≈0.92（右） |
| Sample_Game_2 | x≈0.87（右） | x≈0.11（左） |

**选择**：`detectHomeAttackDirection()` 用「最贴最近底线的人」（判据 `min(x,1-x)` 与朝向无关）
所在侧判定主队该半场的防守端，再由 `makeNormalizer()` 按半场翻转。

**两个必须注意的实现细节**（都是实测踩出来的）：
- **必须在全量帧上检测，不能用 `--from/--to` 裁剪后的帧**。朝向是整场比赛的属性；短窗口里
  「最贴底线的人」可能是开角球的边后卫或压上的中卫。实测 game1 的 55-65s、630-750s 窗口
  仅用窗口内帧检测会判反 → **整段镜像**。
- **样本里没有 P1 时不能拿 P2 的观测去填**（`--from 3000` 裁出的纯下半场片段）。门将在 P2
  换到另一端，用 P2 推 P1 必然相反。检测函数识别样本实际覆盖的半场，再把结论换算到两个半场。

**反面教材**（都实测过，都由测试守住）：用整场 x 中位数（换边把它抵回 0.5，门将认不出）；
用 `min(x,1-x)` 当 depth（在 x=0.5 折叠，过中场的前锋被排到后卫后面）；硬编码「P1 翻转」
（两场起始方向相反，必错一场）。

**兜底**：无从判断时**抛错**而非猜方向——猜错会静默镜像，而镜像在小窗口上几乎不可能被肉眼发现。

### D3: 身份映射到事件协议 id

**选择**：输出 id 与事件协议一致（0-10 主队 / 11-21 客队，门将占 0 / 21），按下式折算到
「该队攻向 x=1」的坐标系后取平均得 depth，depth 小者靠后：

```
主队：period 1 用 x，period 2 用 1-x
客队：period 1 用 1-x，period 2 用 x
```

**替换规则**：主力 = 出场帧数前 11，其余为替补；主力缺席的帧由在场替补顶上该槽位，
保证每个关键帧恒定 22 人（game1 填充率 100%）。

**表头列名容错**：Metrica 每队最多 14 名球员，列名通常 `Player15`，但实测 Sample_Game_2
客队第 26 列写作 **`Player 26`（带空格）**。严格正则 `/^Player(\d+)$/` 会**静默丢掉该球员**
→ 该队整场少一人（实测造成 37.7% 的帧只有 21 人，一度被误判成"源数据只有 11 人"）。
选择：正则容忍空格，且**遇到疑似球员列却解析不出来时直接报错**，不静默丢人。

### D4: 数据质量如实暴露，不修饰

**选择**：能检测的缺陷统计进 `meta.coverage` 并在 viewer 信息条展示；**不**挪动位置掩盖。

| 指标 | 实测 | 处理 |
|---|---|---|
| 球缺失 | 39–41%，且是**长时段**（最长连续 131s） | 补到「离最后已知球位最近的球员」脚下，打 `ballFill` 标记；viewer 状态栏显示"球位置为推断" |
| 坐标重叠 | 5Hz 数据 4.86% 的帧有两人坐标完全相同 | **刻意不去重**，只统计 |
| 人数不足 | 当前两场 0%（安全网） | 如实统计，不造假人补位 |

**理由**：静默修饰比暴露问题更误导——挪动位置会让画面对不上真实数据，观察者无从知道哪里
被改过。球缺失若改用"沿用上一位置"，球会原地冻结两分钟，同样误导。`--ball-fill
nearest|hold|none` 可切，`none` 保留 null 不做任何推断。

### D5: 画面只由「此刻及之前」决定（帧号的纯函数）

**选择**：球员位置、球位置、球是否可见，全部由**帧号**唯一决定（预计算 `lastKnownAt` /
`lastKnownBallAt` 表），不依赖播放路径。

**理由**：否则「拖进度条直达某刻」与「顺着播到某刻」会给出不同画面——观察工具不能有时序歧义。
实测踩到两处：当前帧缺球员时若回退到**下一帧**（未来位置），球会在缺球段结束时提前 0.2s
瞬移；从有球的帧倒回还没球的帧时，坐标会残留未来值。

### D6: 数据源切换的状态由单一真相源推导

**问题**：数据源切换是异步的（一场 18MB），用户能在加载途中做很多事（切回引擎、选别的场次、
选回当前场）。三个 UI 状态（数据源下拉框 / 场次选择可见性 / 事件导航禁用）若各自命令式就地写，
任何一个出口漏处理都会造成「控件指向 A、画面是 B」。

**选择**：`syncSourceUI()` 把三态统一从 `activeSource` 推导；加载用 `loadSeq` 请求序号 +
调用方检查返回值来作废过期请求；**每个改变数据源的路径都必须 bump `loadSeq`**（包括"已经是
这一场"的早退分支）。

**代价与教训**：这一族竞态（过期响应、乐观写入 UI、早退分支）在实现与审阅中**共出了 6 个
变体**。最终靠"收敛到单一推导函数 + 穷举交错矩阵测试"收口。教训记在
`.scratch/notes/real-match-reference.md`：**当同一类 bug 反复以新变体出现时，说明状态机分散在
设计里，该收敛而不是继续打补丁。**

### D7: 帧序列 schema（本 change 的对外接口）

```jsonc
{
  "meta": { "source", "game", "hz", "keyframeHz", "frames", "startTime", "endTime",
            "coord", "orientation", "orientationDetected", "idMap", "coverage" },
  "frames": [ { "t": 0.04,
                "players": [[x,y] | null × 22],   // 下标即事件协议 id
                "ball": [x,y] | null,
                "ballFill": 11 } ]                // 仅补全帧：数字=持球者 id，"hold"=沿用
}
```

**这个 schema 是下一个 change（量化指标）的依赖面**：指标函数需要能从帧序列与引擎时间线
各取同一组量。因此本次把坐标约定（`coord: bottom-left`，与引擎一致）、id 方案、`coverage`
的含义都在此固定下来。

## 风险与权衡

- **数据许可**：Metrica sample-data **未声明正式许可**，README 要求注明来源、负责任使用。
  当前定位是本地开发/研究用途，数据与产物都在 `.gitignore`（不入库）。
  若要公开对比截图或换成可公开发布的数据集，应改用许可更清晰的源（如 SkillCorner，MIT）。
- **样本量**：Metrica 仅 2 场可用（Game 3 格式未支持）。作为参照物样本偏少，
  但足以覆盖"两种相反的起始朝向"这类关键差异。扩大样本是后续接入 SkillCorner 的事。
- **`syncSourceUI` 的重构判断**：审阅评估认为当前形态已到位（状态变量少、提交点与派生点各一，
  已是单向数据流雏形），不需要引入 store。**值得重构的信号**：加第三个数据源、
  播放状态需持久化/深链、UI 状态从 3 个涨到 6+ 个。
