# Design: P0 事件流到球场（event-to-pitch）

## Context

wayfinder 讨论已锁定技术栈：**Rust 引擎**（纯逻辑、平台无关）+ **JS Canvas 画面** + **B 内嵌引擎拓扑**（桌面 Tauri 内嵌、网页 WASM）。演绎参数由引擎给，画面负责演绎；第一版做简单（直线直传）；演绎节奏配置化。事件流协议草案已写（`event-stream-protocol-prototype.md`），但字段合理性**必须靠 P0 原型验证**，纸上无法拍板。

P0 是第一个 OpenSpec change，目标：打通"Rust 引擎 → 事件流 → JS 画面"链路，建立可扩展骨架，让协议在真实代码里被检验。

## Goals / Non-Goals

**Goals:**
- 建立可运行的工程骨架：Rust 引擎 crate + JS 画面层。
- 引擎（WASM）能产出最小比赛事件流，画面能消费并渲染成圆点球场动画。
- 验证事件流协议草案的接缝顺不顺手（字段、枚举、坐标）。
- 引擎保持纯逻辑、平台无关（可被 Tauri 内嵌与 WASM 两种方式消费）。

**Non-Goals:**
- 不做真实球员 AI / 能力值模型（P0 事件靠简单规则 + 随机生成）。
- 不做完整比赛、阵型、战术、换人。
- 不做 Tauri 桌面壳（P0 只在浏览器跑 WASM，桌面壳后续）。
- 不追求视觉精致（第一版直线、简单节奏，先验证链路）。

## Decisions

### D1: 事件流作为接缝，协议先用草案 v1，P0 中迭代
- **为什么**：协议是引擎与画面的唯一契约，合理性只能在真实跑起来后验证。草案 v1（字段、8 类事件、归一化坐标）作为起点，P0 目标之一就是暴露协议问题。
- **备选**：先花时间把协议定稿再写代码——已否决，无法纸上验证。

### D2: 引擎产出"最小但完整"的事件流
- P0 引擎产出：kickoff → 几脚传球 → 一次带球 → 一次射门 → whistle。
- **为什么**：覆盖 kickoff/pass/dribble/shot/whistle 五类核心事件，够验证协议和画面演绎，又不引入球员 AI 复杂度。

### D3: 引擎编译 WASM，浏览器跑
- **为什么**：B 内嵌引擎拓扑要求网页端引擎编译 WASM。P0 直接在浏览器验证"WASM 引擎 → JS 画面"链路，这是最短路径。
- 桌面 Tauri 内嵌是后续（引擎 crate 结构从一开始就兼容）。

### D4: 演绎参数由引擎给，画面负责节奏演绎
- 引擎输出 `speed` / `touch_freq` / `lead`（带球速度/触球频率/传球提前量），画面按 `interpretation-scripts.md` 的剧本（踢-追周期、传跑配合）演绎。
- **为什么**：票据 09 已定。画面不自行推断参数，保证"一个事件只被解释一次"。

### D5: 确定性优先，种子 RNG
- 引擎随机走种子 RNG（同种子 → 同事件流）。
- **为什么**：可回放、可调试；为后续票据 06（完整确定性策略）打基础。P0 先做种子 RNG，定点数等后续。

### D6: 纯逻辑引擎，无 I/O 假设
- 引擎 crate 不假设有文件系统/命令行——数据进、事件流出。消费方式（WASM 调用 / Tauri 内嵌）由宿主决定。
- **为什么**：B 拓扑要求引擎可被任一端调用。

## Risks / Trade-offs

- **[WASM 构建链复杂]** → P0 用最小 wasm-bindgen 配置，先用"WASM 引擎一次性产出整场事件流传给 JS"的最简交互，避免过早引入复杂绑定。
- **[协议字段设计偏题]** → 明确 P0 目标是"跑通链路"，协议按草案 v1 先用，遇到问题就迭代；不做过度设计。
- **[事件量过大/过小]** → P0 先人工构造一小段事件流（或引擎随机生成），观察画面表现再调引擎事件密度。
- **[JS 画面性能]** → 2D 圆点动画 + 事件采样引擎，JS 性能上限远高于需求；如遇问题再优化。

## Migration Plan

- 无（全新代码库，首次开发）。

## Open Questions

- 协议字段（subject/from/to、result 枚举、时间/坐标精度）——**留待 P0 验证后定稿**。
- 引擎与 WASM 的交互方式（一次性产出 vs 逐步产出）——P0 先一次性产出，验证后再定。
