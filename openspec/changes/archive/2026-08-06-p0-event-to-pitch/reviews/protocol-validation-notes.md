# 协议验证笔记（P0 跑通后，票据 02 定稿依据）

> 时间：2026-08-04
> 来源：P0 端到端链路（Rust 引擎 → WASM → JS viewer 消费）真实跑通后的观察。
> 用途：票据 02（事件流协议）从"待原型验证"推进到定稿的依据。

## 一、验证了什么

端到端链路真实跑通：`engine.wasm` 产 149 事件（2700s）→ `protocol.js` 解析 → `game.js` 播放 → `renderer.js` 画圆点球场。

## 二、协议字段哪些顺（验证 OK，保留）

| 字段 | 观察 |
|------|------|
| `t`（秒） | 顺。引擎用浮点秒推进，viewer 按 t 插值，半场 2700 秒正确 |
| `type` + `subject` + `x/y` | 顺。作为基础字段足够定位"谁在哪做了什么" |
| `from`/`to`（pass） | 顺。传球语义清晰（谁传给谁） |
| `x2`/`y2`（pass/shot/dribble） | 顺。双点定位让画面能画轨迹/方向，消除两层坐标猜谜 |
| `result` | 顺。goal 由 shot.result 表达，不需要独立 goal 事件（两跳 whistle 足够） |
| 演绎参数 `speed`/`lead`/`touch_freq` | 顺。引擎给参、画面消费，与票据 09 一致 |
| `players`（lineup 事件） | 顺。B1 修复后，viewer 纯从事件流渲染 22 人初始站位 |
| id 方案（0-10 home / 11-21 away） | 顺。viewer 据 id 分主客队颜色，无歧义 |

## 三、协议字段哪些别扭/需要改（定稿时的候选）

| 问题 | 观察 | 建议 |
|------|------|------|
| **tackle 的 `to` 原缺省** | 第一版引擎没发 `to`，viewer 无法演绎"防守者逼近持球者" | 已修：引擎发 `to` + `x2/y2`（被铲者位置）。**协议定稿时应把 `to`/`x2/y2` 列为 tackle 必填** |
| **进球后无 kickoff** | 引擎进球后只发 whistle，球不重置中圈 | 已修：进球后补 kickoff。**定稿时明确"进球 → whistle(kickoff_again) + kickoff"序列** |
| **`score` 字段冗余** | whistle 带 score，viewer 也可自己数 goal 事件 | 保留（显示比分方便），但定稿时注明"score 是便捷字段，非唯一比分来源" |
| **`subject` 与 `from` 重复** | pass 事件 subject==from（发起者），语义重叠 | 可接受（subject 是协议基础字段，from 是传球语义），定稿时注明关系 |

## 四、没验证/留待 P1 的协议点

- **序列化格式**：JSON 够用，但协议与序列化分离已证明（viewer 只依赖字段语义）。P1 可换紧凑格式。
- **坐标精度**：P0 用 float，确定性靠"同种子同输出"验证（不是定点数）。票据 06 完善时评估是否改定点数。
- **流式产出**：P0 一次性产出整场 JSON，P1 长比赛/实时可能要流式。协议字段不依赖此，接口层适配即可。

## 五、结论

**协议草案 v1 的字段设计经受住了真实链路检验。** 核心字段（t/type/subject/x/y + 双点坐标 + result + 演绎参数 + lineup players）全部顺畅，2 个真实缺口（tackle to、进球 kickoff）已在 P0 修复。票据 02 可据此定稿。
