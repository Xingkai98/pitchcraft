## 0. 一句话

把 `#17A` 的**异常候选**变成**可执行、成组否决、带真实参照的判据组**——
并且**如实记录哪些候选被实测排除**（本轮的排除比保留更有信息量：多条候选在两侧
**数字几乎相同而机制完全不同**，是巧合）。

```text
引擎侧
  engine/tests/p18/ ──► engine.json（逐场值 + 跨场分布 + seed 区间 + 引擎源码指纹）
    （复用 p17a/metrics.rs 的量 + 新增「转换反应」指标）

        ┌──────────────────────────────┴───────────────────────────────┐
        │  check-behavior-gates.mjs                                    │
        │    读两个 JSON → 成组否决 → 打印（**报告期，退出码恒 0**）      │
        │  gates.test.mjs  ← 反证条，**进 verify.sh 门槛**（判据退化会红） │
        └──────────────────────────────────────────────────────────────┘
```

**为什么引擎侧量要跑在 Rust、比对要跑在 JS**：判据需要的量（`PossessionEpisode` /
`ControlFact` / beat movers）只存在于 **Rust sidecar**，wasm 不导出（那是 P15A 的只读诊断面）。
所以引擎侧量必须由 Rust 导出成 JSON；而**判据逻辑只写一份**（JS），两侧都只读 JSON——
这样不存在"两边各写一份看起来一样的实现"（P36 立这份标尺时的第一条理由）。

**为什么放 `openspec/changes/p18-*/notes/criteria/`**：与 `p38-formation-realism` 同款。
判据是 change 的产物，不是仓库的公共设施。

**复用而非重建**（本仓纪律）：

| 复用 | 来源 | 说明 |
|---|---|---|
| `possession_shape` / `control_transitions` | `engine/tests/p17a/metrics.rs` | `action_gap_seconds` 等就是 A 组的量；`#[path]` 活读 |
| 「逐场算再跨场平均」口径 | P17A design §3.1 | 绝不跨场拼接（P38 实测拼接会让 sd 虚高 6.5×） |
| 反证条 + 变异自证 | P38 `notes/criteria/shot-criterion.test.mjs` | 判据**退化时会红** |
| 入库小 JSON + sha256 溯源 | P38 `real-shots.mjs` → `real-shots.json` | 判据器不依赖 90 MB CSV |
| 成组否决 + 报告期 + 升门路径 | P38 `check-criteria.mjs` + `verify.sh` 注释 | 形态逐条对齐 |

## 2. 判据组

### 2.0 判据纪律（**先立规矩再列条**）

1. **每条判据必须带真实参照值与 provenance**（数据集 / 场次 / 文件 sha256 / 口径版本）。
   `#17A` 把期望值标成 `[未标定]` 是对的——**未标定不得进判据组**。
2. **优先立「物理约束 / 分布形态」，其次才是「均值落在某区间」**。
   均值会被"数字搬家"买（P38 铁证；本 change 也实测到两处）。
3. **成组否决 + 报告期**。单条会被买；引擎现状**本来就过不了**，
   立成硬门会一直红到 `#19` 做完（同 P37/P38 报告期的理由）。

### 2.1 A 组：球权过程

真实侧 20 场 / 引擎侧 30 seed，**两侧都逐场算再跨场平均**（本文件所有倍数按此）。

| # | 量 | 真实（mean ± sd） | 引擎 | 倍数 | 立？ |
|---|---|---:|---:|---:|---|
| A1 | 链墙钟时长 (s) | **17.50 ± 2.03** | 49.65 | **2.84×** | ✅ |
| A2 | 链内动作间隔 (s)，start→start | **5.17 ± 0.69** | 12.64 | **2.44×** | ✅ |
| A3 | 链内动作数 | **3.60 ± 0.52**（全部链）／4.11（仅正时长链） | 3.90 | **1.08× / 0.95×** | ⚠️ **不作超限判据** |

**A3 单列为「守恒护栏」**：引擎在这个量上**落在真实的两栏之间**。
用法是 **`#19` 改 A1/A2 时的护栏**——缩短链时长**不得以牺牲动作数为代价**
（P17A §5 同款思路）。**不得**与 A1/A2 并列成"三条都要达标"：
那会让"把链切成两半"这种退化配置更容易过关。

**口径**（两侧必须对齐，否则差 2.4 倍这个结论不成立）：

- **链** = 连续同队控制。真实侧 = 连续同队 `player_possession`，
  且相邻两行之间 `game_interruption_before` 为空（**死球打断不连链**）；
  引擎侧 = `PossessionEpisode`（天然不含死球）。两侧同构。
- **间隔**：真实侧 pp 是**区间**、引擎的决策事件是**瞬时点**。故主口径取
  **start→start**（含上一段持球停留，与引擎同构）；**并列报 end→start**（只含空档）作对照。
  实测两栏：**5.17 vs 3.52** —— 若改用 end→start，引擎/真实倍数从 2.44× 变成 **3.59×**。
  ⚠️ **两栏都要报**，只报一栏就是口径单点。
- **零时长 pp 行**（`frame_end == frame_start`，占 pp 行的 24.5%）：**保留在动作数里、
  排除在时长与间隔外**。⚠️ 这让时长与动作数的分母不同，故 **`*_all` 与 `*_pos` 两栏都报**。
  实测：链动作数 `all` = 3.60、`pos` = 4.11（差 14%）。

### 2.2 B 组：转换反应（**结构性最强的一组**）

引擎侧实测（30 seed，`ContestStarted` → **失球方**首个 `chase`/`close_down`）：

| 延迟 | 占比 | 真实的对照 |
|---|---:|---|
| **d < 0**（丢球**前一拍**就已在跑） | **19.1%** | 真实侧不可能（反应先于事件）|
| **d == 0**（当拍指派追球者） | **37.1%** | 真实侧 **0.0%**（最小正值 0.1 s = 1 帧）|
| **d > 0** | **0.8%**（**全部落在 9.0–10.0 s**） | 真实侧 p50 = **1.50 s**、连续分布 |
| **10 s 内无人** | **42.9%** | 真实侧 **19.2%** |

⇒ **引擎的「反应延迟」分布是双峰 + 空集**：要么 d ≤ 0（已在跑/当拍指派），
要么干脆没人去。**中间没有**——唯一 0.8% 的 d > 0 全部挤在窗口边缘（9–10 s），
那是"恰好快到窗口末"的噪声，不是反应。

真实侧是**连续分布**：0.1 s 处 314、0.2 s 处 336、之后平滑递减到 p50 = 1.50 s。
（**注意**：真实侧 `P(延迟 ≤ 0.2 s)` = **26.3%**——"很快"这一档真实侧**是有的**，
只是卡在 0.1 s 的采样栅格上，故**判据不得写成「必须 == 0」**。）

**判据形态（修正后）**：

| # | 判据 | 真实 | 引擎 | 立？ |
|---|---|---:|---:|---|
| B1 | **`P(延迟 ≤ 0)`**（已在跑 + 当拍指派） | **0.0%** | **56.2%** | ✅ **结构性** |
| B2 | 延迟的**分布形态**（分位数单调、无窗口边缘堆积） | p50 = 1.50 s | **双峰 + 空集** | ✅ |
| B3 | `P(10 s 内无)` | 19.2 ± 3.2% | 42.9% | ✅（2.2×） |

⚠️ **必须按 contest reason 分层**（本轮实测，见下表）。**不得**只报合计——
合计把五种成因混在一起，而它们的形态**完全相反**：

| contest reason | n | P(d<0) | P(d==0) | P(10 s 内无) |
|---|---:|---:|---:|---:|
| `TackleLoose` | 434 | 0.000 | **1.000** | 0.000 |
| `PassLost` | 212 | 0.000 | **0.859** | 0.142 |
| `DeliveryLoose` | 645 | **0.602** | 0.208 | 0.183 |
| `ShotRebound` | 7 | 0.000 | 0.286 | 0.714 |
| `InterceptionLoose` | 729 | 0.000 | **0.000** | **0.984** |
| **合计** | 2027 | 0.191 | 0.371 | 0.429 |

⚠️ **两处必须点名的口径不对称**（第一轮 grill 抓到）：
1. **`DeliveryLoose` 占引擎分母 31.8%**（门球/界外球/角球/解围交付），
   而真实侧口径**按构造排除**这类转换（死球打断不计）。排除后引擎 `P(d≤0)` = **44.7%**、
   `P(10 s 内无)` = **54.4%**。
2. **`InterceptionLoose` 占 36%，它的 `P(d==0)` = 0.000、`P(10 s 内无)` = 98.4%**——
   这个成因下引擎**根本没有追抢**（拦截者对账到球上，无需追）。
   ⇒ **两个成因的形态与真实侧"像"或"不像"是相反方向的**，合计值毫无意义。

⇒ **B 组的判据必须分层**，并在 `gates-spec.json` 里逐层写 `sameThing`。
**机制叙述**（「引擎没有『丢球→反应』这一机制」）**不得**写进判据，
只作为 `#17A` A2/A3 已给的机制假设（`start_loose_ball` 的单队追逐者选择）的**引用**。

### 2.3 C 组：动作链

**映射表**（枚举，不是文本扫描——P17B 的教训：「能用类型系统的别用文本扫描」）：

| 引擎 `pass.result` | 真实 `pass_outcome` | 依据 |
|---|---|---|
| `success` | `successful` | 直接对应 |
| `intercepted` / `out` / `lost` / `contested` | `unsuccessful` | 真实侧只有二分；拿多分类去比二分类 = 口径分叉 |
| （无对应） | **`offside`** | **真实侧有第三个取值**（20 场 62 次），引擎无对应物 |

⚠️ **引擎 `pass.result` 实测有 5 个取值**（不止文档里常写的 4 个），30 seed 实测：
`success` 9825 / `contested` **645** / `intercepted` 729 / `out` 474 / `lost` 212。
**`contested` 不是稀有值**（占传球 5.4%，比 `lost` 还多 3 倍）。
它的 `detail`：`None` 503 / `clearance` 35 / `corner` 107——
**142 条是交付类（解围/角球）**，把它们算成"传球失败"就是 design 自己警告的
「拿分解去比整体」。
⚠️ **真实侧 `pass_outcome` 的空值不歧义**（实测 18710 行）：**空 ⟺ `end_type != pass`**。

**判据**：

| # | 量 | 真实（mean ± sd） | 引擎 | 倍数 | 立？ |
|---|---|---:|---:|---:|---|
| C1 | **以射门【收尾】的链占比** | **0.0661 ± 0.0170** | **0.1767** | **2.67×** | ✅ |
| C2 | 传球失败率 | 0.166 ± 0.033 | **0.173** | 1.04× | ❌ **不立** |

⚠️ **C1 的标签必须与实现一致**：真实侧「**收尾**」= 链末行动是射门（0.0661）；
「**含**射门」= 链内任意位置有射门（**0.0908**）。**两者差 37%**。
本判据取「收尾」，**实现必须与标签一致，并把两栏都报**。

⚠️ **C2 不立（实测排除）**：按映射表算引擎 = **(729+474+212+645)/11885 = 0.173**，
真实 0.166——**几乎相同**，且两侧都在 `realism.rs` L1 的传球成功率带内。
它与 A3 同型：**不是"引擎做对了"，是这条量本来就不区分**。
（第一轮 grill 抓到初稿此处写的 0.126 是把 L1 的 **200 场**数字标成了 30 seed，已更正。）

### 2.4 D 组：restart 恢复 ❌ **不立**（已声明的不可得）

引擎 `RestartSequence` 切三段（死球 → 发出 → 恢复开放），
**真实数据里没有"发出"这个时刻**。可得的是整个死球期（真实侧跨场均值）：
throw_in 19.3 s / free_kick 36.1 s / goal_kick 35.4 s / corner 41.7 s。

**处置**：在 spec 里写死为**已声明的不可得**。**不得**拿引擎的三段去对真实的一段。
⚠️ **这是对 `map.md` #18 授权五类的偏离**（含「restart 后的开放比赛恢复」），
已在 proposal 的诚实声明里记，**须同时在 roadmap 的 frontier 更新里记**（第一轮 grill 抓到）。

## 3. 容忍带怎么定

### 3.1 报告期的带 = 真实跨场分布

- **中心** = 真实跨场均值（带 provenance）；
- **带** = 真实跨场 `mean ± 3·sd`，**并列报出** `p10–p90` 与 min/max；
- **判据输出倍数与分位归属**，不是先验的 pass/fail。

⚠️ **零方差量的例外**：真实侧 `P(延迟 ≤ 0)` 在 20 场里**恒为 0**（sd = 0）——
`mean ± k·sd` **退化成一个点**。处置：这类量**不套公式**，
报「真实侧恒为 X（N/N 场）」并把带定在**采样栅格上**（如 ≤ 0.2 s，见 §2.2 的 26.3%），
理由写进 `gates-spec.json`。**不得**默认套用 mean ± 3sd。

### 3.2 ⚠️ **倍数才是主读法，z 值不是**

真实侧跨场 sd 很小（间隔 0.69、`P(≤0)` = 0），**z 会虚高**。
而且**20 场全部来自同一联赛同一赛季**（实测：20/20 场
`competition_edition = "AUS - A-League - 2024/2025"`，13 支球队）。

⇒ sd 里的变异是「**同一套标注流水线 + 同一联赛**」的变异，**不是足球的变异**。
**正确读法 = 倍数 + 方向**：「链时长差 2.8 倍」「间隔差 2.4 倍」。
z 只用来排序"哪几条最离谱"，**不得**读成"错误程度"。

### 3.3 ⚠️ **被实测排除的候选**（比保留的条目更有信息量）

| 候选 | 引擎 | 真实 | 为什么**不立** |
|---|---:|---:|---|
| 「`P(10 s 内无追抢)`」单独 | 42.9% | **19.2% ± 3.2%** | **两侧不同义**——引擎是「没有追球者被指派」；真实侧 `on_ball_engagement` 是**标注者认为有接触**的事件，不覆盖"有人跑向球"。⚠️ 初稿说此处真实是 46.4%「几乎相同、是巧合」——**那个 46.4% 不可复现**（第一轮 grill 抓到），已更正为 19.2%（**差 2.2 倍**）。**结论（不立）不变，但理由从"巧合"变成"不同义 + 差 2.2 倍"**。 |
| 「链内动作数」（A3） | 3.90 | 3.60 ± 0.52 | **落带内**（1.08×）。降级为守恒护栏。 |
| 「传球失败率」（C2） | 0.173 | 0.166 ± 0.033 | **两侧都在 L1 带内** ⇒ 本就不区分。 |
| ~~「动作间隔的量化粒度」~~ | — | — | **已删除**（第一轮 grill）：初稿那个「相邻唯一取值之差的平均」是**与量纲同变的伪指标**（= `(max−min)/(#unique−1)`），换个样本就变。**引擎的量化粒度本身是真的**（唯一取值 35 个、全是整数秒），但**要用「唯一取值数 / 样本数」表达**，不能用那个伪指标。 |

**这几条是本仓「结论对但机制错」在判据层的同构**：
光看数字（3.90 vs 3.60）会得出"引擎这几项没问题"——而 §2.1 的 A1/A2 说明它**慢 2.4–2.8 倍**。
⇒ **每条候选判据在入选前必须回答「这个量两侧测的是同一件事吗」**，
并把答案写进 `gates-spec.json`（不是写进注释）。
⚠️ **这个判断本身可能出错**（第一轮 grill 就抓到一条判反的），所以它必须**可审计**。

### 3.4 升门时的带（**本 change 不定，但把方法写死**）

报告期的带**可以直接用真实分布**——用途是"量差距"，红是预期的。
**升门**时不行：那时带必须能区分"合法配置簇"与"坏配置"，
而"合法簇"**只有在 `#19` 交付了合格机制之后才存在**（P38 的 `calibrate.mjs`
正是拿 16 个归档变体标的）。

⇒ **升门前置条件写死**：`#19` 交付合格机制 → 用它标定工程带宽 →
把 `check-behavior-gates.mjs` 的 exit 码接进 `verify.sh`。
**不得**为了"让它现在绿"而放宽成 `[未标定]` 或拍一个宽到没判别力的带。

⚠️ **对 `#19` 的如实提醒**（第一轮 grill 抓到 proposal 的因果句有鸡生蛋问题）：
本 change 交付的是**报告期判据**（退出码恒 0）。`#19` 的 tasks 要求「行为门结果」时，
**它拿到的是"报告 + 倍数"，不是可阻塞的门**——真正的门要等 `#19` 自己交付机制后由本判据升格。

## 4. 判别力证明（**与 P38 的差异，如实记录**）

P38 用 **16 个已归档变体**证明判据组会红。**#18 没有这个条件**——引擎还没被改过。
改用三件事：

1. **反证条（逐条）**：对每条判据构造"恰好该被判红"的输入，断言判据**真的红了**。
   进 `verify.sh` 门槛（P38 `shot-criterion.test.mjs` 同款）。
2. **合成变体**：把引擎侧 JSON 按已知变换改，断言只有目标条变绿/变红——
   证明**成组否决不会互相买账**。
3. **唯一的真实历史变体**：`#17A` 已实测 `BASE_ACTION_DEADLINE_TICKS` 7→3
   ⇒ 动作间隔 12.64 → **8.54 s**（30 seed，分析器口径）。把它作为**真实变体**跑判据组，
   断言**仍然全红**（8.54 离真实 5.17 还差 1.65×）。⇒ 证明判据不是对着现状定的阈值。

⚠️ **如实记录局限**（第一轮 grill 的两条，都成立）：
- **反证条在 3–4 条一组的组里只能证明接线**：gates 读 JSON，合成输入可逐字段构造，
  所以"越 A1 不越 A2"总能造出来。它证明的是**谓词电路正确**，不是**判别力**。
- **真实历史变体只看 A 组**：8.54 s 距真实 5.17 s 还有 1.65×，全红是必然的，信息量有限。
⇒ **真正的判别力只能等 `#19`**。本节三件事的作用是**守住判据不被改坏**，
**不是**"证明判据组能分辨真改善"。**不得**把本节读成后者。

## 5. 实现形态

**侦察期已归档**（`notes/probes/`，可复现，数字的来源）：

```text
openspec/changes/p18-behavior-verification-layer/notes/probes/
  real-behavior-probe.mjs        真实侧提炼器（**口径 C1–C6 写在头部**）
  real-behavior-probe.out.txt    它的输出（本设计引用的真实侧数字）
  real-behavior-reference.json   机器可读（每场值 + 跨场分布）
  engine-behavior-probe.rs.txt   引擎侧提炼器（**归档副本**；跑时拷成 tests/zz_*.rs）
  engine-behavior-probe.out.txt  它的输出（本设计引用的引擎侧数字）
```

**实现期要新建**（Slice 1–4）：

```text
openspec/changes/p18-behavior-verification-layer/notes/criteria/
  real-behavior.mjs              生产版真实侧提炼器（加 sha256 + 口径版本，产出可入库 JSON）
  real-behavior-reference.json   ← **入库**（规格化，带 provenance）
  engine-behavior.mjs / .rs      生产版引擎侧提炼器（带 seed 区间 + 引擎源码指纹）
  gates-spec.json                判据定义（量 / 真实中心 / 来源 / sameThing / excluded）
  check-behavior-gates.mjs       判据器（成组否决，报告期，退出码恒 0）
  calibrate.mjs                  标定 + 变异自证
  gates.test.mjs                 **反证条**（进 verify.sh 门槛）
engine/tests/
  p18/gates.rs                   引擎侧量导出（`#[path]` 复用 p17a/metrics.rs）
  p18_behavior_gates.rs          `#[ignore]` 落盘 target/p18-gates/engine.json
```

⚠️ **`notes/probes/` 里的探针是"侦察期的一次性脚本"**，与 `notes/criteria/` 里的
**生产版**是**两份东西**：前者的口径是设计依据（且已归档可复现），后者是交付物
（要带 sha256、口径版本、守卫）。**不要把前者直接当成后者**——那正是本轮初稿
「引擎数字来自未归档临时文件」的复现路径（design §10）。

## 9. 已知局限（如实记录）

1. **真实侧 20 场全部来自同一联赛同一赛季**（实测 `AUS - A-League - 2024/2025`，13 队）。
   ⇒ 无法把「足球」与「A-League 2024/25」分开，而本 change 的交付物正是给 `#19` 标定用的靶子。
   **须做跨数据集检查**（待决策 5）；**不得**只凭这 20 场声称"真实分布"。
2. **`dynamic_events.csv` 是 SkillCorner 的 Game Intelligence 产物**，带模型推断成分。
   本 change **只取坐标、时间、类型、结果**这类可人工核对的字段，**不取任何模型分数**。
3. **`phases_of_play` 的八档词表与我们的 `Phase` 闭集不同**。本 change **不使用**它，只上报。
4. **同义性判断本身可能错**（§3.3 已抓到一条判反的）。
   ⇒ `gates-spec.json` 为每条判据强制填 `sameThing`，就是为了让判断**可审计**。
5. **本 change 不产生可阻塞的行为门**（报告期）；唯一的阻塞是**反证条**（拦"判据退化"）。
6. **合成变体 ≠ 真实验证**（§4）。
7. **第一轮 grill 抓到初稿 5 处数字不可复现**（§10）——
   这不是"作者粗心"，是**本仓「产物可比性要源码指纹」族缺陷的又一次实例**：
   初稿的引擎侧值来自一个**未归档、且被后续探针覆盖**的临时文件。

## 11. spec delta 的相应更正（第一轮 grill 抓到）

- 「每组至少一条结构性判据」与 design 分组矛盾（A 组只有均值条 + 护栏、C 组只有一条）。

  （它们各自只有 1–2 条，形态条落在 B 组）。
- spec 原本**只对真实侧要求 provenance**，引擎侧完全没有。
  ⇒ 已加：引擎侧产物 SHALL 带 seed 区间 + 引擎源码指纹 + 口径版本。
- 「不可得项不得用区域/代理冒充」是**负存在断言**，无可执行判法。
  ⇒ 保留（靠人审），并在 §6 的表里标明它是**人审项**而非自动门。
