# Football Manager 2D 复刻 —— 两层架构设计草案

> 状态：**草案，待讨论**。本文是 wayfinder 讨论的载体，定稿后提升为 `docs/architecture.md`。
> 讨论方式：先看结构，再逐条过"技术选型决策点"（第 5 节）。

## 0. 目标与硬约束

- **从零写**，不依赖现成的 FM 类实现（足球模拟引擎、现成经理游戏代码）；通用工具（Canvas / SDL / Electron / Tauri / WASM 等）允许。
- **2D**，达到早期 FM 的观感：俯视球场、球员是圆点、球是小圆点，动作能看懂。
- **已确认技术栈**：事件引擎 = **Rust**；画面层 = **JS + Canvas**；双端 = 移动端浏览器直玩 + Windows 桌面 Tauri 套壳。引擎纯逻辑、平台无关（桌面原生 / 网页 WASM 均可）。
- **两层**：比赛事件引擎 + 2D 画面层，之间只通过**事件流**通信。
- 参考开源项目（OpenFootManager / agentic-fc / back-of-the-neural-net / Open Football）的**实现方法**，不搬代码。

## 1. 总体架构

```
  比赛配置：两队阵容（球员+能力值）、阵型、战术、种子
                      │
                      ▼
        ┌─────────────────────┐
        │   事件引擎 (Engine)  │  确定性模拟，不关心画面
        │   产出：事件流        │
        └──────────┬──────────┘
                   │  事件流（接缝协议，第 2 节）
                   ▼
        ┌─────────────────────┐
        │   画面层 (Viewer)    │  消费事件流，渲染圆点球场动画
        │   产出：可见比赛       │
        └─────────────────────┘
```

**四条原则**

1. **引擎不知画面、画面不知引擎内部**。唯一的接缝是事件流。引擎可以离线瞬间算完一场比赛，画面层按真实时间播放。
2. **确定性**：同一种子 + 同一配置 → 同一条事件流 → 可回放、可调试。
3. **分区/事件采样，不做连续物理**。球和球员不是牛顿力学仿真，是"状态机 + 概率事件"。
4. **事件要够细**。画面平滑度由事件密度决定——只给 90 条"每分钟事件"画出来就剩一个文字 ticker，要给出每次触球的粒度。

## 2. 事件流协议（接缝，全系统最重要的一处定义）

### 2.1 一条事件的字段

```text
t       比赛时间（秒，浮点或定点数）
type    动作类型（见枚举）
subject 主球员 id（发起者/持球者）
from    传球/传中的来源球员 id（可选）
to      传球/传中的目标球员 id（可选）
x, y    事件发生位置（球场归一化坐标，0-1）
x2, y2  目标位置（可选，用于画轨迹）
result  结果（success / fail / goal / saved / off_target / out ...）
note    附加（如"越位""犯规"，可选）
```

### 2.2 事件类型枚举（早期 FM 够用）

| 类别 | 事件 |
|------|------|
| 开局/结束 | kickoff, whistle |
| 传接 | pass, through_ball, cross, header, receive |
| 进攻 | dribble, shot, one_on_one |
| 防守 | tackle, interception, clearance, block |
| 门将 | save, claim, punch, throw_out, goal_kick |
| 犯规/纪律 | foul, yellow_card, red_card, penalty |
| 死球 | throw_in, corner, free_kick, offside |
| 球员 | substitution, injury |
| 球状态 | ball_lost, ball_won（球权切换）|

### 2.3 坐标系统

- **球场归一化坐标**：`x ∈ [0,1]`（0 = 左门线，1 = 右门线），`y ∈ [0,1]`（0 = 下边线，1 = 上边线）。画面层自行映射到像素。
- 事件坐标同时是引擎内部逻辑位置和画面定位——**引擎里的"在哪"就是画面里的"在哪"**，这消除了两层之间的坐标转换猜谜。

### 2.4 格式

- 第一版用 **JSON**（可读、可调、可 diff）。事件是高频的（一场球几千条），JSON 体积可控。
- 预留换成紧凑格式（如每行定长文本或二进制）的接口，但**协议字段不变**。

## 3. 事件引擎（第一层）

### 3.1 时间推进模型（待讨论，见决策点 D3）

三种候选：
- **A 固定 tick**：每 1/8 秒一个逻辑 tick，tick 内每个球员做一次决策（仿 FM slice）。最接近真实 FM，但实现最重。
- **B 事件驱动**：没有 tick，直接"算到下一个事件"，事件之间时间跳变。最省，但位置连续性差。
- **C 混合**：逻辑 tick 推进（如每 0.1 秒），但**不是每个 tick 都有决策**——有决策点时才触发决策，tick 间球员沿"目标位置"做位置插值。事件流按需吐出，位置连续。

草案倾向 **C**：引擎不重（不用每秒做 22 人 × 8 次决策），画面平滑（位置连续），事件密度可控。

### 3.2 球场模型（待讨论，见决策点 D4）

**分层：宏观分区（战术）+ 微观坐标（位置）。**

- 把球场分成 5 个宏观区（己方禁区 → 己方半场 → 中场 → 对方半场 → 对方禁区，仿 OpenFootManager），决定"球权向哪边推进"。
- 每个球员有**连续坐标**（在哪个区内部的具体位置）+ **角色区域**（战术上的站位基准点）。
- 球有位置 + 拥有者（某队某球员）或 `loose` 状态。

```
struct Player {
  id, team, role        // role: GK / DF / MF / FW
  pos: (x, y)           // 连续坐标
  home_zone: Zone       // 战术站位区域
  state: PlayerState    // FSM 状态，见 3.3
}
struct Ball {
  pos: (x, y)
  owner: Option<PlayerId>
  phase: InPlay | Loose | Dead
}
```

### 3.3 球员行为模型：角色 FSM（参考 Open Football）

**外层状态 = 角色**：`GK / DF / MF / FW`。每个角色有内层状态机。

**内层状态按情境分三组：**

| 情境 | 内层状态 |
|------|----------|
| 持球 | `dribble`, `look_pass`, `look_shoot`, `hold` |
| 无球·进攻 | `receive`, `off_ball_run`, `support`, `make_channel` |
| 无球·防守 | `mark`, `close_down`, `tackle`, `intercept`, `hold_position` |
| 特殊 | `committed`（承诺动作，见下）|

**承诺动作（不可中断）**：门将扑救/出击、滑铲、头球解围、射门。一旦进入 `committed`，在本动作完成前不能被打断、不能参与抢落点——这避免了"门将扑到一半被断球"的荒谬画面（Open Football 的 `is_committed_action` 思路）。

**决策点**：持球球员在决策点评估选项（传给谁 / 射门 / 带球 / 控球），每个选项打分：

```
score(option) = f(能力值, 战术指令权重, 情境因子, 随机)
```

能力值高 → 选项多、质量高；战术指令 → 不同选项的权重；情境（对手距离、队友空当、比分、时间）→ 修正。取最高分执行，生成事件。

### 3.4 能力值模型（待讨论，见决策点 D5）

**最小可用集**（社区实测表明很多属性实际影响很小，别贪多）。草案：

| 组 | 属性（1-20） |
|----|--------------|
| 身体 | pace 速度, acceleration 加速, strength 力量, stamina 体能, jumping 弹跳 |
| 技术 | passing 传球, shooting 射门, dribbling 盘带, tackling 防守, heading 头球 |
| 精神 | positioning 站位, decisions 决策, teamwork 团队, anticipation 预判 |
| 门将 | handling 接球, reflexes 反应, one_on_ones 一对一 |

**影响方式（属性组合原则）**：没有单一属性单独决定结果。例如——

```
射门结果 = f(射门技术, 位置角度, 防守压力, 门将能力, 随机)
传球成功率 = f(传球技术, 距离, 压力, 视野?, 随机)
```

**临时状态**：体能（随比赛消耗，降低动作质量）、士气（进球/失球/教练影响）作为修正系数。

公式全部自研，不抄 FM（闭源且无必要）。原则是**可校准**：每个公式的参数都能独立调，用真实数据对标（见第 6 节）。

### 3.5 规则引擎

放引擎内部，用位置数据判断：
- **越位**：传球瞬间，接球者位置 vs 倒数第二名防守球员。
- **犯规/牌**：抢断失败的低概率结果；恶意程度影响牌。
- **死球**：出边线 → 界外球；出底线 → 角球/球门球（按攻守方）。
- **进球判定**：射门事件 result = goal 时更新比分，触发 kickoff。
- **计时**：半场 45 分钟 + 补时（可选），whistle 事件。

### 3.6 确定性与回放（待讨论，见决策点 D6）

- 引擎所有随机走**带标签的 RNG 流**（"传球流""射门流""越位判罚流"……），同一标签在同一条件下永远相同。这样改一处逻辑不会让整场比赛结果漂移。
- 持久化状态**用定点数或整数**，不用浮点（跨平台一致性）。
- 事件流本身 = 回放数据。存下来就能重放、能倒带、能逐步调试。**画面层和引擎共享这一份事件流。**

## 4. 画面层（第二层）

### 4.1 渲染循环

```
读事件流 → 按 t 推进当前播放时刻 → 对每个可见元素做插值 → 画一帧
```

画面层是"播放器"：引擎可能瞬间算完一场，画面层按真实时间（或倍速）播放事件流。

### 4.2 球场绘制

- 草地（单色绿）+ 白线：边线、中线、中圈、禁区、点球点。早期 FM 就是这种极简画法。
- 全部由几何绘制（画线函数），不依赖图片素材——这样才是"从零写"。

### 4.3 球员与球

- 球员：圆点，两队不同颜色（主色 + 描边），守门员可用不同形状/颜色区分。
- 球：小圆点，或带一条短尾巴表示方向。
- 当前持球球员可加一个高亮圈（早期 FM 有）。

### 4.4 事件 → 动画映射（待讨论，见决策点 D8 + 票据 09）

**核心原则：引擎给数据，画面给"戏"。** 引擎输出带时序的抽象事件（含速度/节奏参数），画面层把事件"演"生动。**人球解耦**：人不是和球一起平移，而是"人撞一下球、球往前一下"的节奏（用户原话）。FM 本身也不逐帧物理，是"切片决策 + 插值"——生动感来自画面层的演绎。

**已定（票据 09）：**
- 引擎给演绎参数（带球速度/触球频率、传球球速/提前量），画面不自行推断。
- 第一版做简单：带球不变向、传球直线（不做外弧）。
- 演绎节奏（phase 时长、人球分离量）做成**配置文件**，方便调参。
- 分帧剧本见 `notes/interpretation-scripts.md`（带球踢-追周期、传球传跑配合）。

| 事件 | 引擎给 | 画面演绎（人球解耦） |
|------|--------|----------------------|
| dribble 带球 | 起点/终点/用时/触球频率 | **踢-追周期**：人向前小冲（球在原位）→ 球被踢出（人减速）→ 人追上 → 再踢一脚 |
| pass / through_ball | 起点/终点/球速 | 球飞向目标；接球者**先跑位**再接，不是原地等球 |
| shot | 起点/终点/球速/弧度 | 球加速飞向球门；门将**先动**扑向一侧 |
| tackle / interception | 防守者/持球者/成功与否 | 防守者加速逼近 → 伸脚 → 球权切换 |
| off_ball_run | 起点/终点/用时 | 球员**碎步**跑过去（不是平移）|
| whistle | 比分/时间 | 画面下方出文字 |

**关键洞察**：open-football 的 2D 至今未稳定，说明"事件→动画"映射（D8）是最容易被低估的一块——它决定"看着像球赛"还是"像幻灯片"。**演绎层值得作为独立的重点设计**（票据 `09`）。

### 4.5 插值策略

事件是离散的（t 时刻一个动作），帧是连续的（~60fps）。**帧与事件之间的空隙用插值补**：
- 球员圆点：在两次事件之间的"位置锚点"间做缓动插值（ease）。
- 球：传球/射门用**球轨迹曲线**（事件带 x,y → x2,y2），中间帧按时间比例取曲线上的点。
- 关键：**位置锚点由事件流提供**（这就是为什么事件坐标就是画面坐标，见 2.3）。

## 6. 校准（"有没有灵魂"的关键）

FM 团队的真功夫在**用真实足球数据校准引擎**。复刻项目也要有这一步：

- 跑 1000 场模拟，统计：每场射门数、进球数分布、控球率、传球成功率、角球数。
- 和真实联赛统计分布对比（公开数据如英超历年场均射门 ~13、场均进球 ~2.7）。
- 调整概率参数（不是加复杂度），直到模拟分布接近现实。
- 这一条决定"看着像足球"还是"像掷骰子"，比引擎多复杂都重要。

## 7. 实施阶段

| 阶段 | 内容 | 验收标准 |
|------|------|----------|
| **P0 接缝** | 事件流格式 + 最小 Rust 引擎（随机生成事件，编译 WASM）+ 最小 JS 画面（画圆点移动）| 浏览器里能看到 22 个圆点踢一场"球"（引擎在 WASM 里实时产事件流）|
| **P1 引擎** | 分区模型 + 角色 FSM + 能力值 + 规则 + 确定性 | 一场比赛产生结构化事件流，可回放 |
| **P2 画面** | 球场绘制 + 事件→动画映射 + 插值 | 画面动作能看懂（传球/射门/抢断） |
| **P3 校准** | 统计对标 + 调参 | 模拟统计接近真实足球分布 |
| **P4 战术** | 阵型、指令、换人（可选） | 阵型不同 → 打法不同 |

**P0 是关键路径**：先打通"引擎 → 事件流 → 画面"这条链，哪怕内容很糙。链路通了，后续都是在两端加肉。
