### 6.2 width 从距离里摘掉，会不会让标量对某种真实退化**变瞎**？

**先把问题问准**。先确认一件结构事实（我实测）：

- **全仓没有任何其它门/带管「队伍横向尺度」**：`grep -n "width\|宽度" engine/tests/realism.rs` → **0 命中**；
  `openspec/specs/match-engine/spec.md` 里「宽度」全是拦截 roll 宽度，与队形无关。
- committed 的真实横向锚（CI 可读）：skillcorner `perMetric.width` = 均值 **35.96**、逐窗 **25.17–46.38**（139 窗）。
  引擎 = 均值 **49.73**、逐窗 48.89–50.05（30 窗）——**高于真实观测上沿**。

⇒ **旧的 0.32 不是伪信号**：它确实在说「引擎比任何真实窗口都宽」。这一点必须写清楚，否则会把「去掉一行」误读成「去掉一个噪声」。

**那摘掉之后瞎了吗？我的判断：没有变瞎，但它把「唯一的两侧约束」换成了「一个方向更钝、另一个方向无约束」。** 具体三条：

1. **不变瞎的那面（pro）**：`spread`（到重心平均距离）+ `hd/ad`（纵深）+ `gap`（两队重心间距）都还在距离里，
   而 width 是三者中最**不承载队形变化**的一行 —— 引擎 width 的 30 窗极差只有 **1.16 m**（48.89–50.05），
   即它对绝大多数改动**近乎常数**，在 `mean|ln|` 里主要贡献一个**常数偏移**，本就不提供区分度。
   一个近乎恒定的行被计分，唯一效果是「谁动了那两个最宽的球员，谁就得到奖励」——恰是 y 轴那种假改动。
2. **变钝/换方向的那面（con，必须承认）**：摘掉后，**横向尺度在标量里彻底没有直接项**。
   现存最近的是 `spread`，而它的零点在真实值 **12.76**、引擎在 **20.83** ⇒
   「把队收拢」在**整个 20.83 → 12.76 区间**都被奖励（这区间正好覆盖 y 轴那种「两人往中间挪」的假改动方向）。
   换句话说：**移除 width 没有移除「收拢被奖励」这个激励，只是把它从 1/9 权重挪成由 spread 独家承担**。
   要等到队形塌到明显小于 12.76，`spread` 才会反过来惩罚。⚠️ 但**别指望 `gap` 兜底**：
   本仓自己记着「标量有退化方向」——`CLAUDE.md:56` 的纯块配置（两队叠在球上）距离 **0.365 全场最低**，
   恰恰因为 `gap` 的零点在真实值 5.24 m，退化形态把两队叠在一起时 `gap` **变小、被奖励**。
   ⇒ 残留的这几行**本来就挡不住那类退化**；移除 width **既不新增、也不修复**这个已记录的退化方向。
   **残余盲区一句话**：**没有 CI 可跑的断言在守「引擎队形不许过窄」**。
   （CLAUDE.md §2 的原话是「能被算出来的量…仍要写成数值断言进 CI」——width 现在是**能算、会打印、无人断言**。）
3. **可选的最小补救（都不需要重下 1.82 GB）**：
   ① 把 `width` 报告行做成一条**报告期断言**：引擎 width 落在 committed 真实逐窗区间
   `[25.17, 46.38]` 之外就打印 ⚠（现在引擎 49.73 **已在区间外** ⇒ 必须先决定「这是要修的缺口」而不是「要改的带」，否则会变成给现状配带的 classic 错误）；
   ② 或者把「报告行不进距离」这件事**写进 SKILL 的操作纪律**：「比距离前先读 width 报告行和 `※` 脚注」；
   ③ 真正的修法（把 width 也换成 q10–q90）我**同意**本 change 的取舍：它要重生成 committed 基线（重下 1.82 GB），
   属于另案 —— 但**应该在注释里把「这是欠账」写死**，而不是只写「没意义」。

**综合**：我**支持**把 width 降为报告行（它是一行低区分度、且会奖励假改动的项），
但**反对**把结论写成「width 那个量没有意义」——有意义的是**真实锚仍在**、且**当前引擎确实比真实宽 38%**。
建议在代码注释与 note 里各加一句：
「**摘下 width 的代价：标量不再对『横向过窄』有两侧约束；引擎 width 目前仍高于真实逐窗上沿（49.73 vs 46.38），
