## 1. 球位在 episode 内确实移动

推进度定义：`0` = 本方球门线，`1` = 对方球门线（主队攻 x=1、客队攻 x=0）。

| 量 | p10 | p50 | p90 |
|---|---|---|---|
| 推进度极差（仅起点 `x`） | 0.082 | 0.245 | 0.447 |
| 推进度极差（**含落点 `x2`**） | — | **0.345** | 0.565 |
| 净推进 | -0.042 | 0.177 | 0.417 |
| 最大回撤 | — | 0.065 | 0.225 |

⇒ 「episode 内存在可分辨的位置变化」成立。**但含落点后极差升约 40%**——
只取起点的口径**低估推进**，这是 §2 口径问题的一个侧面。

---

## 2. 核心发现：**位置口径未定，且差 3 倍**

### 2.1 同一批 episode，两种口径给出不同的「起点带」

| 口径 | 后场起点 | 中场 | 前场 |
|---|---|---|---|
| **A**：episode 内**首个决策动作**的 `Event.x` | 554 / **7.5%** | 5464 | 1354 |
| **B**：该 episode 的 `control_established` 事实的 `location` | 1731 / **23.5%** | 5071 | 570 |

**两者差 3 倍，且 26.6% 的 episode 落在不同的带。**

### 2.2 为什么差——机制已查清

**`Event.x` 是「动作主体的位置」，而 episode 开场通常是一段带球（`beat.main`），
不是决策动作。** 实测：episode 开启 → 首个决策动作的时延
**p10 = -2s / p50 = 8s / p90 = 16s**——**中位 8 秒**。

即：球在本方后场被控制后，要先带若干秒，才出现第一个 `pass`/`shot`——
只看那个 `pass` 的位置，就会把「后场开局」记成「中场开局」。

### 2.3 放大器：门球落点**硬编码过中线**

`goal_kick_land`（`engine/src/lib.rs:3159`）逐字：

```rust
let (lo, hi) = if dir > 0.0 { (0.50, 0.82) } else { (0.18, 0.50) };
```

**门将开大脚的落点恒在 `x ∈ [0.50, 0.82]`（过半场）。**
于是「门将持球（货真价实的后场开局）」在只看首个决策动作的口径下**必然**表现为中场开局。
门球占全部重开的 **31.7%**（1666/5258），是这条偏差的主要放大源。

### 2.4 因此

**在「episode 起点用哪一层的量」定死之前，连「起点带」这种最基础的统计都不可比。**
v1 据此推出的「`build_up` 结构性稀少 ⇒ 该重新定义三档」**不成立**。

## 3. `build_up` 到底稀少吗

用引擎自己的起点口径（B）重算（同一批 episode）：

| 量 | v1（口径 A） | **v2（口径 B）** |
|---|---|---|
| 后场起点占比 | 7.5% | **23.5%** |
| 完整链条（后场起→前场终） | 4.12% | **11–14%（口径内浮动）** |

**⚠️ 「完整链条」一格的区间本身就是本节的证据**：作者复算时，因「末位置」取值不同
（末事件的 `x` vs 末决策动作的 `x`）得到 11.0% 与 13.7% 两个值，分母也随门槛变化
（7372 vs 10096）。**这正说明 §2 的论点成立——口径没定死，连百分点都不可比。**
v2 因此不给单点数字。

**23.5%（后场起点）是不是「够三档用」，本轮不回答**——它需要**用特征跑判别检验**（§5）。
⚠️ 特别是：「区域占比 ⇒ 阶段可用性」这一步本身**触犯契约**
（`map.md:64`：「`build_up ≠ 后场`……不得用区域/坐标冒充战术阶段」）。
**v1 犯了这一步，v2 不再犯。**

**不受口径影响、仍然成立的现象**（可作后续输入）：

- **终点带偏斜**：72.9% 的 episode 终于前场（两种口径一致——末动作接近收束）；
- **单调向前仅 35.4%**：多数 episode 内有回撤；
- **跨三分线**：约 75% 的 episode 至少跨一条。
  （v1 写的「其中 ≥2 条占 27.7%」**标签错**：那是**带间转移次数** ≥2；
  真正「走过 ≥2 条**不同的**三分线」只有 **4.7%**。）

## 4. 现有数据能算什么（可行性，含成本）

**能**：`viewer/match-metrics.js` 的 `sampleEngineFrames(game, {stepSec})` 在引擎侧实测可用——
60s 得 301 帧、每帧 **22 人**带球位、`teamShape` 返回 `{depth,width,cx,cy,spread,n:10}`、
**0 个 null 帧**。

**⚠️ 两处 v1 说重了的约束**：`includeExtrapolated:false` 与 `MIN_OUTFIELD_PLAYERS=7`
**在引擎侧是空操作**——引擎帧不带外推标记、每队恒 10 名外场。它们是给真实侧（SkillCorner）用的。

**❌ v1 的「静态特征几乎不用新写」是过度延伸**：
`teamShape` 是 **JS**（`viewer/match-metrics.js`），
而 **15B 的 `PhaseAnnotator` 是 Rust**（design §11 的入参/产物都在 Rust 侧）。
`engine/src/` 里**没有任何团队宽度/重心/spread 实现**。
⇒ 要吃这段代码，**要么把指标移植进 Rust，要么让引擎导出快照**——**这是本票的实际成本，v1 未计**。

**❌ 另一条 v1 未意识到的路**：`episode.event_indexes` **只挂 1.6% 的 beat**
（8361/536426），所以**「用 `event_indexes` 重建轨迹」不通**——
必须走 `sampleEngineFrames` 的全量采样。（两种读法差别很大：`event_indexes` 口径只得 18.1%
后场起点，全量口径 23.5%。）

## 5. 对 #116 的建议下一步

1. **先定位置口径**（本轮的头号阻塞）。建议：**以 `ControlFact` 为权威**
   （它是观测层对「episode 在哪开始/结束」的定义），
   **不以决策动作的 `Event.x` 代替**。定完再算任何位置统计。
2. **修 v1 误用的推论方式**：不得由「区域占比」推「阶段可用性」（触契约）。
3. **特征先行**：定义「带时间关系的推进特征」（净推进口径已有；横向转移 / 线间距 / 接应需定义），
   并给出覆盖率与 `unknown` 占比。
4. **成本要计入**：JS 侧已有实现 → Rust 侧 15B 的移植（或引擎导出快照），二者选一并估工。
5. **phaseability 实测**：用特征跑「三档能否分开」的判别检验——**这才是 gate 的实质**。
