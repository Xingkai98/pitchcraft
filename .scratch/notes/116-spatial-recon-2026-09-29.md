# #116 侦察：#15B 的三档 phase 在本引擎里可判定吗？

## 0. 结论摘要

| 问题 | 答案 |
|---|---|
| episode 内球位会移动吗？ | **会**。推进度极差 p50 = **0.245**（≈25 m），净推进 p50 = 0.177 |
| 所以「有阶段可分」有物理基础吗？ | **有**，但**结构性偏斜严重**（见 §2） |
| `build_up` 在本引擎常见吗？ | **不**。仅 **7.5%** 的 episode 起于后场；`build_up → final_third` 完整链条只有 **4.12%** |
| 现有数据够算团队空间特征吗？ | **够，但有口径约束**（外推点默认跳过，`MIN_OUTFIELD_PLAYERS = 7`） |
| 三档可直接判定吗？ | **不能直接判**，但障碍只剩一个（§3.2 的 `build_up` 稀少）。初稿以为还有「挂载单元冲突」，**已证伪**（§3.1） |

**⇒ phaseability gate 的初判**：三档**不能原样直接判**（`build_up` 结构性稀少），
**但 §11 的挂载约束与数据不冲突**。结论指向「重新定义三档」而非「改挂载单元」。

## 1. 球位在 episode 内确实移动（有阶段可分）

推进度定义：`0` = 本方球门线，`1` = 对方球门线（主队攻 x=1、客队攻 x=0）。

| 量 | p10 | p50 | p90 |
|---|---|---|---|
| 推进度**极差** | 0.082 | **0.245** | 0.447 |
| 推进度**净推进** | -0.042 | 0.177 | 0.417 |
| 动作数 | 2 | 4 | 10 |
| 最大回撤 | — | 0.065 | 0.225 |

**跨三分线**：75% 的 episode 至少跨一条；其中 ≥2 条占 27.7%。

⇒ 「episode 内存在可分辨的位置变化」成立，**三档不是无米之炊**。

## 2. 但分布严重偏斜——三段式模型与本引擎不匹配

**起点带**：后场 **554 (7.5%)** / 中场 **5464 (74.1%)** / 前场 1354 (18.4%)
**终点带**：后场 43 (0.6%) / 中场 1956 (26.5%) / **前场 5373 (72.9%)**

按 `start_reason` 拆起点：

| 原因 | 带 | 计数 |
|---|---|---|
| `restart_control` | 中场 | 2922 |
| `pickup` | 中场 | 2448 |
| `restart_control` | 前场 | 699 |
| `pickup` | 前场 | 655 |
| `restart_control` | 后场 | 299 |

**结构性含义**：episode 主要**在中场开启、在前场结束**——即多数 episode 是「中场拼抢/重开 → 打进前场」，
而不是「后场组织 → 推进 → 前场」，**起始阶段（`build_up`）天然稀少**。

**完整链条**（后场起 → 前场终）：**304 / 7372 = 4.12%**。
**单调向前**（无任何回退）：2607 / 7372 = 35.4%。

**本报告不归因**：偏斜的成因未在本轮核实。候选（**均未验证**）：`OFF_BALL_RUN_DIST = 0.02`
与 `PRESS_UP_OFFSET = 0.02` 等队形目标尺度，以及重开/拾取的实际发生位置。
⚠️ 注意 `SIDE_SHIFT_FACTOR = 0.06` 是**横向**因子（随球横向漂移），
**不能拿它解释纵向偏斜**——本报告初稿曾误引，已删。

**可确证的是现象**：引擎的推进不是「从后场一路打上去」，而是「在中前场反复争夺」。

## 3. phaseability 的核心问题

### 3.1 「同队连续 episode」**不是**连续推进（初稿论据被推翻）

**初稿写过**：「44.3% 的同队连续段说明推进跨 episode，与 phase 挂单 episode 冲突」。
**实测推翻**——那些「同队相邻」绝大多数**中间隔着死球**：

同队相邻 episode 对 3264 个，**真无缝接续的只有 11 个（0.3%）**；
间隔中位 **4 秒**、p90 **32 秒**。间隔里发生的事（前段结束 → 后段开始）：

| 前段结束 | 后段开始 | 计数 |
|---|---|---|
| `out` | `restart_control` | 1112 |
| `foul` | `restart_control` | 1099 |
| `control_lost` | `pickup` | 690 |
| `control_lost` | `restart_control` | 178 |

**⇒ 它们是「一次进攻结束（出界/犯规/丢球）→ 比赛重启」的序列，不是同一次推进的延续。**

**修正后的结论**：**本轮的证据不支持「推进跨 episode」这个主张**——
也就是说，**design §11「phase 挂在单个 `PossessionEpisode` 内」与数据没有冲突**。
初稿把它写成冲突，是**用了一个不成立的连续性判据**（只看队别相同，没看中间是否死球/隔多久）。

> ⚠️ 这条更正很重要：初稿曾据此建议「先答 #113 的挂载单元问题再写谓词」——
> **该建议的理由不成立**。挂载单元的冲突**未被证据支持**，15B 可以按「单 episode」继续设计。

**但仍然成立的**：episode 之间的推进**总量**会跨段累积（例如死球前推进了 20m、重开后继续推进 20m）——
这是「一次进攻」的语义，属 **#17B 的报告层**，不是 phase 的挂载单元问题。

### 3.2 `build_up` 稀少，是引擎行为而非算法缺陷

`build_up`（后场组织）仅 7.5% 起点。**若 15B 的主要产出是「大多数 episode = 中场阶段」，
它对 #17B 的增量价值有限**——因为三个标签里有两个（`progression`/`final_third`）几乎覆盖全部。

⇒ 15B 的设计应面对这个事实：**要么接受 `build_up` 是稀有标签**，
**要么重新定义三档**（例如按「是否形成推进」而非「在哪个区域」）。
后者正是本票新增的「phaseability 特征」要回答的。

## 4. 现有数据能算什么（可行性）

**位置来源**：`viewer/match-metrics.js` 的 `sampleEngineFrames(game, stepSec)`——
从 viewer 插值态按 5Hz 采样，给出**完整 22 人** `{id,x,y}`。P36/P37 的引擎侧指标已走此路。

**口径约束**（必须继承，勿新造）：
- **外推点默认跳过**（P37 D2）：`teamShape` 默认 `includeExtrapolated: false`；
- `MIN_OUTFIELD_PLAYERS = 7`：外场球员不足则返回 `null`（不是补零）；
- 采样 0.2s，与真实侧 keyframeHz 对齐。

**已实现、可直接复用的特征**（`teamShape`）：`depth`（q10–q90 纵深）、`width`、`cx/cy`（重心）、
`spread`（到重心距离）、`n`（有效人数）。
**⇒ #16 的「静态特征」部分几乎不用新写**——已有实现且已与真实数据对齐。

**缺的**是**带时间关系**的那组（本票新增要求）：净推进、推进/回撤/横向转移、
线间距变化、接应是否形成。这些**没现成实现**，是本票的实际工作量。

## 5. 对 #116 的建议下一步

1. ~~先答「推进跨 episode」~~ —— **不需要**（§3.1 已证伪）。挂载单元按 §11 的「单 episode」继续。
2. **特征先行**：定义「带时间关系的推进特征」（净推进口径已有；横向转移 / 线间距 / 接应需定义），
   并给出覆盖率（多少 tick 能算出、多少落 `unknown`）。
3. **phaseability 实测**：用这些特征跑「三档能否分开」的判别检验——**这是 gate 的实质**。
4. **面对 §3.2**：`build_up` 仅 7.5%。要决定：接受它是稀有标签，
   还是**重新定义三档**（按「是否形成推进」而非「在哪个区域」）。
   **这一条是 gate 最可能的结论方向**，也是 #116 该给 15B 的答案。
