## 1. ★ 两条真不变量：修 + 根因订正

### 1.1 `p53_same_team_spacing_holds_between_anchors`

**落地报告 §D4 的原解释（「P34 carrier 拍内扫掠豁免」）被探针证伪。** 实测（`rescan`/`p53_probe`）：

- 违规 = **seed 8 t=719s，pair id2/id4，d=1.765m，`sk_raw=−0.191` → `kind=START`**——
  最近点在**线段起点**，不是拍内中点；
- 拍内扫掠（`sweep_pair_lateral`）遇到「起点已 <阈值」本就**早返回**（「起点不可动」），
  **与 carrier 是否豁免无关**。

**真机制**（事件 dump 实证）：t=717 一次传球（`subject 10 → 4`，落点 `(0.2761,0.4906)`）；
飞行期（t=717→718）**无球 mover id2 跑进了该落点 1.765m 内**；t=719 结算 `PassCaught` 时
`finalize_highlight` 把 id4 直接放到落点 → **下一拍 carrier 的起点**（=`st.pos[4]`）距 id2 仅
1.765m，而**起点不可动** ⇒ 整拍残留。即：**`finalize_highlight` 的参与者位置写回绕过了同队分离**。

**修**（`lib.rs` `PassCaught` 结算处）：
```rust
let (rx, ry) = separate_target_point(st, receiver, catch_pos);
st.pos[receiver] = (rx, ry); st.last_ball/carrier_from = ...
```
即用**既有**单点分离把接球者从**当前**队友位置推开（队友冻结、只推接球者）。

**验证**：`p53` 绿（seed 8 最坏 1.765m → **2.133m**）；**L1 仍 4/5**（未破射门几何）。
**不是缩守卫**——修的是真实的写路径缺口；非 carrier 对的守卫原样保留。

### 1.2 `realism::l2_cross_event_invariants`（射门落点）

**落地报告 §7 说「`y2` 越界」——错。** 探针（`shot_probe` + 定向变异）定位：违例是
**`x2` 越门线**（应 0.02，实 0.0192/0.0194），**不是 `y2`**。
```
seed=1  t=4552.000 subj=14 result=off_target x2=0.0192 y2=0.4400 detail=header       → X2_BAD
seed=42 t=...      subj=..   result=saved      x2=0.0194 y2=...    detail=undefined    → X2_BAD
```
⚠️ **不是「唯一违例=header」**（收尾订正过窄）：违例**两条射门路径都会出**——
seed 1 是 **header**（`emit_header_shot`），seed 42 是 **open-play saved 射门**（`detail=undefined`，
走 `emit_shot_highlight`）。根因：`separate_target_point` 为求 2.2m 分离余量把射门终点沿 x
推离门线——但对已 >2.0m detector 阈值的 pair 是多余的。

**修**：**两条**射门路径（`emit_shot_highlight` / `emit_header_shot`）分离后都把 `x2` 夹回
门线（只保留 y 方向分离）——正因为两条路径**都**能违例，才必须两处都夹。
**验证**：`rescan shot 1..=120` **零违例**；定向变异（只撤一条路径的夹回）→ 对应 seed **当场红**
（撤 header → seed 1；撤非 header → seed 42），证明两条夹回都是必要条件。

## 7. ★ CI 阻断：球 snap（**已修**，viewer-only，引擎零改动）

**修好基线哨兵后，CI 第一次跑到 step 4/9（WASM e2e）就红**——这条红一直被 step 3 的基线哨兵遮住
（verify.sh step 3 失败即 `exit 1`，step 4 从未执行）。

  ⇒ **v4 引入的回归**——v4 的四层移动层改了站位，使某一次传球落进下述「边界窗」；**与 p53 / L2 修法无关**。

### 7.1 根因（先证伪任务书假设，再定位真因）

**假设（任务书高置信）= p53 的 `separate_target_point` 引入 → 证伪。** 把 `finalize_highlight`
的 `PassCaught` 结算里那次 `separate_target_point` 临时撤掉重建 → `maxBallJump` **逐位不变**
（`0.12308014665249632`）。原因：该 `separate` 只改**引擎内部状态**，**不改已发出的事件**——
`pass.x2/y2`（球锚点的来源）在传球 tick 就已定型。**撤改已还原。**

**真根因 = 引擎↔viewer 的「传球飞行时长」口径不一致：**
- 引擎 `flight = distance_meters(全精度端点)/speed` → 决定高亮在哪个 tick 结算；
- 但事件坐标序列化是 **`{:.4}`（4 位小数）**，viewer 用**这 4 位小数**重算 `ballDur = dist/speed`。
- 两者差 ~2e-4 s。seed1 t=4942 那次传球（subject 13→14，落点 `0.5094,0.713`）：引擎全精度 flight **≤ 1.0**
  （→ tick 4943 结算，该拍**带球锚点**），但 viewer 按 4 位小数算出 `ballDur = 1.0002 > 1.0`
  → **传球末端锚点(t=4943.0002) 排在下一拍起点锚点(t=4943.0) 之后**（事件在时间上"重叠/插队"）。
- viewer 插值器规则「相邻锚点 `evt` 不同 → hold」在此**误当事件间隙** → 球**冻在飞行中点**(0.4354,0.8114)，
  t=4943 瞬移到落点(0.5094,0.713) = **0.1231**。**佐证**：t=4944 还有一个 0.030 的**同源**跳变
  （球又冻了一拍），只是 < 0.05 阈值没报。

**决定性验证**：把序列化精度提到 `{:.10}` 重建 → `maxBallJump 0.123 → 0.0186`、e2e 绿 ⇒ 坐实是**精度/时长口径不一致**。

### 7.2 修法（**viewer-only**：`viewer/game.js`）

引擎流**按位置是连续的**（传球末端 anchor 的位置 == 下一拍起点 anchor 的位置，两者都 = 落点），
问题在**事件时间上重叠时 viewer 的 hold 规则**。故修渲染层，不碰引擎：

- 新增 `eventBoundaryFlags`（算每个 `evt` 的**首 / 末**锚点），`_buildAnchorIndex` 为球 / 每球员预算；
- `_interpolateAnchors`（continuous）：相邻锚点 `evt` 不同时，**仅当** `prev` 是其事件**末**锚点**且**
  `next` 是其事件**首**锚点（= 真·事件间间隙）才 hold；否则（事件重叠）**照常插值**，延续本事件轨迹。
- 非重叠场景行为**逐位不变**（真间隙仍 hold、同事件仍插值）——只改重叠这一条路径。

**依据**：`pitch-viewer` spec 的「无 snap」是 **viewer 侧**契约；引擎的连续契约（`from(N+1)==to(N)`）
是**拍间**位置连续、本就成立。引擎流位置连续、只是渲染漏了重叠 ⇒ 修渲染层。**非**静默放宽 e2e 阈值（`0.05` 原样）。

### 8.2 根因（逐条定位；与 p53 的直写路径**不同**）

修法前先把两条 finding 摊开（诊断探针复用 `spacing-sweep` 同一条真实采集管线
`Game` + `captureObservation` + `detectPlayerOverlap`；探针已删）。**探针与真工具等价**已核：
同一窗「复用同一个 `Game`」与「每窗新建 `Game`」的 finding **逐项一致**（`seekTo` 无状态）。

**共同机制**：高亮期参与者（接球者 / 抢断双方）**被排除出 movers、且 `st.pos` 冻结在动作前
位置**（`tick` 高亮分支 / 各 `emit_*` 的 `beat_movers(&[from,to], &[from,to])`）。但 viewer 在
参与者的**两个同事件锚点**间线性插值，把它从**动作前位置**沿直线滑到**高亮终态**（接球者 =
落点 `x2/y2`；抢断 = `subject_end`/`carrier_end`）。于是分离 solver 只把参与者当作**静止一点**，
**看不见这条滑行直线**——队友 mover 的拍内轨迹可与它交叉到 <2m，而端点检查（用的是「动作前
静止点」）看不见。

- **seed 59**：传球飞行 [3896, 3898.59] 内，接球者（id4）从 (24.69,32.01) 沿直线滑向落点
  (26.87,32.74)；队友 mover（id2）同拍从 (28.13,34.94) 跑到 (24.32,34.18)。二者在**拍中点**
  t=3898.5 交叉到 **1.937m**（两端点却各 ~2.95m ⇒ 纯**拍内扫掠**）。
- **seed 18**：t=1094 抢断（subject=id4）的结算点 `subject_end`=(10.5,32.49) 成为 id4 下一拍的
  **起点**，与队友 id2 的上一拍终点 (12.43,32.68) 相距 **1.931m**；结算点写回 `st.pos` 时**未与
  同队队友分离**（`finalize_highlight`/emit 处的同队分离只覆盖**被抢者** `carrier_end`，**不覆盖**
  抢断者 `subject_end`），⇒ 下一拍起点越界、起点不可动 ⇒ 整拍残留。

⇒ 与 §7.5 的 p53 修（PassCaught 补 `separate_target_point`）**不是同一条路径**：p53 修的是
**接球点这个端点**（发射时就分离）；本节修的是**参与者的整条显示轨迹**（拍内扫掠的参与者侧）。

### 8.3 修法（`engine/src/lib.rs`，最小、有原则）

把**高亮参与者的拍内滑行段**作为**冻结线段**纳入既有的同队分离 solver（`separate_same_team_m`）：

1. `Highlight` 增 `t_start`（= 动作事件 tick；viewer 的滑行历时 `[t_start, t_end]`）。14 个
   `Highlight { .. }` 构造点各加 `t_start: t`（纯字段，零行为）。
2. `commit_beat_positions_ex` 增形参 `frozen_segs: &[(id, from, to)]`：这些 id 一律按**冻结**
   处理（只作约束、**不**被推移、**不**写回 `st.pos`、**不**补 mover），但其 `before`/`pos`
   被覆写为**本拍滑行子段** `[lerp(t), lerp(t+1)]`，从而进入 `sweep_pair_lateral` 的扫掠检查。
   其余调用点传 `&[]`（行为不变）。
3. 新 `highlight_frozen_segs(st, t)`：为**每个**参与者的滑行段算本拍子段；起点 = `st.pos[id]`
   （冻结 ⇒ 即动作前位置），终点 = 参与者终态。起点==终点者（传球者/射手/门球门将）退化为一点，
   等价旧行为。
4. `beat_movers` 调 `commit_beat_positions_ex(.., &highlight_frozen_segs(st, t))`——高亮飞行期
   的每一拍（含 emit 那一拍）都自动带上。

**没有**放宽任何阈值/detector 门；是**新增一条约束**（把 viewer 的显示滑行段补进分离）。
修完默认集 **0 findings**（见 8.4）。
