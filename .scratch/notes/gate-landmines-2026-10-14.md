# ① 标尺 / 门禁「自伤」清单（供过目，暂无代码改动）

**日期**：2026-10-14 · **背景**：C5（站位表 x 压缩）与 y 轴两轮的判据镜各自查到——**门禁里有带会随机红**，
会让每一轮探索把噪声误判成「是我这次改动破的」。本 note 逐条给出真实锚、改法与成本。
真实锚一律来自本仓 `research/2026-08-23-match-realism-testability/report.md` §6（PL 官方 / StatsBomb / Opta，带引文编号）。

---

## 1. `width` → 从「距离标量」降级为**报告行**（改工具，不动引擎）

- **依据**：`viewer/match-metrics.js:234` 是 `Math.max(...ys) - Math.min(...ys)`（**未裁剪极值统计量**）；
  而 `hd`/`ad` 早已是 `q10–q90`（P37 用户拍板）——**两个估计量不对称**，模块自己的注释也写着
  「报告项；**不承载校准目标**」。
- **实测（y 轴判据镜）**：引擎 `width` 逐 90 s 窗**几乎常数**（sd≈0.5，极值恒由 id5/id8 两根固定车道撑起）；
  真实 `width` 窗间跳 **13.9–53.6**（sd≈9 m）。⇒ **拿一个近常数去拟合一个 sd 9 m 的量**；
  「把 width 的均值修进带」没有意义（y 轴实测：修进去的同时把「有人贴边」从 11.7% 打到 0.03%）。
- **改法**：`tools/visual-review/like-football.mjs` —— 把 `width` 从 `LOSS_METRICS`（进距离标量）
  移到**旗标/报告行**（像 `dir` 那样只打印、不进 `mean|ln|`）。同步改 `like-football.test.mjs`
  （它现在把 width 算进 bad/fb4 的分数）。
- **成本**：小。**不需要重生成真实基线**（真实侧那行照旧从 committed 基线打印）。
- **不做**：不改 `match-metrics.js` 的估计量——那会触发基线重生成（要重下 1.82 GB 真实数据 + 重跑转换器），
  成本大且对判断无必要。

## 2. `角球单场max ≤ 15` → 改成**分布护栏**（改门，附真实锚）

- **依据**：`engine/tests/realism.rs:848` 自述是「单场硬上界兜数量级漂移」；它是对 **200 场取 `max`** 的
  **极值统计量** ⇒ **随机红是必然**。判据镜在 **pristine main** 的块 1601–1800 实测 **16 ⇒ 破**
  （7 块序列 14/14/13/12/14/11/**16**）。
- **真实锚**：report §6 / `:24` / `:132`——**角球 ~6–14/场（双方），典型 ~10**（引 [15]）。
  ⇒ 真实数据上 200 场的单场 `max` 估计在 **18–22**（Poisson 近似，**待核**）——
  **`≤15` 这条在真实数据上也会破**；它不是真实锚，是引擎量级护栏。
- **改法（择一，倾向 A）**：
  - **A（分布护栏）**：改成「200 场中 ≥16/场的场次比例 ≤ 5%」——保留「不爆炸」的意图，去掉极值抖动。
  - **B（按真实重锚）**：先拿到真实**逐场角球分布**，再按真实单场极值定上界。
- **附带（只写进 spec、不加断言）**：均值带 `[1,7]` 是**护栏带**，而真实是 **6–14**——
  引擎 4.83 **低于**真实下沿。**这不是「达标」，是「引擎角球偏少」**，别把它当校准目标（`adversarial-explore` 硬纪律第 10 条）。

## 3. `禁区内进球占比 [0.72,0.92]` → **带不动，查引擎回归**

- **真实锚**：report §6 / `:127`——**~85–88% 的进球来自禁区内**（2024-25 禁区外进球 11.7%；引 [18][20]）。
  带中心 0.85 就是这个锚，**下沿 0.72 是为了让引擎过而放宽的**。
- **引擎轨迹**（同一测试的注释 + 判据镜实测）：P9 时代 **86.9%** → #104 后 **0.753** → **今天 0.7211**
  （判据镜：pristine main 的 7 个互不相交 200 场块 **3 块破**：0.7143 / 0.7184 / 0.7102，块均值 ≈0.7227、sd≈0.0092，
  即**下沿落在均值下方 0.30σ**）。
- ⇒ 这不是「带太紧」，是**引擎在看不清的地方退了 4 个点**（0.753 → 0.7211），而 0.13 宽的下沿把它遮住了。
- **建议**：**立项查回归**——在 `dc86ca1^`（p143r-v4 之前）与现在的 main 上、**同一 seed 集**跑 200 场
  对比 `inside_r`（每轮 ~215 s，便宜），定位是哪次改动压下去的。带**只在引擎修回真实锚之后再收窄**
  （例如收到 `[0.80, 0.92]`）；**现在放宽 = 消音**。

## 4. 明确**不做**的（一并写清，免得后来者重复调查）

- **`spacing` 的 0.137 m 余量不动**：它是真实分离不变量（目标 2.2 / 扫掠地板 2.14 / 检测阈值 2.0）的余量，
  **不是标定错误**。只建议在 spec 里写明：「该门在基线只剩 **6.9%** 余量；任何压小典型同队间距的改动必红」
  ——并注明 **y 轴已实测：它与横向宽度正交**（压宽 25% 只消耗 0.0007 m）。
- **`射正率` 上界 0.39 / `转化率` 上界 0.14 不动**：`.scratch/notes/19-band-provenance-2026-10-01.md` 已判
  「上界按 engine 现状配（P9 遗留）」，**属另案**。
- **`l3_shot_ratios` 的另外两条（射正率/转化率）不因本项连带改**：第 3 条的结论是「先修引擎，再谈带」。

## 5. 需要点头的三件事

3. **立一个项**：`禁区内进球占比` 的引擎回归调查（比较 `dc86ca1^` vs main）。
