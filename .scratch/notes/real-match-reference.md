# 真实比赛对照（tracking → 2D 圆点）

> 状态：**已实现可跑**（2026-09-18）。这条通路独立于引擎，是调参/校准的**参照物**。
> 立项动机（用户原话）：「现在咱们调来调去，我只能用语言来描述感觉不对劲的地方，还是很局限，
> 比如直接找现实中的比赛能不能转成 2d 这种格式来参考，以及观察行为」

## 一句话

公开的足球 tracking 数据本身就是**逐帧 22 人 + 球的位置**——它跟我们引擎产出的 `beat`
（每拍若干球员的 from→to）是同一类东西的两种采样。所以不需要"把真实比赛编译成事件流"：
把 tracking 按时间插值，直接喂给**同一个** `renderFrame` 就能播，球场、圆点、配色全部复用。
真实比赛和我们的比赛因此可以背靠背切换播放，肉眼对照。

## 为什么不是"转成事件流"

事件流是我们引擎的**输出格式**，带演绎语义（谁传球给谁、射门结果、抢断成败）。tracking 里
没有这些——只有位置。硬要反推事件（possession/传球识别）是一整个研究领域（见
`socceraction` 等），投入大、误差不可控，而且**反而丢掉了对照的价值**：

- 对照的价值就在于它是**没经过我们引擎加工**的原始行为。
- 一旦经我们的演绎层渲染，看到的就又变成"我们的引擎认为比赛该怎样"，失去了参照意义。

所以设计上是**绕过引擎与演绎层**的旁路：`tracking JSON → TrackingPlayer → renderFrame`。

## 数据源

第一批用 **Metrica Sports sample-data**（GitHub 公开，`metrica-sports/sample-data`）：

| 场次 | 格式 | 采样 | 时长 | 球缺失率 |
|------|------|------|------|----------|
| Sample Game 1 | 3-CSV（每队一个 tracking + 一个 events） | 25Hz | 5800s | 39.1% |
| Sample Game 2 | 同上 | 25Hz | 5646s | 41.0% |
| Sample Game 3 | EPTS/FIFA 纯文本 + events.json | 25Hz | 半场 | 未支持 |

- 坐标：**0-1 归一化**，球场 105×68m，(0,0) 在左上、(1,1) 在右下。
- 每队 CSV 最多 **14 名球员**（11 主力 + 最多 3 替补），门将的球衣号是 **11**（不是 1）。
  列名通常形如 `Player15`，但**实测有 `Player 26`（带空格）的写法**，解析需容忍。
- 许可：**未声明正式许可**。README 要求注明来源、负责任使用。当前定位是本地开发/研究用途，
  不对外分发数据本身（数据与转换产物都在 .gitignore 里）。

其他候选见调研报告（SkillCorner opendata 9 场 broadcast tracking、Last Row、StatsBomb 360 等），
`tools/fetch-tracking-data.mjs` 的 `DATASETS` 表是接入点。

## 怎么跑

```bash
# 1. 拉数据（一次性，约 60MB，落 .scratch/tracking-data/，不入库）
node tools/fetch-tracking-data.mjs

# 2. 转成 viewer 能吃的帧序列（落 viewer/data/，不入库）
node tools/convert-tracking-to-frames.mjs \
  --in .scratch/tracking-data/sample-data/data/Sample_Game_1 \
  --out viewer/data/real-game-1.json --keyframe-hz 5
# Sample_Game_2 → viewer/data/real-game-2.json 同理
# 可选：--from/--to 裁时间窗（秒）；--ball-fill nearest|hold|none 切缺球补全策略

# 3. 起 viewer，数据源选「真实比赛（对照）」
cd viewer && python3 serve.py 8000
```

`viewer/data/` 不存在时 viewer 会在状态栏提示生成方法，不会静默失败。

## 三个必须处理的坐标/身份问题（都已在转换器里解决）

1. **半场方向必须从数据检测，不能硬编码**。引擎的约定是「主队永远从 x=0 攻向 x=1」，
   而 Metrica 的 x 是固定球场坐标、上下半场换边。**关键在于：两场比赛的起始方向约定是
   相反的**——

   | | P1 主队门将 | P2 主队门将 |
   |---|---|---|
   | Sample_Game_1 | x≈0.12（左） | x≈0.92（右） |
   | Sample_Game_2 | x≈0.87（右） | x≈0.11（左） |

   所以「P1 翻转、P2 不翻转」这种写法在 game1 上正确、在 game2 上把**整场镜像**
   （两队左右颠倒），而且因为 game1 正常而极难发现。转换器改为
   `detectHomeAttackDirection()`：用最贴底线的球员（通常是门将）在哪一侧来判定，
   再由 `makeNormalizer()` 按半场翻转。检测结果写进 `meta.orientationDetected`。

   **两个必须注意的实现细节**（都是踩过的坑）：
   - **检测必须在全量帧上做，不能用 `--from/--to` 裁剪后的帧**。朝向是整场比赛的属性；
     短窗口里"最贴底线的人"可能是开角球的边后卫或禁区内的防守球员，据此判定会静默镜像
     （实测 game1 的 55-65s、630-750s 窗口都判反）。全量帧让偶发个例在平均中抵消，
     于是裁剪只影响输出范围、不影响朝向。
   - **找不到 P1 时不能拿 P2 的观测去填**（例如 `--from 3000` 裁出的纯下半场片段）。
     门将在 P2 换到另一端，用 P2 推 P1 必然相反。检测函数会识别样本实际覆盖的半场，
     再把结论换算到两个半场。

   判据用「最贴底线的人」而非"认定门将"，因此门将大幅压上时由留守的后卫胜出，仍然判对。

   - 回归护栏：`convert-tracking-to-frames.test.mjs` 与 `tracking-e2e.test.js` 都
     **两场各测一遍**，且做过变异验证（强制回硬编码 → game2 用例变红、game1 仍绿）。

2. **y 轴朝向**。Metrica 原点左上（y 向下），引擎是左下（y=0 在下边线）。
   `renderFrame` 的 `normalizedToPixels` 做 `py = margin + (1-y)*h`，所以转换器把 y 翻成
   `1-y` 后，两者语义就对齐了。这一步与方向无关，恒定。

3. **身份映射到 0-10 / 11-21**。不能按球衣号排序（门将是 Player11，排中间）。
   用**距离本方门线的平均距离**识别门将，且这个量必须在按上面检测出的朝向折算后的
   坐标系里算（把每帧摆成「该队攻向 x=1」，本方门线恒在 0，depth 越小越靠后：
   门将 < 后卫 < 中场 < 前锋），据此排槽位。

   踩过的三个坑（都由 `tools/convert-tracking-to-frames.test.mjs` 守住）：
   - 用整场 x 中位数 —— 换边把它抵回 0.5，门将认不出；
   - 用 `min(x,1-x)` —— 在 x=0.5 折叠，过中场的前锋被排到后卫后面；
   - **硬编码半场方向** —— 见上面第 1 条，会整体镜像。

   替补：主力 = 出场帧数前 11 名，其余为替补；主力缺席的帧由在场替补顶上该槽位，
   保证每个关键帧恒定 22 人。

## 数据质量的如实处理

以下各项都是**参照数据本身的局限或数据不规整**，不是转换错误。转换器把它们如实统计进
`meta.coverage` 并在 viewer 信息条展示——静默修饰比暴露问题更误导。

- **球缺失 39-41%，且是长时段**（实测最长连续 **131 秒**）。缺球时把球放到**离最后已知球位
  最近的球员**脚下（默认），该帧打 `ballFill: <id>` 标记；viewer 状态栏显示"球位置为推断"。
  - 曾考虑直接沿用上一位置（`hold`），但那会让球原地冻结两分钟，反而误导观察。
  - `--ball-fill hold|nearest|none` 可切；`none` 保留 null 不做任何推断。
- **场上人数不足 22**：用 `meta.coverage.shortHandedPct` 标记，viewer 信息条显示"人数不足帧 x%"。
  当前两场数据都是 0%（见下条的教训），保留该指标作为**未来数据不规整时的安全网**，
  避免"少一个圆点"被误当成渲染 bug。
- **表头列名可能有空格**：Sample_Game_2 客队第 26 列写作 `Player 26`（**带空格**）。
  严格正则 `/^Player(\d+)$/` 会静默丢掉这名球员，导致该队整场少一人
  （实测造成 37.7% 的帧只有 21 人——一度误判成"源数据只有 11 人"）。现在正则容忍空格
  （`/^Player\s*(\d+)$/`），且**遇到疑似球员列却解析不出来时直接报错**，不静默丢人。
- **坐标重叠伪影**：同一帧两名球员坐标完全相同。实测 Sample_Game_1 原始数据里主队队内就有
  1.78% 的帧；转换到 5Hz 后合计 **4.86%** 的帧有重叠（同队 802 对、跨队 756 对）。
  **跨队精确重合在物理上几乎不可能**，是追踪伪影而非真实贴身；渲染时表现为两个圆点完全
  重叠（看起来像一个，会误读成"少了一个人"）。
  - **刻意不去重**：挪动球员位置会让画面对不上真实数据，观察者无从知道哪里被改过。
  - 用 `meta.coverage.duplicateCoordPct` 标记，viewer 信息条显示"坐标重叠 x%"。
  - 真实数据里的典型例：`t=0.0s id8(H) == id12(A)`、`t=96.2s id4(H) == id8(H)`。

## 实现里几条通用的正确性原则（踩坑后总结）

这些不是足球领域知识，而是"参照物"这个定位本身要求的：

1. **画面只由「此刻及之前」决定**。球员、球、球是否可见，都必须是**帧号的纯函数**，
   不能依赖播放路径。否则「拖进度条直达某刻」与「顺着播到某刻」会给出不同画面。
   预计算 `lastKnownAt` / `lastKnownBallAt` 表就是为此——倒带时不会残留未来位置。
2. **朝向是整场比赛的属性**，必须用全量帧判定（`--from/--to` 只影响输出范围）。
3. **宁可报错也不猜**。方向检测失败、表头有无法解析的球员列——都直接抛错。
   静默给错（镜像、少一人）比显式失败危险得多：前者在小窗口上几乎不可能被肉眼发现。
4. **数据质量如实暴露**，不用"修复"掩盖：缺球补全打 `ballFill`、重叠坐标只统计不去重、
   人数不足只统计不补人。挪动位置会让画面对不上真实数据，观察者无从知道哪里被改过。
5. **异步加载要有"作废"机制**。数据源切换是异步的（一场 18MB），用户在加载途中能做的事
   很多：切回引擎、选别的场次、选回当前场……每一个出口漏处理都会造成「控件与画面错位」。
   做法是 `loadSeq` 请求序号 + 调用方检查返回值，并且**每一个改变数据源的路径都必须 bump
   `loadSeq`**（包括"已经是这一场"的早退分支）。
6. **UI 状态要从单一真相源推导，不要在事件处理器里就地写**。`syncSourceUI()` 把
   「数据源下拉框 / 场次选择可见性 / 事件导航禁用」三态统一从 `activeSource` 推出。
   反例是把 `sourceSelect.value = 'tracking'` 写在 `await` **之前**——加载失败或被作废时
   没人拨回来，于是"下拉框说真实比赛、画面是引擎"。这一族竞态（F1/F3/X1/X2/A/B）
   共出了 **6 个变体**，最终靠"收敛到单一推导函数 + 穷举交错矩阵测试"才收口。
   （教训：当同一类 bug 反复以新变体出现时，说明状态机分散在设计里，该收敛而不是继续打补丁。）

## 已知边界

- **tracking 模式下不能做观察采集**（点采集会被拒绝并提示）。原因是采集链路读的是引擎的
  `game` 对象（含事件流、赛场时刻），而 tracking 没有事件流——采到的会是"引擎冻结的那一刻"
  而不是用户正看的真实比赛。要支持"对着真实比赛做观察"需要单独设计采集的数据来源，
  不是放开守卫就行。

## 结构

```
tools/fetch-tracking-data.mjs          拉公开数据集（.scratch/tracking-data/）
tools/convert-tracking-to-frames.mjs   tracking CSV → 帧序列 JSON
tools/convert-tracking-to-frames.test.mjs
viewer/tracking-player.js              帧序列 → 每帧 { players, ball }（插值/播放控制）
viewer/tracking-player.test.js
viewer/tracking-e2e.test.js            真实数据 → renderFrame 的像素级验收
viewer/app.js                          数据源切换（引擎比赛 ↔ 真实比赛）
viewer/index.html                      #data-source / #tracking-select / #tracking-meta
```

帧序列 schema（v1）：

```jsonc
{
  "meta": { "source", "game", "hz", "keyframeHz", "frames", "startTime", "endTime",
            "coord", "orientation", "idMap", "coverage" },
  "frames": [ { "t": 0.04, "players": [[x,y]|null × 22], "ball": [x,y]|null,
                "ballFill": 11 /* 仅补全帧，数字=持球者 id */ } ]
}
```

`players` 下标即事件协议球员 id（0-10 主队 / 11-21 客队），与引擎的事件流同一 id 方案——
两边能直接并排对照，不需要额外的映射层。

## 如何用它校准（下一步）

现在能看，但还没形成**闭环**。可做的方向，从省力到费力：

1. **并排对照**（已具备）：同一块球场切换数据源，肉眼比对站位紧凑度、队形伸缩、
   攻防转换速度、球速。
2. **量化指标**（最有价值，已验证可行）：从两边各算同一组统计量，把"感觉不对"变成
   可比的数字。这一层不需要看画面，能进 CI，完全符合项目「验证不得依赖视觉」的约束。

   已跑过可行性探针（真实数据 game1 的 600–900s 窗口，1500 帧 @5Hz）：

   | 指标 | 真实比赛实测 |
   |------|-------------|
   | 主队平均队形宽度 | 40.1 m |
   | 主队平均队形纵深 | 58.2 m |
   | 客队平均队形宽度 | 39.9 m |
   | 客队平均队形纵深 | 49.5 m |
   | 主队宽度 p10–p90 | 29.6 – 51.6 m |

   有合理量级、有波动（= 有信号），足以区分"阵型太扁/太散/纵深不够"。做法是把同一组
   函数分别喂给 TrackingPlayer 的帧与引擎事件流的时间线，输出可直接对比的数字。

3. **模板匹配**：从真实数据切出典型场景（反击、定位球、压迫），在我们的引擎里造同样
   起点的场景，对照行为差异。

第 2 条是把这条通路从"玩具"变成"标尺"的关键一步，建议作为下一个 change 立项。
